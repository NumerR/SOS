# 03. Неизвестные требования и решения

Три вопроса блокируют Этапы 5-6 и выбор топологии. Остальное Агент 1 закрывает безопасным разумным решением и документирует допущение (бриф, п.9).

## 1. Требуют ответа владельца

### B1. Топология: GitHub Pages + внешний backend ИЛИ один Go-хост

Причина: от этого зависят структура фронтенда (абсолютные vs относительные пути, `API_BASE_URL`), модель cookie и объём работы по CORS. Сейчас приложение работает как единый Go-хост и полностью пригоден в этом виде.

| | A. Один Go-хост | B. Pages + внешний backend |
|---|---|---|
| Работа сегодня | да | требует переработки путей и конфига |
| Cookie-авторизация | same-origin, `SameSite=Lax` | cross-site: `SameSite=None`, блокировка в Safari на iOS |
| CORS/HTTPS | не нужны отдельно | allowlist + обязательный TLS |
| Соответствие букве брифа | частично (Pages не используется) | полностью |
| Риск | низкий | средний-высокий (вход на мобильных) |

Рекомендация: **A** для MVP; B — вторым релизом, если требование Publish на Pages строгое.

### B2. Доступ к источнику расписания

Фронтенд ссылается на `https://tksu.ru/bitrix/js/api-apeks-vuz/rasp-stud/rasp-stud.html` (`web/schedule.html:54`). С этого хоста `tksu.ru` недоступен (TCP «Network is unreachable» при работающем интернете), снимков виджета в веб-архиве нет. Реальные эндпоинт, параметры (группа, дата, семестр) и формат ответа неизвестны. Придумывать структуру сайта запрещено брифом, поэтому нужны:

1. URL страницы/эндпоинта, который браузер реально вызывает при выборе группы (взять из DevTools → Network: XHR/fetch запрос виджета).
2. Пример ответа (JSON или HTML) для одной конкретной группы — можно без масок, это публичные данные.
3. Список групп/справочник, если он отдельным запросом.
4. Подтверждение, что у источника нет требования авторизации/CAPTCHA (если есть — парсинг откладываем, это прямое ограничение брифа).
5. Часовой пояс расписания и семестровая сетка (начало/конец, номера пар, перерывы).

Альтернативы, если прямого доступа нет: официальный API университета, экспорт по запросу, ручной импорт файла расписания (CSV/XLSX) через админку — последний вариант реализуем без внешнего доступа и снимает блок.

### B3. Источник событий (Telegram)

`api.telegram.org` и `t.me` с этого хоста недоступны, канал в брифе не назван. Нужны:

1. Имя (username) канала и 3-5 примеров постов с реальные форматированием (дата/место/название).
2. Является ли владелец канала тем же человеком, что и проект, и готов ли добавить бота в администраторы канала — без этого Bot API не отдаёт `channel_post` и историю сообщений.
3. Если нужен архив старых постов: подтверждённый экспорт (Telegram Desktop «Export chat history») или иной разрешённый источник.
4. Категоризация: брать из хэштегов поста, из справочника, или без категории.
5. Геометка: координаты берём только из явных ссылок/приложенной точки геолокации поста; адреса не геокодируем без выбранного разрешённого сервиса (бриф требует «нет вымышленных координат»).

## 2. Допущения, принятые командой (меняются одним решением, без переписывания кода)

| # | Допущение | Почему |
|---|---|---|
| A1 | PostgreSQL как основная БД, SQLite уходит | требование брифа; плюс SQLite с `SetMaxOpenConns(1)` (`db.go:26`) не даст параллельных фоновых импортёров |
| A2 | Миграции — embed-файлы SQL + `schema_migrations`, собственный runner ~150 строк | внешняя `golang-migrate` — лишняя зависимость для проекта, который читают изучающие Go |
| A3 | bcrypt остаётся (не Argon2id) | уже работает и корректен; смена алгоритма без причины не оправдана |
| A4 | Формат времени в API — RFC 3339 UTC, день занятия — `YYYY-MM-DD`, `TZ_NAME` в конфиге | устраняет текущий баг локального времени сервера (`handlers/schedule.go:60-65`) |
| A5 | Роль `teacher` не выдаётся при саморегистрации | закрытие дыры из отчёта 01 §4.1; назначается админом |
| A6 | Единый формат ошибки `{error:{code,message,fields}}` | фронтенду нужно различать 401/403/422; бэкенд+фронт+тесты обновляются одновременно |
| A7 | Дизайн-система: текущая палитра (parchment + petrol-teal) или тёмно-синяя из брифа — ждём ответа; до ответа новые страницы верстаем на существующих токенах | переделка палитры трогает 589 строк CSS и 6 страниц; менять «на всякий случай» нельзя |
| A8 | Модульность = `internal/modules/*` + явный реестр, без Go-plugin | требование «подключать модуль без переписывания ядра» выполняется и так, без динамической загрузки |
| A9 | Тесты на PostgreSQL в GitHub Actions (сервис-контейнер), локально — `docker compose` | даёт проверяемый прогон без ручного развёртывания БД |

## 3. Известные ограничения, которые не блокируют MVP

- Восстановление пароля и подтверждение email не проектируются, пока не выбран способ доставки (бриф требует сначала спроектировать безопасный процесс).
- Страница 404 и стилизованные ошибки: при варианте A отдаёт Go-сервер, при варианте B — Pages. Решение следует из B1.
- Карта событий: поставщик тайлов (OSM/Leaflet vs свой список без карты) выбирается после B3, потому что без реальных координат карта пуста.
- Ограничение размера тела запроса сейчас 1 MiB и только в `readJSON` (`response.go:30`); под загрузку изображений событий понадобится отдельное хранилище и политика — вне MVP.

## 4. Правила ревью и интеграции (для всех агентов)

1. Ветка на задачу, имя `feat/<module>-<short>` или `fix/<short>`; `main` не трогаем напрямую.
2. Изменения контрактов (API, схема, env) — только через ADR, принятый Агентом 1.
3. PR не готов к ревью без: `go vet ./...` чисто, `go test ./...` зелёный, миграция применяется на чистой БД, фронтенд-смоук пройден.
4. Ревью проверяет по чек-листу: параметрический SQL, таймаут контекста, лимит длин полей, проверка прав на сервере, отсутствие секретов в коде/логах, отсутствие `innerHTML` с неэкранированным значением, наличие теста на новый путь.
5. Никаких фиктивных данных в production-интерфейсе без явной маркировки; если интеграция не готова — состояние «ожидает подключения» вместо заглушки (бриф, п.8, критерии MVP).
