# 01. Отчёт о состоянии проекта

Все утверждения ниже либо проверены запуском команд, либо подтверждены чтением кода с указанием `файл:строка`. Непроверенное помечено «не проверено».

## 1. Что это сейчас за проект

Один Go-сервер (`net/http`, стандартная библиотека) плюс статический фронтенд на Vanilla JS, который **раздаёт тот же Go-сервер**. База — SQLite на `modernc.org/sqlite` (без CGO). Сборщиков, фреймворков и ORM нет.

Объём на 2026-10-26 (после ADR-0033): 55 файлов продуктового Go — 10177
строк, 28 файлов тестов Go — 9226 строк (17 пакетов `go list ./...`), фронтенд — 3049 строк JS +
932 HTML + 768 CSS, jsdom-сьюты — 2838 строк в девяти файлах (восемь гоняет `test:all`,
девятый — `schedule-source-python.cjs` — своим прогоном), проверки без сборки —
2099 строк в трёх скриптах (`check-frontend.mjs` 805 + `check-focus.mjs` 891 +
`check-docs.mjs` 403),
живые прогоны в шелле — 724 строки в четырёх скриптах (`schedule-source-python.sh` 99 +
`source-states-smoke.sh` 229 + `run-live.sh` 177 + `db-outage-live.sh` 219; последние восемь
сьютов гоняет именно третий — см. ADR-0026).
Пропорция тестов к
коду перестала быть стыдной: тестового Go почти столько же, сколько продуктового
(0,91 : 1). Исходная оценка («3118 строк Go, 4 пакета, тестов нет») относится к
базлайну Этапа 1.

История коммитов на момент исследования: 7 коммитов, все в `main`, веток нет. CI нет, тестов нет, каталога `.github/` нет, `migrations/` нет, `docker-compose` нет. (Сейчас это уже не так — см. § «Статус после T0.2» и таблицу PR в документе 04.)

Реализованные бизнес-сущности: пользователи, сессии, курсы, записи на курсы, задания, сдачи и оценки, ресурсы, события, агрегирующая лента «дедлайны + события».

## 2. Проверено запуском (фактический базлайн)

```
go build ./...   → успех (скачал golang.org/x/crypto, компиляция чистая)
go vet ./...     → успех, замечаний нет
go test ./...    → "no test files" во всех 5 пакетах
```

Сервер поднят локально (`go run ./cmd/server`), проверены живые сценарии:

|---|---|---|
| Health | `GET /api/health` | 200 `{"status":"ok"}` |
| Регистрация | `POST /api/auth/register` (student) | 201, возвращён объект пользователя |

Вывод: каркас авторизации, сессий и CSRF работает и пригоден как основа. Тестовая БД `data/` после проверки удалена, сервер остановлен.

## 3. Критическая находка: UI заданий и оценок не работает

Функциональность «задания/сдачи/оценки» добавлена на бэкенде, но её фронтенд не подключён ни к одной странице:

- `web/js/modals.js` содержит `ModalManager` и `window.renderStudentAssignments`, но **не подключён ни в одном HTML** — `grep -rn "modals.js" web/` не даёт ни одного совпадения.
- `web/js/dashboard.js:228-233, 301, 331, 343` вызывает `ModalManager.open(...)` и `window.renderStudentAssignments(...)`.
- `web/js/modals.js:2-5` ищет элементы `#modalContainer`, `#modalTitle`, `#modalBody`, `#modalCloseBtn`; их нет ни на одной странице (`grep` находит `modalContainer` только внутри modals.js).

Практический эффект: клик по «Задания» / «Управление заданиями» / «Новое задание» на дашборде даёт `ReferenceError: ModalManager is not defined`, модальное окно не открывается. Сам API (`/api/assignments`, `/api/submissions`, `/api/submissions/grade`) работает и защищён корректно.

Статический вывод уверенный; повторить в браузере: открыть `/dashboard`, нажать «Задания» на любом курсе, посмотреть консоль (не проверено визуально — браузер в этой среде недоступен).

## 4. Находки по безопасности (бэкенд)

Высокий приоритет:

1. **Самовыдача роли `teacher`.** `internal/handlers/auth.go:35-45` пропускает `teacher` из публичной регистрации. Любой созданный аккаунт получает право создавать курсы (`internal/handlers/courses.go:38`), задания, оценивать чужие сдачи и читать списки студентов своих курсов. README:52-55 утверждает обратное только про `admin`.
2. **Нет ограничения частоты запросов вообще.** `grep` по `ratelimit|limiter` — 0 совпадений. `/api/auth/login` (`main.go:81`) открыт для подбора пароля; `bcrypt` на каждый запрос = вектор отказа в обслуживании.
3. **Отзыв сессий неполный.** `Logout` (`auth.go:169-172`) удаляет только текущую сессию; `SessionStore` не имеет `DeleteAllForUser` / `DeleteExpired` (`store/sessions.go` — только Create/Get/Delete). Протухшие строки копятся, фильтруются лишь при чтении (`sessions.go:73`). Смены пароля в API нет вовсе, значит отзыв сессий при компрометации невозможен.
4. **User enumeration по таймингу.** `auth.go:139-148` возвращает 401 до вызова `bcrypt`, если пользователь не найден, и после — если пароль неверный.
5. **Шаблон уязвимости XSS во фронтенде.** `dashboard.js:259` и `modals.js:84` вставляют заголовок задания в JS-строку внутри атрибута `onclick`: `'${GS.escapeHtml(a.title)}'`. `escapeHtml` заменяет `'` на `&#039;`, HTML-парсер декодирует его обратно до разбора JS — апостроф в названии задания выводит из строки. Хранящийся XSS через название курса/задания. Нужен перенос обработчиков на `addEventListener` + `data-id`.
6. **`Secure` у cookie снимается при подделке заголовка.** `auth.go:236-246` доверяет `X-Forwarded-Proto`; при plain HTTP между прокси и приложением это открывает выдачу незащищённого cookie. Префикса `__Host-` нет.

- **1 — закрыто.** Публичная регистрация создаёт только `student`; `teacher`/`admin`
  назначает администратор через `POST /api/admin/users/role` (`RequireRole` + `RequireCSRF`,
  сам себе роль менять нельзя). Проверено тестами и живыми запросами.
- **2 — закрыто.** `internal/ratelimit` (токен-бакет) + middleware на `login`/`register`:
  20 запросов/10 мин на IP для входа, 10/час на IP для регистрации, 5 неудачных
  проверок пароля на аккаунт за 15 мин. Ответ `429` с `Retry-After`.
- **3 — закрыто.** `DeleteAllForUser` + `DeleteAllForUserExcept` + `DeleteExpired`;
  `POST /api/auth/logout-all`; `POST /api/auth/change-password`; фоновый сборщик
  `cleanSessions` в `cmd/server/main.go` (первый проход сразу при старте, далее раз в час,
  `context.WithTimeout` 30 с на проход).
- **4 — закрыто.** Сравнение с bcrypt выполняется всегда, неизвестный логин
  проверяется против фиктивного хэша.
- **5 — закрыто в T0.1** (переход на `data-*` + делегирование вместо `onclick`).
- **6 — закрыто в T0.3.** `X-Forwarded-Proto` не читается без `TRUST_PROXY=true`
  (`isSecureRequest`), так что на plain HTTP кука `Secure` не снимается подделкой
  заголовка. При защищённом запросе сессия выдаётся как `__Host-gs_session`
  (`HttpOnly`, `Secure`, `Path=/`, без `Domain`); на локальном HTTP остаётся
  `gs_session`, иначе префикс ломает прогон без TLS. Чтение куки перебирает оба
  имени, снятие — всегда оба. Остаток риска: `csrf_token` сознательно не `__Host-`
  и не `Secure` — его читает JS для заголовка `X-CSRF-Token`, а `SameSite=Lax`
  + double-submit покрывают сценарий.
- Пункты среднего приоритета: верхняя граница длины пароля введена в T0.2
  (`maxPasswordLength`); в T0.3 добавлены лимиты длины для всех остальных
  текстовых полей (`internal/handlers/fields.go`, ответ `422` до обращения к БД),
  структурированный лог (`slog`), таймауты `http.Server` и graceful shutdown,
  `context.WithTimeout` на каждый запрос (`WithDBDeadline`).

Средний приоритет:

- *(закрыто в T0.3)* `http.ListenAndServe` без таймаутов чтения/записи/идеала и без `MaxHeaderBytes` (`main.go:137`); graceful shutdown отсутствует (`signal.Notify` нет, только `defer db.Close()` в `main.go:33`).
- *(закрыто в T0.3)* Ни одного `context.WithTimeout` для обращений к БД (`grep` по `internal/` — 0) — висякий запрос держит соединение; `db.SetMaxOpenConns(1)` (`db.go:26`) усиливает эффект.
- *(закрыто в T0.3)* В `internal/` нет логирования вообще: ошибки слоя доступа к данным превращаются в generic 500 (`internal/handlers/courses.go:25`, `internal/handlers/submissions.go:70` и др.).
- *(закрыто: пароль — в T0.2, остальные поля — в T0.3)* Нет лимитов длины полей у заданий/сдач/оценок: `internal/handlers/assignments.go:102-128`, `internal/handlers/submissions.go:68,196`; пароль не ограничен сверху (`auth.go:79`), а bcrypt читает только первые 72 байта.
  Осталось известное свойство bcrypt: `maxPasswordLength = 200` символов защищает
  обработчик от мегабайтного тела, но два пароля, совпадающие в первых 72 байтах,
  по-прежнему дают один хэш — полный контроль над длиной пароля дал бы только
  argon2id, который сознательно не вносим (docs/02 §7); граница в 200 символов
  принята в ADR-0007.
- *(закрыто ADR-0010, `439a08b`)* Проверка `user.Role == "admin"` и аналогичные ролевые условия разбросаны по ~15 местам вместо единого правила: права спрашивает `authz`, а сравнение роли осталось только в тексте комментария (`internal/authz/authz.go:5`). Координаты прежних мест были снимком дня исследования — после правок ADR-0023…ADR-0032 они съехали, и проверка строк этого не ловит: сверяется длина файла, а не содержимое строки (§6 про ADR-0025).
- Ошибки уникальности определяются сравнением текста строки ошибки (`internal/store/users.go:336` — `isUniqueConstraintError` по подстроке `"UNIQUE constraint failed"`, там же `internal/store/users.go:94` сверяет отсутствие пользователя через `strings.Contains(err.Error(), ErrNotFound.Error())`) — диалект-зависимо и хрупко; 10 мест в `internal/store/*.go` сравнивают `err == sql.ErrNoRows`, и только 2 делают это через `errors.Is`.
- *(закрыто ADR-0029, `27d61ec`)* `internal/handlers/assignments.go`: при ошибке БД флаг `isEnrolled` молча оставался `false` → 403 вместо 500, сбой маскируется под отказ доступа. Тот же класс оказался не один: семь мест в двух обработчиках (3 в `internal/handlers/assignments.go`, 4 в `internal/handlers/submissions.go`) склеивали «строки нет» и «база не ответила» в один ответ — 404 или 403 вместо 500. Сведены к уже существующим в дереве конвенциям (`errors.Is(err, store.ErrNotFound)`, трёхшаговый порядок «сбой → отсутствие → чужое»), зафиксированы тестом `internal/handlers/db_failure_test.go` (224 строки, 8 тестов).
- *(закрыто ADR-0031, `c413422`)* `RequireAuth` при сбое базы отвечает 401 (замерено черновым тестом на копии дерева): `internal/handlers/handlers.go:149-165` в нумерации того дня возвращает `false` на любую ошибку `Sessions.Get` и `Users.GetByID`, а HTML-страницы (`internal/handlers/pages.go:60,70,84` там же) в этом случае делают 302 на `/login`. Хуже остальных случаев класса: политика 401 из ADR-0011 читает это как истёкшую сессию и уводит на вход, вход при лежащей базе тоже не проходит — петля вместо «сервер не справился». Закрыто различением `nil, nil` («входа нет») и `nil, err` («хранилище не ответило») в `authenticatedUser`, точкой `pageUser` для трёх защищённых страниц и `internalError` с `sessionFailureReason` (`internal/handlers/handlers.go:165,49`, `internal/handlers/pages.go:84`); тесты — `internal/handlers/session_failure_test.go`, живой слой — `tests/db-outage-live.sh`.
- 500-страницы в `web/` нет — единственная служебная страница `web/404.html`. Поэтому ADR-0031 и не тронул ветки «входа нет»: браузерный GET при 500 получает JSON-конверт ADR-0003 как тело страницы, и человек видит `{"error":…}` вместо внятного «сервер не справился». Нужное решение — не только ветка в `if`, но и ответ «что отдавать защищённому GET»: отдельная страница или перенос текста отказа в HTML.
- *(закрыто ADR-0030, `4ac5fa5`)* Из 47 вызовов `writeError(w, http.StatusInternalServerError, …)` в `internal/handlers` причину в лог писали четыре места, а не пять, как было записано раньше: `grep` по `requestLogger(r).Error` давал пять строк, но пятая — `internal/handlers/schedule_source.go:675` в нумерации HEAD, где файл тогда занимал 690 строк — относится к 502, а не к 500. Строка доступа при 500 есть всегда (`internal/handlers/logging.go:117-118`, с `request_id`), а `slog.Any("error", err)` — нет, так что «что именно упало» оставалось догадкой; см. комментарий `internal/handlers/logging.go:18`. Закрыто helper'ом `internalError` (`internal/handlers/errors.go:56`): все места пишут `reason` (тот же текст, что видит клиент) и `error`; после ADR-0031 таких мест 49 в 13 файлах (было 47 в 11). Замок — `internal/handlers/error_path_guard_test.go` (статический, по исходникам пакета) и `internal/handlers/internal_error_test.go` (поведенческий).
- *(закрыто ADR-0032, этот коммит)* Молчаливая нулевая дата вместо отказа: при неразобранном `due_date`/`event_date` обработчик не отвечал отказ, а писал `0` — в прежней нумерации `internal/handlers/assignments.go:147`, `internal/handlers/events.go:55`. Клиент получал 201 с записью `due_date: 0`, запись лежала в базе и отдаётся из `/api/assignments`, а в агрегирующую ленту она не попадает никогда: все четыре запроса ленты фильтруют `due_date > 0` / `event_date > 0` (`internal/store/schedule.go:48,110,131,152`). Отказ был проигнорирован дважды — на записи и на чтении, — и ни один слой не сказал ни слова. Закрыто `parseDateField` (`internal/handlers/fields.go:77`): пустое значение (и пробелы) — «даты нет», неразобранное — 422 с названием поля; вызовы — `internal/handlers/assignments.go:144`, `internal/handlers/events.go:52`. Фронтенд перестал подменять нечитаемую дату пустой строкой (`web/js/modals.js:443`, `web/js/schedule.js:641`), а подпись поля для таких input'ов берётся по пару `поле + "_raw"` (`web/js/common.js:57`), иначе человек читал бы «— поле: event_date» вместо «Дата и время». Тот же класс, что закрыл ADR-0029 («не удалось» склеено с «не задано»), но это решение про валидацию ввода, а не про отказ хранилища.
- `writeJSON` при отказе кодирования вызывает `http.Error(w, "json encode error", 500)` (`internal/handlers/response.go:13`) уже после `WriteHeader`, поэтому код физически не уходит, а текст не является конвертом ADR-0003. Правка требует решения о том, что делать с начатым ответом, — в ADR-0030 оставлено отдельной находкой и подписано освобождением в замке, чтобы не растворилась.
- *(закрыто ADR-0033, этот коммит)* В дереве нет `recover()` (`grep -rn 'recover()' --include='*.go'` — пусто): 500 от паники в обработчике идёт мимо `internalError`, его стек попадает в stderr без `request_id`, и в конверте его нет. Замер черновым тестом на копии дерева оказался хуже формулировки: клиент получал не 500, а обрыв соединения (`EOF`) — браузер показывает «нет связи с сервером» там, где сервер живой; в slog не попадало ничего, ни строки доступа (ADR-0025), ни причины (ADR-0030), потому что `net/http` перехватывает панику выше `LogRequests`; `X-Request-Id` терялся вместе с незаписанными заголовками, а стек (1328 байт) уходил в `http.Server.ErrorLog` без request id. Закрыто middleware `Recover` (`internal/handlers/recovery.go:50`) внутри цепочки: 500 с конвертом ADR-0003 через `internalError`, тот же текст в `reason`, стек полем `stack=` той же записи, `X-Request-Id` на месте, и отдельная ветка для уже отправленного ответа (`responseStarter`, `recovery.go:40`; признак поднимает `statusRecorder`, `internal/handlers/logging.go:159`) — там статус менять поздно, поэтому пишется `response_started=true`. Порядок обёрток вынесен в `rootHandler` (`cmd/server/main.go:65`) и закреплен статическим замком (`cmd/server/root_test.go:125`), потому что неподключенный middleware ведёт себя ровно как его отсутствие, а тесты обработчиков про `main` ничего не знают. Тот же класс, что закрыли ADR-0029/0030/0031/0032 («не удалось» и «не задано» склеены), но в обратную сторону: здесь неудача вообще не была ничем — она обрывала ответ.
- `/api/auth/login`, `/register`, `/logout` без `RequireCSRF` (`main.go:79-82`, ограничение признано в комментарии). Для `login` это CSRF-подстановка сессии (session fixation) — низкий, но реальный риск.

Что **не** подтверждено (хорошие новости): SQL-инъекций нет — во всех `internal/store/*.go` только параметрические `?`-плейсхолдеры, `fmt.Sprintf` в SQL не встречается; открытых редиректов в `pages.go` нет (редиректы жёсткие); `javascript:`/`data:` ссылки во фронтенде отфильтрованы allowlistом `schedule.js:121`.

## 5. Архитектура и модульность (оценка TECH LEAD)

Добавление одного нового бизнес-модуля сегодня требует правки 6 мест в 4 файлах: таблица в единой SQL-строке (`database/db.go:43-141`), типы (`models/models.go`), `store/<x>.go`, `handlers/<x>.go`, поле в struct **и** позиционный аргумент `handlers.New(...)` (`handlers/handlers.go:18-53`, сейчас 9 подряд), затем конструктор и маршруты в `main.go:39-61, 63-132`. Реестра модулей, интерфейса регистрации и пер-модульных миграций нет — то есть требование «подключать/отключать модуль, не переписывая ядро» пока не выполнено, хотя слои HTTP/логика доступа к данным уже разделены и код в целом читается.

Уточнение после T1.1 (`439a08b`): из перечисленного закрыто третье и четвёртое —
`handlers.New(handlers.Deps{…})` собирает зависимости по именам полей (с `f1b4c7e`),
маршруты объявлены в `internal/modules/<name>/module.go`, а не в `main.go`, реестр
модулей (`platform.Registry`) и runner миграций есть. Требование «добавить модуль,
не переписывая ядро» проверяемо: новый модуль = пакет + одна строка в `moduleList()`
(приёмка — `docs/how-to-add-a-module.md`, проверено тестовым `notesModule` в
`cmd/server/modules_test.go`). Не закрыто: таблицы и типы модуля по-прежнему живут
в общих `internal/database/db.go`, `internal/models` и `internal/store`, поэтому
полный распад по модулям — за `T2.1`.

Закрыто: `<a class="skip-link" href="#main">` первой ссылкой на восьми страницах и `<main id="main" tabindex="-1">` (без `tabindex` якорь прокручивает, но фокус остаётся в шапке); `h1.page-title` на пяти страницах, `<span class="section-label">` → `<h2>` в 16 местах; `scope="col"` у 11 `<th>` (`admin.html`); `--muted` посчитан и потемнён (2,81:1 → 5,22:1), как и `--danger`, а для границы поля добавлен `--line-strong` (3,08:1 при пороге 3). **Два пункта оказались не тем, чем выглядели.** Про модалки (`role="dialog"`, `aria-modal`, ловушка и возврат фокуса) здесь было написано ошибочно: всё это живёт в `web/js/modals.js:12-126` с T0.1 — правки нет, есть тест `accessibility.cjs`, раздел 3. Про `aria-current` — требование несуществующее: ни одна ссылка шапки не ведёт на страницу, где стоит (это панель действий), поэтому атрибут был бы мёртвым кодом и сознательно не вводился. Отдельно ADR-0016 записал в «что это не закрыло» то, чего у него не было: `role="status"` подписан, а поле на него не ссылается. **Снято следующим шагом (ADR-0018, `11ac07f`):** `aria-describedby` проставлен в разметке и в шаблонах `modals.js`, радиогруппа описана через `fieldset`, а связь проверяется и статически (восьмая группа `check-frontend.mjs`), и в рантайме (текст отказа попадает в связанный элемент). Остаток того же ADR-0016 — «числа посчитаны для 13 выбранных пар, а не для каждого сочетания в CSS» — **снят ADR-0019 (`487af91`)**: список вырос до 26 пар, и шестая группа проверки разбирает `style.css` и инлайновые `style=""`, требуя, чтобы каждая заданная ими комбинация «текст + подложка» была измерена или занесена в `CONTRAST_EXEMPT` с проверяемой причиной (единственное освобождение — подпись отключённой кнопки, 1,58:1, WCAG 1.4.3); подложки состояний `:hover`/`:active`/`:focus`/`[disabled]` проверяются отдельно, потому что текст в них наследуется от базы. Значения токенов при этом не менялись: правка документированная, пиксельно ничего не сдвинулось. Не проверено: озвучка живым скринридером и вид новых состояний фокуса — браузера в работе не было. **(Вид состояний фокуса проверен и исправлен ADR-0020, `304f0cc`:** живой замер
восьми страниц — 77 элементов, 0 невидимых, найдено и заменено одно кольцо радиокнопки,
которое рисовал только `--teal-tint` при 1,10:1 к подложке панели; возврат невидимого кольца
запрещает новая группа 9 `check-frontend.mjs`. Тот же обход дополнен ADR-0022 (`86edfe9`):
пять состояний открытого диалога на `/dashboard` замеряются в нём же — 14 колец внутри окон,
ловушка проверяется живым `Tab`, а находкой стала форма, в которую фокус не входил (правка в
`web/js/modals.js`). Скринридер — по-прежнему открыто, и он требует
человека с NVDA/VoiceOver, а не машины разработки.**)** Закрепляется тремя слоями: `check-frontend.mjs` (статика, падает в CI), `tests/ui/accessibility.cjs` (DOM-поведение, 112
проверок офлайн) и `scripts/check-focus.mjs` (живой замер отрисовки — вне CI, потому что на
раннере нет браузера; прогон ручной).
- Дизайн-система: базовые классы переиспользуемы; стилевые блоки страниц идут одним файлом (сейчас 768 строк, из них ~115 добавила таблица расписания в T4.1, ~39 — доступность в T0.5, 14 — комментарии ADR-0019 о контрасте и 12 — правка кольца радиокнопки и её замер в ADR-0020), а часть строк 329-590 — постраничные one-off блоки. Пункт про «висячие токены, используемые без объявления» (`--e3`, `--bw-thick`, `--primary`) устарел и проверен заново: `--e3` объявлен в `style.css:51`, `--bw-thin` и `--bw-thick` — в `style.css:62-63`, а `--primary` после `grep -rn -- "--primary" web/` не встречается ни разу. Блок `:root` занимает строки 6-69 (сдвинулся на 4 из-за комментариев ADR-0019), в нём новые `--line-strong` (`:25`) и контрастные правки `--muted`/`--danger`; с ADR-0019 их значения защищает не только список пар, но и покрытие: любой тон, который CSS подставляет под текст (включая подложки состояний и `--btn-bg`), обязан быть в измеренных парах, иначе CI красный.

## 8. Исследование источников данных (Агент 4)

Оба внешних источника на этапе исследования **не удалось верифицировать**, и это блокировало этапы 5-6. Сейчас блок снят для расписания (см. пункт 1 ниже), для Telegram он остаётся.

1. Расписание. Фронтенд ссылается на `https://tksu.ru/bitrix/js/api-apeks-vuz/rasp-stud/rasp-stud.html` (`web/schedule.html:54`) — виджет «1С:Университет / APEKS ВУЗ» внутри Bitrix. DNS резолвится (`86.110.162.34`), но TCP-подключение с этого хоста недоступно: `curl` → «Network is unreachable» (GitHub и другие хосты при этом отвечают, то есть сеть есть, недоступен конкретный ресурс). Запросами в `rasp-stud.html` и в JS виджета проверить нельзя. Wayback: снимок главной `tksu.ru` от 2026-10-17 есть, снимков `/bitrix/js/api-apeks-vuz/*` в индексе нет; при попытке домена по CDX сервис отдал «Internet Archive services are temporarily offline». Следовательно реальный эндпоинт, параметры (группа/дата/семестр) и формат ответа **неизвестны** — придумывать структуру нельзя (прямое требование брифа, п.4 «Парсер расписания»).

   **Закрыто в T4.1.** Блок снял не доступ к сайту, а готовый парсер владельца (`schedule_parser`, Python): из него взяты эндпоинт `https://apeks.tksu.ru/api/call/schedule-schedule/student`, токен в query-параметре и реальные тела ответов, а живая фикстура месяца (`internal/apeks/testdata/apeks-2026-10-week.json`, группа Б-ИСиТ-22) легла в основу парсера и тестов. С этой машины `apeks.tksu.ru` по-прежнему не проверялся: `tksu.ru` недоступен, и запрос к нему был бы только обещанием, а не проверкой. Поэтому клиент и handlers протестированы против локального HTTPS-стаба (`httptest.NewTLSServer`, держит TLS-сертификат именно потому, что боевой путь — только HTTPS), а конец-к-концу прогонялся против него же: импорт, чтение и отрисовка страницы. Что источник отдаёт вживую сегодня — не проверено; расхождение лечится одной правкой парсера и фикстурой, а не переписыванием модуля.
   **(Дополнено ADR-0021, `63f8cb3`: боевой источник с этой машины заговорил — сняты
   каталог (587 групп) и октябрь у группы 494 (98 пар), импорт прошёл через оба движка, и
   расхождение нашлось настоящее: пустые уровни дерева групп источник отдаёт списком `[]`,
   а не словарём. Лечится ровно тем же, чем обещалось, — правкой разбора и новой
   фикстурой. Сами пары разбирает приложенный Python-парсер владельца, а не переписанный
   на Go код: `SCHEDULE_SOURCE=python` по умолчанию, Go-клиент остался запасным движком.)**
2. Telegram. `https://api.telegram.org` и `https://t.me` с этого хоста недостижимы (код 000). Канал в брифе не назван. Факты, которые надо подтвердить у владельца, собраны в документе 03.

Что можно зафиксировать как техническую основу заранее (без привязки к конкретным данным): бот Telegram получает `channel_post` только если он добавлен в администраторы канала; историю чужого публичного канала Bot API не отдаёт; для исторической загрузки легальны экспорт/архив от владельца канала. Это согласуется с п.4 брифа и не требует домыслов о доступе.

## 9. Итог этапа

Проект не «пустой скелет» и не «переписывать»: есть рабочий, собираемый, проверяемый модульный монолит с корректной моделью аутентификации (bcrypt, серверные сессии, HttpOnly-cookie, double-submit CSRF, права через `authz`) и честным разделением слоёв. Из трёх направлений работы первое закрыто целиком (UI заданий, роли, подбор пароля, таймауты, журнал), второе — за `T2.1` (PostgreSQL), а из третьего расписание сделано: источник подключён, пары импортируются и читаются со страницы (с ADR-0021 их разбирает приложенный Python-парсер, а Go-разбор — запасной движок). Остаётся модуль событий — он, как и карта, упирается в ответ B3, а не в код.
