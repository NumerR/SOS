# 05. Принятые решения (ADR)

Владелец ответил на блокирующие вопросы (Этап 1 → Этап 2). Фиксируем как согласованные контракты; менять в одностороннем порядке нельзя (бриф, п.4).

## ADR-0001. Размещение: GitHub Pages + внешний backend

Статус: принято владельцем.

Схема: `web/` публикуется на GitHub Pages; Go API и фоновые задачи — на отдельном хосте с PostgreSQL. Frontend и backend — разные origin-ы, поэтому:

1. **Все пути во фронтенде — относительные** (`./css/…`, `./js/…`, ссылки `./dashboard.html`), чтобы работало под базовым путём `https://<user>.github.io/SOS/`. Плюс `<base>` не используем, ловушка: он ломает якорные ссылки.
2. **`API_BASE_URL` — отдельный конфиг** (`web/js/config.js` со значением по умолчанию для разработки и подменой при публикации), а не хардкод в вызовах.
3. **CORS**: явный allowlist origin-ов Pages, `Access-Control-Allow-Credentials: true`, обработка `OPTIONS` (pre-flight из-за заголовка `Content-Type: application/json` и `X-CSRF-Token`). Пустой allowlist = same-origin режим, заголовков CORS нет.
4. **Cookie-модель — это главный риск схемы, и у него есть дешёвый обход.** `SameSite` считается по **site** = eTLD+1, а не по origin. Поэтому:
   - Если Pages публикуется на **собственном домене через CNAME** (например `sos.example.ru`, а API на `api.example.ru`) — это одна site-зона,существующие cookie `SameSite=Lax; HttpOnly; Secure` продолжают отправляться, CSRF-модель double-submit остаётся валидной, ничего не нужно менять в модели авторизации. **Это рекомендованный путь.**
   - Если Pages остаётся на `https://numerR.github.io/SOS/`, а API на другом регистрируемом домене — запросы становятся кросс-сайтовыми: нужен `SameSite=None; Secure`, и Safari (ITP) по умолчанию блокирует такие сторонние cookie → вход на iPhone/iPad с высокой вероятностью не работает. Придётся переходить на bearer-токен (`Authorization`), что для ванильного JS означает хранение токена в коде страницы/хранилище браузера и перенос риска с CSRF на XSS.
   
   Открытый вопрос владельцу (D-01): есть ли собственный домен для Pages. До ответа код пишем так, чтобы оба варианта переключались конфигурацией (`COOKIE_SAMESITE`, `COOKIE_DOMAIN`, `CORS_ALLOW_ORIGINS`), а фронтенд читал токен авторизации из одного места (`auth.js`), а не из десяти.

5. **Страницы, которые сегодня отдаёт Go** (`/`, `/login`, `/register`, `/dashboard`, `/schedule`, `/admin` из `cmd/server/main.go:72-77` и `internal/handlers/pages.go`), на Pages становятся обычными файлами: либо `login.html` (тогда ссылки `./login.html`), либо сохранение «красивых» URL через `404.html`-роутер на фронтенде. Решение: **используем `.html`-файлы как есть** — предсказуемо на Pages, без JS-роутера и без зависимости от настроек сервера. (Уточнение после `ADR-0011`: реализованы относительные пути без расширения — `login`, `./` — потому что их отдаёт Go-сервер, на всём текущем проверяемом; выбор «каталоги с index.html» или `404.html`-роутер перенесён в момент публикации и закрывается одной строкой в `web/js/config.js`.) Роуты `/api/*` уходят из статических путей.
6. GitHub Pages не запускает Go и не даёт PostgreSQL (бриф, п.5) — это и причина схемы; подключение к БД из браузера запрещено, всё через API.

## ADR-0002. PostgreSQL сейчас, версионируемые миграции

Статус: принято владельцем.

- Драйвер: `github.com/jackc/pgx/v5/stdlib` через `database/sql` — код store-пакетов остаётся на знакомом `sql.DB`, без ORM (бриф: без лишних абстракций).
- Собственный runner миграций (~150 строк): `migrations/NNNN_*.sql` + `up`/`down` секции, таблица `schema_migrations(version, applied_at)`, применение при старте, блокировка одновременных применений advisory lock. Внешняя `golang-migrate` не вводим.
- Типы: `bigserial`, `timestamptz` вместо unix-int, `CHECK` на `role`, `score`; ошибки уникальности по `pgerrcode.UniqueViolation` (`23505`) вместо сверки текста (`internal/store/users.go:94,251-253`).
- Локальная разработка и CI: `deploy/docker-compose.yml` (postgres 16 + приложение), в GitHub Actions — сервис-контейнер postgres; тесты миграций на чистом volume.
- SQLite полностью убираем: `SetMaxOpenConns(1)` (`internal/database/db.go:26`) не дал бы параллелить фоновые импортёры и держал бы два диалекта в одном коде.
- Существующие `CREATE TABLE IF NOT EXISTS` из `db.go:43-141` переносятся в `0001_init.sql` без изменения логики; локальная `data/app.db` не мигрируется (дево-файл, в git не попадает).

## ADR-0003. Модульность и единый формат ошибки

Статус: принято; формат ошибки реализован полностью (`fcfc6c9`, `2f68b4e`) — см. §4
`docs/02-ARCHITECTURE.md`.

- Модули: `internal/modules/<name>` со своими handlers/service/store/migrations + явный реестр (`docs/02-ARCHITECTURE.md` §2-3). Разбор `handlers.New(...)` с 9 позиционными аргументами на `Deps`-struct — первый шаг, иначе каждая новая сущность правит все вызовы.
- Права: реестр permissions + `authz.Can(user, perm)` вместо ~15 мест сравнения строки роли.
- Формат ошибки: `{"error":{"code","message","fields"}}` (коды: `invalid_json`, `validation`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `rate_limited`, `csrf_failed`, `internal`). Бэкенд, `web/js/common.js` и тесты меняются в одном PR.

Как реализовано и чем расширено:

- Конверт живёт не в `internal/handlers`, а в отдельном `internal/apierror`: тем же
  форматом обязан отвечать и транспорт (405 для неизвестного метода пишет
  `internal/platform`, минуя любой обработчик). Пока формат лежал только в
  `handlers`, этот путь и остался плоским — его закрыл `fcfc6c9`, и он же
  проверяется тестом ядра, а не наблюдательностью.
- К списку кодов добавлены два: `method_not_allowed` (405) и
  `source_unavailable` (502/503 — источник расписания). Оба появились не как
  украшение: 405 нельзя отличить от 404 по одному статусу маршрутизатора, а
  отказу источника нужен свой код, потому что страница решает по нему «показать
  кнопку повтора», а не «красную строку».
- `code` выводится из статуса одной функцией `CodeForStatus`; явно (`WriteCode`)
  задаётся только там, где статус не классифицирует неисправность:
  `invalid_json` при 400, `csrf_failed` при 403, `unauthorized` для
  «неверный текущий пароль» при том же статусе, что и у истёкшей сессии.
- `fields` — ключ из JSON запроса, подпись человеку берётся у самой формы
  (`GS.fieldLabel`), а не из словаря соответствия: словарь устарел бы на первом
  же переименовании поля.
- Тесты формата, которые раньше искали в ответе подстроку `"error"`, теперь
  разбирают конверт: подстрока оставалась истинной и для старого формата,
  поэтому именно она и пропустила немигрированный 405.

## ADR-0004. Источник расписания — контракт готов, данные не подтверждены

Владелец указал `https://tksu.ru/bitrix/js/api-apeks-vuz/rasp-stud/rasp-stud.html`. Проверено с этого хоста: DNS резолвится (`86.110.162.34`), подключение не устанавливается ни на 443, ни на 80 («Couldn't connect»/«Network is unreachable» при работающем интернете), снимков страницы и JS виджета в веб-архиве нет (`archived_snapshots: {}`).

Следовательно формат запроса к данным, параметры (группа/дата/семестр) и структура ответа **неизвестны**, и по требованию брифа (п.4: «не выдумывай структуру сайта») парсер не пишется. Что делаем вместо этого:

- Таблицы `schedule_sources`, `schedule_groups`, `schedule_entries`, `import_runs` и API `GET /api/schedule/entries?group_id=&from=&to=` — по контракту из docs/02 §5-6; они от деталей источника не зависят.
- Интерфейс `ScheduleSource { FetchGroups(ctx) ; FetchEntries(ctx, groupKey, from, to) }` и регистрация источника по имени; конкретный адаптер `tksu` остаётся незакрытым с явной отметкой «ожидает подтверждения источника» (критерий готовности MVP, бриф п.8 это допускает).
- UI показывает: нет данных + причину + `last_success_at` из `schedule_sources`.
- Чтобы завершить адаптер, нужен один из трёх артефактов: (1) URL XHR-запроса из DevTools → Network и сырой ответ для одной группы, (2) официальный API университета, (3) сохранённая HTML-страница результата, открытая с сети, где tksu.ru доступен. Также фиксируем: страница-виджет `rasp-stud.html` сама по себе данные не отдаёт — она только загружает JS, который обращается к API «1С:Университет / APEKS»; парсить её HTML бессмысленно.

## ADR-0005. События: только ручное добавление, источник — интерфейсом

Владелец выбрал ручное добавление (Telegram-канал не назван, Bot API с этого хоста недоступен). Поэтому:

- Работает CRUD событий преподавателем/админом; схема расширяется полями `location_text`, `lat/lon (NULL)`, `geo_state`, `category`, `image_url`, `source_url`, `starts_at`, `ends_at`, `published_at`.
- Дедупликация на `UNIQUE(source_id, external_id)` закладывается сразу (для ручных записей `source_id = NULL`, `external_id` не обязателен) — чтобы будущий импорт не требовал изменения схемы.
- Модуль источника `EventSource` остаётся без реализации; в UI и README явно: «источник Telegram не подключён».
- Фиктивных координат и вымышленных мест не заводим (бриф, п.3): без координат событие не попадает на карту.

## ADR-0006. Роли назначает администратор; перебор гасится токен-бакетом в памяти

**Контекст.** Публичная регистрация принимала `role: "teacher"`, то есть любой
посетитель получал права создавать курсы, задания и оценивать чужие работы.
Ограничения частоты запросов не было ни на одном эндпоинте.

**Решение.**

- Регистрация выдаёт только `student`. Роль меняет администратор через
  `POST /api/admin/users/role` (`RequireRole("admin")` + `RequireCSRF`), интерфейс —
  на `/admin`. (С T1.1, ADR-0010: `RequireRole` удалён, маршрут декларирует право
  `user.role.manage`.) Собственную роль менять запрещено (409): иначе админ может
  отрезать себе доступ посреди сеанса.
- Смена роли отзывает все сессии пользователя (`DeleteAllForUser`), иначе
  повышенные или отозванные права живут до истечения куки (24 часа).
- Ограничение частоты — токен-бакет (`internal/ratelimit`), три набора: вход по IP
  (20/10 мин), неудачные проверки пароля по аккаунту (5/15 мин), регистрация по IP
  (10/час). Ответ `429` + `Retry-After`. Неудачная попытка отвечает `401`, а `429`
  появляется со следующего запроса — интерфейс «вы заблокированы» не подтверждает,
  что аккаунт существует.
- bcrypt выполняется и для неизвестного логина (фиктивный хэш) — ответ не различается
  по таймингу.

**Последствия и ограничения.**

- Бакеты живут в памяти процесса: за двумя инстансами лимит удваивается, после
  рестарта обнуляется. Для одного приложения это приемлемо; при переходе на
  несколько инстансов нужен общий счётчик (Redis) — зафиксировано в docs/03.
- Ключ — адрес TCP-соединения, если не включён `TRUST_PROXY` (см. ADR-0007).
  За реверс-прокси без этого флага все клиенты делят один бакет — поэтому флаг
  завязан на публикацию наружу, а не включён «на всякий случай».
- Тесты UI и сид теперь требуют админ-сида (`ADMIN_USERNAME`/`ADMIN_PASSWORD`):
  преподаватель больше не появляется «сам из регистрации».
- Блокировка постепенная, а не жёсткая: после исчерпания бакета следующее
  разрешение выдаётся через `window/capacity`, то есть через 3 минуты будет
  доступна одна попытка. Это осознанный выбор в пользу отсутствия фонового
  очистителя и состояния «разблокировать».

## ADR-0007. Остаток T0.2: сборщик сессий, «выйти везде», смена пароля, доверие прокси

**Контекст.** ADR-0006 оставил четыре незакрытых пункта: протухшие строки в
`sessions`, отсутствие отзыва всех сессий пользователем, отсутствие смены пароля
и ключ лимитера, нераспознающий клиента за прокси.

**Решение.**

1. **Очистка — фоновый тикер в процессе, а не отдельный cron.** `cleanSessions`
   в `cmd/server/main.go` делает первый проход сразу при старте (забирает мусор
   между перезапусками) и далее ходит раз в час. Один проход ограничен
   `context.WithTimeout(30s)`; ошибка чистки пишется в лог и не роняет сервер.
2. **«Выйти везде» (`POST /api/auth/logout-all`) снимает и текущую сессию.**
   Кнопка в интерфейсе — это сценарий компрометации, «остаться здесь, выгнать
   остальных» в нём не ожидается. Требует `RequireAuth` + `RequireCSRF`, снимает
   обе куки (`gs_session`, `csrf_token`) и уводит клиента на `/login?revoked=1`.
3. **Смена пароля требует текущий пароль и сохраняет текущую сессию.**
   `POST /api/auth/change-password`: проверка текущего пароля через bcrypt,
   затем `DeleteAllForUserExcept(текущая)`. Отзыв всех сессий кроме текущей —
   сознательный выбор: пользователя не выбрасывает из вкладки, где он только что
   ввёл новый пароль, при этом чужие устройства выходят. Ответ содержит
   `revoked_sessions`, чтобы это было видно человеку. Ограничение — 6 запросов
   на IP за 15 минут: текущий пароль внутри открытой сессии тоже перебирают.
   Новую сессию при смене не заводим: если куки нет, отзываем вообще всё.
4. **`X-Forwarded-For` и `X-Forwarded-Proto` доверяем только при `TRUST_PROXY=true`.**
   `ClientIP` берёт первый валидный IP из `X-Forwarded-For`, иначе — адрес
   соединения; `isSecureRequest` читает `X-Forwarded-Proto` только под тем же
   флагом. Без флага поведение консервативное (лимитер по IP прокси, `Secure`
   только при реальном TLS); с флагом — корректное, но требующее закрытого
   прямого доступа к порту. Один флаг на оба заголовка: их нельзя доверять
   по отдельности.

**Последствия и ограничения.**

- Доверие адресов из `X-Forwarded-For` по-прежнему без списка доверенных
  прокси-хостов: флаг «врубили — закрыли порт», а не «разобрали цепочку».
  Полный разбор (списки CIDR, подсчёт глубины) остаётся заделом на публикацию.
- Верхняя граница длины пароля (`maxPasswordLength` = 200) введена, потому что
  bcrypt читает только первые 72 байта, а длинное тело — бесплатный способ
  замедлить обработчик.
- Смена пароля не пишет запись в `audit_events` (таблицы нет) — только
  структурированный лог (`slog`, ADR-0008). Аудит входит в T1.2 — и закрыт там
  же (`26066e8`, ADR-0012): теперь смена пароля пишет и событие, и строку лога.
- `LogoutAll` и `ChangePassword` не отзывают токены мгновенно на стороне
  клиента: вкладка на другом устройстве узнает об этом при следующем запросе,
  что для cookie-сессий и есть механизм отзыва.

## ADR-0008. T0.3: сервер с таймаутами, корректной остановкой, структурированным логом и границами полей

**Контекст.** До этого коммита `ListenAndServe` шёл без единого таймаута, база
вызывалась без дедлайна, логи были `log.Printf` без корреляции между записями,
а текстовые поля заданий/сдач/оценок не имели верхней границы. Это не «гигиена
ради гигиены»: каждый пункт — отдельная отказоустойчивость (Slowloris, висячий
запрос к базе, нечитаемый лог, мегабайтный `title`).

**Решение.**

1. **Таймауты на `http.Server`.** `ReadHeaderTimeout` 5 с, `ReadTimeout` 10 с,
   `WriteTimeout` 30 с, `IdleTimeout` 90 с, `MaxHeaderBytes` 64 КиБ. Заголовок
   ограничен отдельно от тела, потому что режет его именно заголовок: тело и так
   упирается в `MaxBytesReader` (1 МиБ) внутри `readJSON`.
2. **Остановка по сигналу, а не `os.Exit`.** `signal.NotifyContext(SIGINT,
   SIGTERM)` → `server.Shutdown(10s)`. Если за 10 секунд запросы не дошли —
   `server.Close()` принудительно: висящий процесс хуже оборванного запроса.
   Фоновый сборщик сессий останавливается тем же контекстом и дожидается до
   `db.Close()` (иначе горутина пишет в закрытую базу).
3. **Дедлайн на базе — middleware, а не обёртка вокруг каждого вызова.**
   `WithDBDeadline` ставит `context.WithTimeout(r.Context(), 5s)` на весь
   запрос; обработчики уже передавали `r.Context()` в хранилище, поэтому
   ограничены оказываются все обращения сразу, и пропустить одно структурно
   нельзя. Вариант «обернуть каждый вызов сам» дал бы сотни строк шаблонного
   кода и гарантированно забытый адрес.
4. **`slog` JSON + request id.** `LogRequests` выдаёт идентификатор (8 байт
   `crypto/rand`), кладёт его в контекст, в `X-Request-Id` ответа и в каждую
   строку лога. Чужой `X-Request-Id` принимается только под `TRUST_PROXY`,
   и то не длиннее 64 символов и без управляющих символов — иначе это
   лог-инъекция и способ подделать корреляцию. Тело запроса и ответа в лог не
   пишется: там пароли и содержимое сдач. Уровень по умолчанию `info`,
   `LOG_LEVEL=debug` включает статику.
5. **`__Host-` на сессионную куку при HTTPS.** Имя `__Host-gs_session`
   выпускается, когда запрос защищён (`r.TLS` или доверенный
   `X-Forwarded-Proto`); на локальном HTTP остаётся `gs_session`, потому что
   браузер выбросил бы `__Host-` без `Secure`. Чтение пробует оба имени,
   снимание — всегда оба. CSRF-кука префикса не получила: её читает JS по
   имени `csrf_token`, и double-submit без HTTPS всё равно не сильнее обычной
   куки.
6. **Границы текстовых полей общие для всех mutate-эндпоинтов.** Заголовки —
   200 символов, описания и комментарии — 2000, категория — 64, URL — 2000,
   текст сдачи — 20 000. Считаются символы (`utf8`), а не байты: иначе русская
   сдача на 2000 символов (4000 байт) была бы «слишком длинной». Оценка
   ограничена шкалой 0–10 — ровно той, что задана полем ввода в `modals.js`.
   Курсы, ресурсы и события переехали на общий `validateLength` с сохранением
   прежних текстов ошибок (это покрыто тестом).

**Последствия и ограничения.**

- Проверено живьём (собранный бинарник, изолированная `DB_PATH`): соединение с
  недописанными заголовками закрыто без единого байта ответа через 5.01 с при
  `ReadHeaderTimeout` 5 с; `POST` с телом 20 КБ из заявленных 900 КБ, начатый до
  `SIGTERM`, получил `400 Bad Request` через 10.001 с (сработал `ReadTimeout`,
  сервер за это время не бросил активные соединения) и процесс завершился с
  кодом 0 и строкой `сервер остановлен корректно`; `/api/health` отдаёт
  `{"status":"ok","db":"ok"}` и `503 {"status":"error","db":"error"}`, если база
  не ответила за секунду; при `TRUST_PROXY=true` и `X-Forwarded-Proto: https`
  `Set-Cookie` уходит под `__Host-gs_session; Secure`, без заголовка —
  обычный `gs_session`; `title` из 201 символа даёт `422 {"error":"title is too long"}`,
  из 200 — `201` (граница inclusive, счёт в рунах: проверено на кириллице).
  Замер сделан до `ADR-0003`: граница и статус те же, а форма этого отказа теперь
  `422 {"error":{"code":"validation","message":"title is too long","fields":{…}}}`.
- `WriteTimeout` 30 с отключает долгие стриминговые ответы. Сейчас их нет;
  если появится выгрузка отчётов — для неё нужен отдельный обработчик со своим
  таймаутом, а не общий.
- Дедлайн в 5 с на запрос — это и лимит на «тяжёлые» future-выборки (лента по
  всем курсам). При переходе на PostgreSQL (T2.1) значения стоит пересмотреть
  по реальным замерам, а не по вкусу.
- Логи идут в stdout: файл-ротацию и сборщик делает платформа, а не приложение.
- Request id коррелирует строки одного запроса, но не связывает их с записями
  в базе: для этого нужен `audit_events` (T1.2). Уточнение после `ADR-0012`:
  журнал добавлен, но колонки `request_id` в нём нет — запись связывается с
  автором, действием и временем, а точная привязка «эта строка базы = этот
  запрос» не сделана намеренно (в журнале нет запросов, которые не
  дошли до обработчика, и дублировать идентификатор ради отладки — значит
  хранить ещё одно поле, которое никто не читает).

## ADR-0009. T0.4: CI из трёх работ, проверка целостности фронтенда без сборки

**Контекст.** Класс багов T0.1 (`web/js/modals.js` лежал на диске, был
синтаксически валидным, но ни одна страница его не подключала, а `dashboard.js`
вызывал `ModalManager` → `ReferenceError`) не ловится ни `go test`, ни
`node --check`: файл целый, просто никем не ссылается. В репозитории не было ни
одного workflow — `.github/` отсутствовал.

**Решение.**

1. **Три работы вместо одной.** `go` (gofmt, `go vet`, `go build`,
   `go test -race -count=1`), `frontend` (`node --check` по каждому
   `web/js/*.js` + `scripts/check-frontend.mjs`), `ui` (jsdom-тесты против
   живого сервера). `ui` нуждается в первых двух: гонять полный прогон сервера
   ради теста, который падает на формате или синтаксисе, — способ получить
   красный CI без понимания причины.
2. **Целостность фронтенда проверяется по четырём признакам, а не «на глаз»:**
   каждый `<script src>` и `<link href>` указывает на существующий файл; каждый
   JS-файл в `web/js/` подключён хотя бы одной страницей (это и есть детектор
   бага T0.1); каждая `getElementById`-мишень объявлена на той странице, где
   запускается скрипт — в HTML или в разметке, которую скрипт сам вставляет;
   в HTML нет инлайновых `on*`-обработчиков.
3. **История прогона — в `npm ci`, значит lockfile в репозитории.**
   `tests/ui/package-lock.json` закоммичен: без него `npm ci` падает, а `npm
   install` каждый прогон тянет свежие версии jsdom, и UI-тесты начинают
   валиться по причинам, не связанным с кодом проекта.
4. **Пароль сида в workflow — не секрет.** `ADMIN_USERNAME`/`ADMIN_PASSWORD`
   в `env` работы `ui` питают одноразовую SQLite-базу внутри раннера, которая
   умирает вместе с ним; они не дают доступ ни к чему живому. Настоящие
   учётные данные (будущий `DATABASE_URL` прод-базы, `TELEGRAM_BOT_TOKEN`)
   по-прежнему только в GitHub Secrets и в логи не выводятся.
5. **Триггеры: `pull_request` + push в `main` + ручной запуск.** Push в
   feature-ветку CI не гоняет: для открытого PR это удвоило бы прогоны на тот же
   коммит. Проверки всё равно видны до слияния — на PR.
6. **PostgreSQL-часть приёмки T0.4 перенесена, а не сделана наполовину.**
   Сервис-контейнер `postgres` и dry-run миграций появляются вместе с T2.1:
   сейчас схема применяется кодом (`internal/database/db.go`), отдельного
   SQL-пакета нет, поэтому «прогон миграций на чистой БД» в CI сегодня означал бы
   проверку несуществующего файла.

**Последствия и ограничения.**

- Проверено локальным прогоном тех же команд на чистой копии репозитория: gofmt
  пусто, `go vet`, `go build`, `go test -race -count=1 ./...` зелёные; `node
  --check` по всем 8 файлам; `check-frontend.mjs` — 6 страниц, 8 файлов, ок;
  сервер + `tests/ui/seed.sh` + `npm ci` + `npm run test:all` → 20/20, 11/11,
  22/22. Детектор бага T0.1 проверен на намеренно сломанных копиях: удаление
  строки `<script src="/js/modals.js">` → `FAIL modals.js не подключён ни к
  одной странице`; удаление файла → `FAIL подключён несуществующий скрипт`;
  инлайновый `onclick` и фантомный `getElementById` → тоже FAIL.
  Версии `actions/checkout@v4`, `actions/setup-go@v5`, `actions/setup-node@v4`
  зафиксированы явными тегами.
- Что нельзя проверить локально: сам GitHub-раннер (версии образов, поведение
  `actions/*`). Первый прогон закрыл и это: run 40037668304 на коммите `d4a2141`
  (`pull_request`) — `completed / success`, три работы зелёные, UI-шаги (build,
  `npm ci`, запуск сервера, `seed.sh`, `test:all`) прошли на `ubuntu-latest`.
- `check-frontend.mjs` не исполняет JS: он проверяет связи. Поведение страниц
  по-прежнему закрывают jsdom-тесты, а не этот шаг.
- `go test -race` на macOS/Linux требует gcc для раннего этапа — на
  `ubuntu-latest` он предустановлен; если CI переедет на контейнер без gcc,
  флаг придётся убрать или добавить `apt-get install`.

## ADR-0010. T1.1: реестр модулей и права вместо ролей

**Статус:** принята, реализована в `439a08b` (ветка `fix/t0-frontend-modals`, PR #2).

**Контекст.** К Этапу 3 доступ решался сравнением строки роли: `hasRole([]string{"teacher", "admin"}, user.Role)`
в ~15 местах обработчиков, `RequireRole("admin")` в `main.go`, switch по ролям в
`store/schedule.go`, отдельно — список ролей в админке и ещё один в `normalizeRole`.
Каждый новый маршрут означал «не забыть проверить роль внутри», и забыть было
чем: `if user.Role == "admin"` внутри обработчика владельца строки — это та же
проверка, что и в роутере, только без единого места, где её видно. Плюс маршрутов
стало 25, и они описывались 103 строками в `main.go`.

**Решение.**

1. **Право, а не роль.** `internal/authz` держит таблицу `Spec{Name, Description, Roles}`;
   обработчик и маршрут говорят про `course.create`, `submission.grade`,
   `event.source.manage`. `Can(роль, право)` — единственная функция проверки;
   `RequireRole` и `hasRole` удалены, вместо них `RequirePerm(право, текст отказа, next)`,
   который внутри вызывает `RequireAuth`.
2. **Обход владения — отдельное право.** «Админ может оценить чужую работу»
   записано как `submission.grade.any`, а не как `if role == admin` в обработчике:
   в матрице видно, что такое право существует и у кого оно есть. Единственное
   право, которого у администратора нет — `schedule.scope.created`: ему
   соответствует `schedule.scope.all`.
3. **Deny-by-default для неизвестного права.** `Can` возвращает `false` для права,
   которого нет в реестре; `ValidPermission` вызывается при добавлении маршрута,
   поэтому опечатка в константе валит сборку маршрутизатора, а не превращается в
   «разрешить всем» или в тихой 403 «модуль сломался».
4. **Маршрут описывает допуск.** `platform.Route{Path, Method, Handler, Perm,
   DenyMessage, Public, CSRF}` — одно объявление на метод. Список методов вместо
   одного был бы удобнее на бумаге и вреден в деле: у `GET /api/courses` и
   `POST /api/courses` разные права и только у POST нужен CSRF.
5. **Валидация при старте, а не при запросе.** `Registry.Add` копит проблемы,
   `Mount` возвращает ошибку, `main.go` на ней не стартует: пустой путь, путь без
   «/», метод с пробелами, nil обработчик, `Public`+`Perm`, неизвестное право,
   дубль (путь, метод), недостающая обёртка middleware.
6. **Миграции модуля — общий runner.** Таблица `platform_module_migrations
   (module, version, applied_at)`, PK(`module`,`version`), одна транзакция на
   миграцию, откат при ошибке, skip-if-applied. Версию нельзя переиспользовать,
   имя модуля уникально.
7. **Формат ответа не менялся.** Переезд на реестр не трогает §4 docs/02:
   тексты отказов перенесены в `DenyMessage`, `{"error": "…"}` остаётся, чтобы
   смена формата и смена каркаса не оказались одним незапускаемым изменением.
   Дальше так и вышло: формат изменён отдельно — `fcfc6c9` + `2f68b4e` (`ADR-0003`),
   и `DenyMessage` из этого пункта переехал в конверт без смены текста.

**Что осталось в коде.** `internal/handlers/*` и `internal/store/*` — общие
пакеты, у модулей пока только объявления маршрутов (`Migrations()` у всех шести
возвращает `nil`, core-схему создаёт `internal/database/db.go`); распад по
модулям и переезд схемы на версионные миграции — `T2.1`. Страницы и статика
сознательно вне `Registry` (отказ там — редирект 302, не JSON).

**Проверено.** `gofmt -l` пусто, `go vet` чисто, `go test -race -count=1 ./...`
зелёное (59 тестов + 32 подтеста). `internal/authz/authz_test.go` сверяет матрицу
в обе стороны и требует, чтобы `Permissions()` был отсортирован;
`internal/platform/platform_test.go` — диспетчер по методам, 405, catch-all,
7 случаев валидации реестра, прогоны миграций с откатом;
`cmd/server/modules_test.go` — 14 проверок на настоящем `moduleList()` +
настоящих обработчиках + SQLite: аноним 401, студент 403 с текстом, преподаватель
201, чужой преподаватель 403, админ 201 через `*.any`, PUT 405, неизвестный путь
404, CSRF 403→201. Мутация (`Perm: authz.CourseCreate` убран) — тест падает на
`student POST /api/courses: 201`, возврат — зелёный. Live curl и UI-сьюты
20/20 · 11/11 · 22/22. [run 40041370917](https://github.com/NumerR/SOS/actions/runs/40041370917) —
`completed / success`. Развёртывания не было ни у одного коммита.

**Ограничения, которые надо знать.** Runner миграций сейчас использует SQLite
(`?`, `strftime('%s','now')`) — диалект и тип даты меняются в `T2.1`, это
заранее документировано в `internal/platform/migrations.go` и в
docs/how-to-add-a-module.md. `Registry.Routes()` даёт права только для логов и
документации — решение принимает `RequirePerm`, второго источника истины нет.

## ADR-0011. T3.1 (первая половина): один транспорт, политика 401 в клиенте, относительные пути страниц

Статус: принято агентом 3, подтверждено прогоном. Коммит `8fef933`.

**Контекст.** К моменту T1.1 фронтенд делал запросы к API из 24 мест, и каждое
место само решало, что такое 401: часть показывала текст ошибки в блоке, где
крутился spinner (пользователь оставался на странице без доступа), часть
редиректила сама. Словарь подписей ролей был скопирован трижды, пять функций дат
— переписаны в `schedule.js` заново и расходились формулировками с дашбордом.
Пути в HTML и в JS были абсолютными (`/login`, `/js/common.js`), что ломается под
базовым путём GitHub Pages (`ADR-0001`, пункт 1), а `GS` висел `const` на верхнем
уровне — в global lexical-области, поэтому дополнить его из другого файла было
невозможно.

**Решение.**

1. **Один выход в сеть.** `web/js/core/api-client.js`: базовый URL, `credentials`
   (`same-origin` против `include` для кросс-origin), CSRF-заголовок для
   небезопасных методов, `AbortController` по `REQUEST_TIMEOUT_MS`, ошибка одной
   формы (`status` / `code` / `message` / `fields` / `retryAfter` / `data`). Прямой `fetch(` во всём
   фронтенде остаётся ровно один — внутри клиента.
2. **Политика 401 по умолчанию — «уйти на вход», а не «показать текст».** Это
   дефолт клиента; там, где 401 является штатным ответом формы (вход с неверным
   паролем, смена пароля с неверным текущим) или где страница работает в гостевом
   режиме (`/api/schedule`, `/api/resources`, probe на лендинге), вызов явно
   передаёт `on401: "throw"` — таких мест 7. Дефолт выбран потому, что забыть
   редирект легче и дороже по последствиям, чем написать его руками.
3. **Текст сервера важнее нашей формулировки.** `describe()` сначала отдаёт то, что
   сказал сервер (`error.message` из конверта), и только при пустом ответе подставляет русскую
   строку по статусу. Иначе сломались бы переводы в `account.js` и утверждения
   сьютов (`/неверн/i`). Исключение — 429: там всегда наш текст с секундами из
   `Retry-After`, потому что серверная строка «too many requests» без срока
   бесполезна. Разбор плоского `{"error": "строка"}` в клиенте оставлен: так
   отвечают прокси и сервер более старой сборки, и «404 page not found» от прокси
   пользователь должен увидеть текстом, а не пустой строкой.
4. **Защита от петли редиректов проверяется по имени страницы, а не по хвосту
   пути**: `pageName("/SOS/login") === pageName("login")`. `endsWith` ловил бы и
   `/relogin`, а сравнение целиком ломается о подкаталог Pages.
5. **Общее отображение данных — в `web/js/core/format.js`** (подписи и чипы
   ролей, `GS.can` — наборы «кому показывать кнопку», даты, инициалы). Страницы
   не знают, где лежит словарь: `common.js` переэкспортирует короткими именами.
   Отсутствие core-скрипта — `console.error` при старте, а не тихий `undefined`
   в подписи: это тот же класс поломки (неподключённый файл), который ловит
   `scripts/check-frontend.mjs`.
6. **`GS` — свойство `window`, единственный второй глобалка — `SOS_CONFIG`.**
   Порядок подключения фиксирован: `config.js` → `core/api-client.js` →
   `core/format.js` → `common.js` → скрипт страницы; проверяется тем же
   `check-frontend.mjs` (файл без подключения = находка).
7. **Пути страниц относительные и лежат в `SOS_CONFIG`** (`"login"`, `"dashboard"`,
   `"./"`, `"login?revoked=1"`), навигация — только через `GS.api.navigate()`.
   Хук `SOS_CONFIG.navigateTo` существует ради проверок: в jsdom переход между
   документами не реализован, и без хука «уводит ли на вход» наблюдалось бы только
   как предупреждение раннера.
8. **`on401` не отменяет редирект сервера**: страницы без сессии по-прежнему
   закрывает бэкенд (302 на `/login`), клиент закрывает случай «сессия истекла,
   пока страница уже открыта» — до этого он и был дырой.

**Что осталось от `ADR-0001` и как это связанно с путями.** Пункт 5 ADR-0001
предполагал `.html`-файлы как есть (`./login.html`). Сейчас реализованы
«красивые» относительные пути (`login`, `./`), потому что их отдаёт Go-сервер,
на котором всё проверяется. При публикации на Pages это требует одного из
(workflow `deploy-frontend.yml` — отложена): раздавать страницы каталогами
(`login/index.html`, `dashboard/index.html` — Pages отдаёт index без расширения)
или добавить `404.html`-роутер. Расширение решается в момент публикации, конфиг
`SOS_CONFIG` для этого и существует: менять строки по шести файлам вместо одной.

**Проверено.** Числа измерены, а не заявлены: 24 вызова API через `GS.fetchJSON`
и 0 прямых `fetch(` вне клиента (`grep`), 7 мест с `on401: "throw"`, одно
вхождение `student: "студент"` (было три), 56/252/130/114 строк в
`config.js`/`api-client.js`/`format.js`/`common.js`. Новый сьют
`tests/ui/session-expiry.cjs` (187 строк, 14 проверок) отзывает сессию настоящим
`POST /api/auth/logout` и требует: навигация ровно одна и только на вход, на
`/login` и в гостевом расписании — ноль, `dashboard` из `/login` разрешается в
`/dashboard`. Прогон локально: 20/20 · 11/11 · 21/21 · 14/14 = 66 проверок,
`node --check` по 11 файлам `web/js/**/*.js`, `check-frontend.mjs` — 6 страниц и
11 подключённых скриптов, `go test -race -count=1 ./...` — всё ok. CI
[run 40044462737](https://github.com/NumerR/SOS/actions/runs/40044462737) —
`completed / success`, включая работу `UI против живого сервера`. Развёртывания не
было ни у одного коммита.

**Ограничения, которые надо знать.** Вариант B (внешний API + CORS) кодом
поддержан, но не запускался: сервера с другим origin нет; относительные пути
проверены разрешением и смоуком на Go-сервере, а не на боевом Pages. Лимит
входов (20 на IP за 10 минут, `ADR-0006`) теперь ограничивает и тесты: полный
`npm run test:all` — 17 входов по логу сервера (16×200 + 1×401), повторный прогон «поверх» предыдущего
упирается в 429; `account-security.cjs` из-за этого умеет возвращать seed-ный
пароль и в ветке сбоя. `error.code` клиент читал, а сервер его не отдавал —
этот пробел закрыт `ADR-0003` (`fcfc6c9`), см. §4 docs/02.

## ADR-0012. T1.2: журнал действий в базе рядом с логом, а не вместо него

Статус: принята агентом 2 (совместно с агентом 3 по UI), подтверждено прогоном. Коммит `26066e8`.

**Контекст.** С `ADR-0008` в проекте был структурированный лог (`slog` +
`request_id`), и он закрывал другую задачу: «что произошло с этим запросом».
Вопрос «кто входил под этим логином вчера вечером» по логу не задаётся — он
пишется в stdout и живёт ровно столько, сколько процесс, не фильтруется по
автору и из интерфейса администратору недоступен вовсе. Отчёт 01 (§6) ставил
`audit_events` в список сущностей брифа, которых в проекте нет; `ADR-0007` и
`ADR-0008` переносили запись в `T1.2`, `ADR-0010` оставил под новое право место
в реестре, а `docs/02` §6 держал строку схемы. То есть требование было
зафиксировано как известная пустота, а не как сделанное.

**Решение.**

1. **Два канала, два читателя.** Строка лога остаётся (в ней `request_id`,
   длительность, метаданные запроса — это читает тот, кто разворачивает и
   отлаживает), а в `audit_events` пишется то, что спрашивает администратор:
   автор, действие, объект, итог, ip. Дублирование покрывается разными
   требованиями к данным, а не ленью: лог нельзя сделать запросом, а базу
   нельзя сделать потоком.
2. **Таблица принадлежит модулю.** `internal/modules/audit` объявляет миграцию
   `2026-10-24_audit_events` и маршрут `GET /api/admin/audit`; ядро не
   правилось. SQL DDL живёт в `internal/store/audit.go` и оттуда же исполняется
   в тестах — это размен осознанный: держи мы DDL в пакете модуля, `store` и
   `handlers` импортировали бы пакет, который импортирует их, то есть цикл.
3. **Автор может быть неизвестен — и это нормальная строка.** `actor_user_id`
   Nullable, `ON DELETE SET NULL`. Неизвестный идентификатор (подбор пароля по
   логину, которого в базе нет) не имеет автора по определению, а удалённая учётка
   не должна стирать историю своих действий. UI показывает такую строку как
   «не установлен», а не скрывает её.
4. **Итог — флаг `ok`, а не отдельное имя действия.** `auth.login` + `ok=false`
   вместо `auth.login_failed`: фильтр остаётся по действию, причина живёт в
   `detail`, и список допустимых действий не удваивается. Реестр имён
   (`ValidAuditAction`) рядом с DDL, поэтому опечатка видна при записи, а
   неизвестный фильтр в чтении отдаёт 422 со списком правильных имён.
5. **Список «чего не бывает в журнале» — инвариант с тестом.** Пароли,
   bcrypt-хеши, id и токены сессий, CSRF-токены, текст комментария к оценке не
   пишутся ни при каком исходе. Формулировка в коде ничего не стоит, поэтому
   стоит тест: он проходит по всем строкам таблицы и ищет каждую подстроку.
   Пишется при этом идентификатор, по которому подбирали пароль, — это ответ на
   «по кому именно били», и он не даёт входа.
6. **Сбой журнала не имеет права становиться 500.** `recordAudit` — побочный
   эффект: ошибка INSERT уходит в лог `warn`-ом, ответ запроса не меняется.
   Проверено мутацией: после `DROP TABLE audit_events` вход остаётся 200.
   Выбор в пользу доступности входа, а не гарантии каждой записи.
7. **Страница без общего счётчика.** `GET /api/admin/audit` отдаёт список и
   ничего больше: `COUNT(*)` по журнальной таблице на каждом запросе — цена, которой
   нет, а «есть ли ещё» выводится из `len == limit`. `ORDER BY at DESC, id DESC`
   с тай-брейком по `id` обязателен: при секундном разрешении два события одного
   такта реальны, и без него пагинация дублировала бы или теряла строку.
8. **Что не пишется.** Отказы 403 и ошибки валидации 422: это шум проверки
   формата, а не события. Ответ на «кого не пустили» следует из права
   `audit.view`, а не из журнала.
9. **Срок хранения — не решение разработчика.** Журнал содержит идентификаторы,
   ip и user agent, то есть персональные данные; «сколько хранить и кто чистит»
   ушло владельцу (`docs/03` §3) вместо молчаливого выбора «вечно» или «30 дней».

**Проверено.** `gofmt -l` пусто, `go vet ./...` чисто,
`go test -race -count=1 ./...` — всё ok (83 теста верхнего уровня в 6 пакетах,
было 59). 24 новых теста: `internal/store/audit_test.go` 8 — первые store-тесты
в репозитории, `internal/handlers/audit_test.go` 12 — по тесту на точку записи
плюс «сбой записи не меняет ответ» и «в журнале нет секретов»,
`cmd/server/audit_test.go` 4 — доступ, цепочка оценки, фильтры и потолок
`limit`, «маршрут объявлен модулем». Живой сервер после `tests/ui/seed.sh` и
четырёх jsdom-сьютов: 29 строк журнала, все семь действий, 2 строки без автора.
UI-сьюты 20/20 · 24/24 · 21/21 · 14/14 = 79 проверок, `check-frontend.mjs` — 6
страниц и 11 скриптов. CI [run 40047906544](https://github.com/NumerR/SOS/actions/runs/40047906544)
— `completed / success` (`Go` 10/10 шагов, `Фронтенд без сборки` 8/8, `UI против
живого сервера` 14/15, последний шаг служебный). Развёртывания не было ни у
одного коммита.

**Ограничения, которые надо знать.** Диалект — SQLite (`INTEGER PRIMARY KEY
AUTOINCREMENT`, unix-секунды в `at`); переезд на `bigserial`/`timestamptz` —
`T2.1`, как и у остальных таблиц. Панель администратора проверена jsdom против
Go-сервера: на Pages (`ADR-0001`, вариант B) она ещё не открывалась. В UI нет
ни пагинации, ни фильтров — API их отдаёт, страница показывает первые 50.
`ip` пишется через `ClientIP` и потому совпадает с реальным адресом клиента
только при `TRUST_PROXY=true` за доверенным прокси (`ADR-0007`); на локальном
прогоне это `127.0.0.1`.

## ADR-0013. T3.1 (вторая половина): общая шапка в JS, страница 404 и один обработчик отправки

Статус: принята агентом 3 (фронтенд) совместно с агентом 1 (архитектура). Реализовано в `8b3a027`, прогон CI — в таблице прогонов `docs/04`.

**Контекст.** К началу этой работы в проекте было три долгих хвоста, и все три —
про копии. Первый: шапка и подвал были переписаны в шесть HTML-страниц вручную
(в HEAD это 184 строки: от 16 на входе и 16 на регистрации до 49 в кабинете), и
общее в них — рамка, бренд, логотип и кнопки выхода, различаются только три-четыре
ссылки. Правка навигации означала шесть правок, а пропущенная одна не ломала
страницу, а тихо расходила её с остальными: так и появилось расхождение, которое
мы словили в подвале `/admin` (см. ограничения). Второй: `web/js/schedule.js`
содержал два дословно одинаковых `submit`-обработчика (ресурс и событие),
отличавшихся адресом, текстами и списком для перезагрузки. Третий: на неизвестном
адресе сервер отдавал `404 page not found` — текстом, без стилей и ссылок;
страница 404 стоит в списке остатка T3.1 (`docs/04`, «Add `profile.html` … and
page 404»), в отчёте 01 она помечена как «нет» со ссылкой на `pages.go:11`, а
`docs/03` увязывает её выбор с B1 (вариант A — отдаёт Go, вариант B — Pages).
Класс багов, который это всё оплачивает, в проекте уже был: T0.1 — файл
`modals.js` существовал на диске, но не был подключён ни к одной странице, и
`dashboard.js` падал на `ReferenceError`; `ADR-0009` прямо фиксирует, что
`check-frontend.mjs` не исполняет JS, а проверяет только связи.

**Решение.**

1. **Шапку и подвал рисует `web/js/core/layout.js`, а не копипаста.** Страница
   объявляет вариант атрибутами `<body>`: `data-layout` (ключ навигации),
   `data-brand-sub`, `data-footer-note`, `data-footer-stack`; в теле остаются
   пустые `<header class="site-header">` и `<footer class="site-footer">`.
   Таблица `PAGES` (шесть ключей: index, login, register, schedule, dashboard,
   admin) живёт в одном файле — ссылка, подпись, иконка, `id`, скрыта ли.
2. **Идентификаторы не переименованы.** `#logoutBtn`, `#adminLink`, `#loginLink`,
   `#userAvatar`, `#userName`, `#userRole` остались теми же: к ним обращаются
   `common.js`, скрипты страниц и четыре jsdom-сьюта. Переименование стоило бы
   «красше» и сломало бы интерфейс — это контракт, а не деталь реализации.
3. **Отрисовка — сразу при загрузке скрипта, не на `DOMContentLoaded`.**
   `layout.js` подключён в конце `<body>` выше страничных скриптов, поэтому
   `common.js` и `schedule.js` получают готовую шапку и вешают обработчики на
   существующие узлы. Порядок подключения файлов — часть контракта (он же
   проверяется `check-frontend.mjs`).
4. **Повторный `render()` ничего не затирает** — флаг `header.dataset.filled`.
   Смысл не в «не удвоить разметку» (присваивание `innerHTML` удвоить её не
   может), а в том, что страничные скрипты правят шапку после отрисовки:
   `dashboard.js` пишет имя пользователя и прячет `#adminLink`. Второй вызов —
   горячая перезагрузка, лишний `<script>`, тест — стёр бы эти правки.
5. **Страница 404 намеренно исключение из правил этой ADR.** `web/404.html`
   (70 строк) не подключает ни одного скрипта и использует абсолютные пути
   (`/css/style.css`, `href="/login"`). Причина: она отдаётся на произвольной
   глубине (`/a/b/c`), и относительный путь там разрешится не в приложение, а в
   `/a/b/login`; и ошибка должна работать, когда приложение не работает.
   Запрошенный адрес на страницу не выводится — только фиксированный текст.
6. **`Handlers.NotFound` различает API и страницы** (`internal/handlers/pages.go`):
   `/api/*` получает `404` + JSON `{"error":{"code":"not_found","message":"route not found"}}`
   (иначе клиент `GS.fetchJSON` падал бы на разборе HTML; форма отказа — `ADR-0003`,
   на момент этого пункта было плоское `{"error":"route not found"}`), остальное —
   `web/404.html` со статусом `404`. HTML читается через `os.ReadFile` и пишется с явным
   `WriteHeader(404)`, потому что `http.ServeFile` вставляет `200` сам и
   перечить ему не может; нет файла — обычный `http.NotFound`.
7. **Два обработчика отправки свёрнуты в `bindCreateForm`** в `schedule.js`:
   блокировка кнопки, `is-loading`, сброс формы, сообщение, перезагрузка списка —
   механизм один, различаются только адрес, тексты и `buildPayload`. Дата события
   вынесена в `toEventDate` (нечитаемое и пустое дают `""`, то есть «без даты»).
   Хелпер приватный и живёт в этом файле: второй потребитель не выдуман, а
   публичный API на одного потребителя — это контракт, который надо поддерживать.
8. **`check-frontend.mjs` получил узкое исключение.** Правило «каждый
   `getElementById` объявлен на странице» теперь считает объявленными и `id`,
   перечисленные в таблице `PAGES` — но только в `core/layout.js`, а не в любом
   скрипте. Иначе проверка превратилась бы в «ссылаться можно куда угодно».
   Исключение проверено в обе стороны: с ним — 7 страниц ок, без `id` в `PAGES`
   — FAIL.

**Проверено.** `gofmt -l` пусто, `go vet ./...` чисто, `go test -race -count=1 ./...`
— шесть пакетов ok: 88 тестов верхнего уровня + 32 подтеста (было 83 + 32; новые 5
в `cmd/server/notfound_test.go`: неизвестная страница, глубокий путь, `/api/*`
на `GET` и `POST`, известные страницы остались `200`, в 404 нет ни `<script`,
ни `onclick=`). `node --check` по 12 файлам `web/js` (2331 строка) — чисто,
`check-frontend.mjs` — 7 страниц, 12 скриптов подключены. JSDOM: пятый сьют
`tests/ui/schedule-forms.cjs` (54 проверки) полностью офлайновый — `fetch`
подменён роутером, сервер не нужен и лимитер входов (`ADR-0006`) не расходуется;
четыре прежних сьюта добавили `core/layout.js` в бандл. Чистый прогон
`npm run test:all` против свежего сервера на `:8099` с сидом: 20/20 · 24/24 ·
21/21 · 14/14 · 54/54 = 133 проверки, код выхода 0. Мутационная проверка сьюта
(7 мутаций, каждая убивается ровно своим пунктом): без `form.reset()` — 2 FAIL,
без защиты `isNaN` в дате — 3 FAIL, без `await reload()` — 4 FAIL, без проверки
заголовка до запроса — 4 FAIL, без `dataset.filled` — 1 FAIL, `brand-sub` вразрез
с атрибутом страницы — 1 FAIL, без CSRF-заголовка в клиенте — 1 FAIL. Эквивалентность
разметки сверялась структурным диффом jsdom-документа против `git show HEAD:web/<page>`:
совпадает, кроме двух сознательных отличий (см. ограничения). Развёртывания не было.

**Ограничения, которые надо знать.**

- **Шапка теперь зависит от JS.** Без JavaScript навигации на странице нет
  (ни в шапке, ни в подвале) — раньше она была в HTML. Размен осознанный: весь
  рабочий интерфейс и так требует JS, а цена обратного хода — 24 строки на
  страницу. Если понадобится индексация ссылок поисковиками или чтение без JS,
  разметку возвращаем в HTML (или делаем SSR), и `layout.js` тогда остаётся для
  состояний (`#userName`, скрытый `#adminLink`).
- **Визуально в браузере не проверялось.** Подтверждены DOM и HTTP-поведение
  (jsdom + Go-тесты + `curl`), не подтверждён пиксельный результат: заголовок,
  отступы и чипы в шапке выглядят как раньше с точностью до разметки, но
  скриншотом это не сверялось.
- **Две осознанные отдачи от прежней разметки.** У декоративных SVG в ссылках
  навигации появился `aria-hidden="true"` (скринридер читал иконку как текст);
  в подвале `/admin` устаревшая подпись `RequireRole · admin only` заменена на
  `authz · только администратор` — права с `ADR-0010` живут в реестре, а не в
  `RequireRole`.
- **404 под GitHub Pages (вариант B, `ADR-0001`) требует своего файла.**
  Абсолютные `/css/style.css` и `/login` верны для Go-сервера в корне и неверны
  под каталогом `https://<user>.github.io/SOS/`. При публикации нужен
  `404.html` с путями от базового каталога — это тот же открытый вопрос D-01,
  что и для `deploy-frontend.yml`.
- **Хвост T3.1 остаётся:** `profile.html` (отдельная страница профиля вместо
  блока в кабинете) и `deploy-frontend.yml`. `core/layout.js` — не предлог для
  новой страницы: профиль решается в `docs/04` отдельно.

## ADR-0014. Остаток T3.1: страница `/profile` и перенос панели доступа

Статус: принята агентом 3 (фронтенд) совместно с агентом 1 (архитектура). Реализовано в `ae291e8`, прогон CI — в таблице прогонов `docs/04`.

**Контекст.** `docs/04` ставил `profile.html` в зависимость от ответа B1/B2 и
перечислял содержимое: «имя, email, группа, preferences, выход из всех сессий».
Из этого набора платформа хранит только имя, логин, почту и роль
(`internal/models` — `User`, `db.go:44-51`): `groups` и `user_preferences` в
схеме отсутствуют (строка «Сущности …» в матрице расхождений `docs/01` §6), а
номер учебной группы — часть источника расписания, то есть B2. Выбор поэтому был
между «не делать страницу, ждать ответов» и «нарисовать таблицу с пустыми
полями группа/предпочтения»; второе прямо противоречит требованию брифа не
выдумывать данные и структуре источника. Третья зацепка лежала в самой разметке:
смена пароля и «выйти везде» жили секцией `04` в `dashboard.html`, хотя по
постановке задачи это содержимое профиля, а не кабинета.

**Решение.**

1. **Профиль показывает ровно то, что хранится.** Один запрос
   `GET /api/auth/me`, четыре строки таблицы: имя (или логин, если имя пустое),
   логин, почта, роль с подписью и чипом из `core/format.js`. Ни одного поля,
   которого нет в ответе сервера.
2. **Секция «Группа и предпочтения» — текстовая, без пустых inputs.** Она
   говорит, что полей нет в схеме и откуда они зависят (B1/B2), вместо
   заглушек, которые человек принял бы за данные. Именно этот пункт отличает
   страницу от «нарисуем UI под неизвестный источник».
3. **Панель доступа переехала с кабинета на профиль** — секция вместе со
   `web/js/account.js`, без второй копии разметки. Размен: путь «сменить
   пароль» стал на один клик длиннее (шапка → Профиль), зато форма одна, и
   она на странице, которая по постановке задачи за доступ и отвечает.
4. **Значения пишутся через `textContent`, а не `innerHTML`.** Имя и почту
   может изменить администратор через API, и экранирование в шаблоне — то, что
   забывают; здесь шаблон, в который подставляется строка, отсутствует вовсе.
5. **Ошибка чтения профиля не остаётся «Загрузкой…».** При 5xx, сетевом сбое и
   теле без логина ячейки становятся прочерками, а над таблицей появляется
   текст. Это та же приёмка, что закрыла «вечный spinner» в первой половине
   T3.1, только на новой странице.
6. **401 обрабатывает транспорт, а не страница:** политика `on401: "redirect"`
   уводит на вход, и текст ошибки человек, скорее всего, не увидит — редирект
   быстрее. Для смены пароля на этой же странице поведение обратное
   (`on401: "throw"` в `account.js`): там 401 — штатный «неверный текущий».
7. **Навигация — через общий компонент:** в `core/layout.js` добавлен вариант
   `profile` (кабинет, расписание, блок пользователя, выход) и ссылка
   «Профиль» в вариантах `dashboard` и `admin`. Ссылки относительные, как и
   везде (ADR-0011), иначе под каталогом Pages они ушли бы в корень домена.
8. **Доступ страницы решает сервер, а не JS:** `Handlers.ProfilePage` без
   сессии отдаёт `302` на `/login`, как `DashboardPage`. HTML-страницы идут
   мимо реестра прав (ADR-0010), поэтому проверка живёт в обработчике, а её
   наличие закреплено тестом на уровне маршрутизатора.

**Проверено.** `gofmt -l` и `go vet ./...` — чисто. `go test -race -count=1 ./...`
— шесть пакетов `ok`, 91 тест верхнего уровня и 32 подтеста (123 строки `PASS:`);
новые `cmd/server/profile_test.go` — 3 теста. `node --check` — 13 файлов `web/js`.
`scripts/check-frontend.mjs` — 8 страниц, все скрипты подключены (в том числе
`account.js → profile.html` и новый `profile.js → profile.html`), инлайновых
обработчиков нет. `npm run test:all` против свежего изолированного сервера
(`:8099`, отдельный файл базы) — код выхода `0`, шесть сьютов: 54 + 35 + 20 +
24 + 29 + 14 = 176 проверок, 14 входов в логе сервера (лимитер 20/10 мин,
ADR-0006, не исчерпан). Новые проверки прогнаны мутациями: семь правок
(`setError` без сброса ячеек, отсутствие guard на ответе без логина, незаполненная
шапка, роль без подписи, `on401: "throw"`, имя без фолбэка на логин, убранный
`<script src="js/account.js">`) — каждая уронила именно свой пункт, а не
«что-нибудь». Развёрнуто ничего: публикация Pages не делалась.

**Что это не закрыло.** Полей группы и предпочтений по-прежнему нет — это
вопросы владельцу B1 и B2, и страница их не прячет, а называет. Панель не
проверена в настоящем браузере (только jsdom и HTTP-ответы Go), визуальная
часть опирается на существующий CSS без новых классов. Осталась копия
обработчика отправки в `dashboard.js` (создание курса): `bindCreateForm`
приватен для `schedule.js`, и вынести его в `GS` — отдельный шаг.

## ADR-0015. T4.1: источник расписания — АПЭКС-ВУЗ, Go-клиент, хранение импорта и страница вместо внешней ссылки

Статус: принята агентом 4 (источники) совместно с агентом 1 (архитектура) и агентом 3 (фронтенд). Реализовано в `1baa480`, прогон CI — в таблице прогонов `docs/04`.

**Контекст.** ADR-0004 оставил `T4.1` заблокированным: эндпоинт, параметры и формат
ответа источника были неизвестны, а `docs/01` §8 зафиксировал, что `tksu.ru` с машины
разработки недоступен и выдумывать структуру нельзя. Блок снял артефакт владельца —
готовый Python-парсер (`schedule_parser`): в нём есть боевой адрес
`https://apeks.tksu.ru/api/call/schedule-schedule/student`, способ доступа (токен в
query-параметре) и живой пример ответа, который лёг в `testdata/` без правок. Требование
брифа к этому месту — «парсер расписания, день/неделя по группе, аудитория, время
последнего обновления», и оно до сих пор не выполнялось: `/schedule` показывал
ссылку на виджет вуза.

Дальше были четыре решения, каждое с ценой.

**Решение.**

1. **Парсер переписан на Go, а не оставлен как Python-процесс.** Вариант
   sidecar (`python parser.py | json`) означал второй рантайм во всех трёх
   работах CI, отдельную сборку, отдельный способ упасть и невозможность
   потестить разбор одним `go test`. У Python-версии есть ценность, но это
   эталон, а не зависимость: из неё взяты адрес, параметры запроса и правила
   разбора (сортировка по реальному времени начала, флаги «пустая пара» и
   «самоподготовка» вместо выдуманной дисциплины,
   декодирование флаг-полей), а живой ответ зафиксирован фикстурой, чтобы
   расхождение формата было видно по тесту, а не по пустой таблице.
   **(Отменено ADR-0021 (`63f8cb3`) по прямому указанию владельца: разбор делает
   приложенный Python-парсер, Go-клиент остался запасным движком, выбираемым
   `SCHEDULE_SOURCE`. Из аргументов выше пережиты оба: «потестить одним `go test`»
   теперь покрывает и мост, и паритет двух разборов, а «второй рантайм во всех трёх
   работах CI» обернулся одной офлайн-работой без сети и без секретов. Пункт 2 этим
   решением не отменён: токен по-прежнему едет в строке запроса к чужому API, строго
   по HTTPS и ни в одном логе не печатается — у Python-пути он к тому же не попадает в
   аргументы запущенного процесса, потому что передаётся только окружением.)**
2. **Токен в URL-запросе — осознанный компромисс с пунктом брифа «не включать
   токены доступа в URL».** Так устроен чужой API, и обойти это можно только
   перестав ходить к источнику. Ограничиваем следствие: запрос идёт строго по
   HTTPS (клиент не собирается на http-схеме — иначе токен ушёл бы открытым
   текстом), токен читается только из `APEKS_TOKEN`, не печатается ни в одном
   логе, не возвращается ни в одном ответе API и не попадает в строку журнала;
   `scrub` вырезает его и весь URL из текста ошибки, потому что чужая библиотека
   могла вернуть его внутри `url.Error`; в браузере адрес источника не появляется
   вовсе — там только наши `/api/schedule/*`. Проверка «в ответах и в журнале нет
   токена» — тесты `TestErrorMessagesCarryNoSecret`, `TestTransportErrorIsScrubbed`
   и пункт офлайн-сьюта.
3. **Хранение — отдельные таблицы импорта, а не `events`/`schedule_entries`
   мечты.** `schedule_source_groups (source, external_id)` и
   `schedule_source_lessons` с `UNIQUE (source, group_ext_id, external_id)`;
   учебный день — `day_key` числом `YYYYMMDD` (у источника время пары — строка
   «12:20 – 13:55» без даты-во-всём-мире, а `timestamptz` из выдуманной даты был
   бы вымыслом), день без точной даты — `99999999`. Импорт месяца — замена
   целиком в одной транзакции: повторный импорт не удваивает пары, удалённая
   источником пара исчезает и у нас, а битый ответ источника не оставляет
   половину месяца (тесты `TestReplaceMonthIsRepeatable`,
   `TestReplaceMonthDropsStaleLessons`, `TestImportBrokenPayloadKeepsOldMonth`).
   Текст нормализуется и очищается от HTML на сервере — страница рисует то, что
   лежит, без попыток «починить» данные на клиенте.
4. **Чтение публичное, запись — право и CSRF.** `GET /api/schedule/groups` и
   `GET /api/schedule/lessons` объявлены `Public: true`: в ответе нет
   персонального, а гость страницы расписания — нормальный читатель (это и есть
   ответ на «ссылку на первоисточник видеть должен каждый», и ссылка
   `source_page_url` приезжает вместе с данными). Три админских маршрута
   закрыты новым правом `schedule.source.manage` (только `admin`) и требуют
   CSRF-заголовок. Исходящий запрос к чужому сайту возможен только оттуда, где
   стоит человек и его кнопка: автоматического планировщика в этой части нет,
   `IMPORT_INTERVAL` не реализован, и частота обращений к источнику остаётся
   административным решением.
5. **Пустое состояние отличается от ошибки и от «пар нет».** Без токена сервер
   стартует штатно, страница говорит «расписание ещё не импортировано», а
   админская панель подсказывает переменную `APEKS_TOKEN`; пустой месяц —
   отдельный текст, потому что «в этом месяце занятий нет» и «мы ничего не
   забирали» — разные вещи. Вымышленных пар на странице появиться не может по
   конструкции: рисует её только `GET /api/schedule/lessons`.
6. **Внешняя ссылка не удалена, а понижена до кнопки.** Виджет вуза остаётся
   первоисточником, и у читателя должен быть путь свериться; наше расписание
   — это копия, и называть её заменой оригинала нельзя.
7. **Страница переключена на наши данные без отказа от уже сделанного.** Лента,
   витрина ресурсов и события на `/schedule` не тронуты; добавлены поиск по
   каталогу групп с `datalist`, переключение месяца, метка «обновлено …», а
   выбранные группа и месяц запоминаются в `localStorage` — это состояние
   просмотра, а не персональные данные, и именно поэтому оно не спрашивает
   входа. Инициализация страницы больше не обрывается на 401: гостевая ветка
   читает публичные маршруты, а сбой профиля (5xx) показывается текстом, а не
   молчаливой подменой «вы войдите».

**Проверено.** `gofmt -l` и `go vet ./...` — чисто. `go test -race ./...` — семь
пакетов `ok`, 150 тестов верхнего уровня и 52 подтеста, из них новые: `internal/apeks`
(23 теста: разбор фикстуры, конфиг и HTTPS-гард, токен в запросе и его отсутствие в
ошибках, таймаут и отмена, лимит размера ответа), `internal/store/schedule_source_test.go`
(15: каталог, разрешение группы и неоднозначность, замены месяца, диапазоны и порядок,
статистика, идемпотентность миграции), `internal/handlers/schedule_source_test.go`
(21: публичность чтения, отказ записи без права/CSRF/сессии, импорт и журнал,
неконфигурированный источник = `503`, скрытие подробностей источника).
`node --check` — по всем файлам `web/js`, `scripts/check-frontend.mjs` — 8 страниц.
Офлайн-сьюты: `schedule-timetable.cjs` 59/59 (гость видит таблицу, редиректа нет,
plural-формы, экранирование `<img onerror>`, переход декабрь 2026 → январь 2027,
разрешение имени в id, состояния 502/404, payload импорта без `count` и с `count:3`,
ни одного запроса на `tksu.ru`), плюс прежние `schedule-forms` 54, `profile-page` 35,
`assignments-modal` 20, `account-security` 29, `session-expiry` 14 и `admin-roles` 24
против живого сервера. Конец-к-концу проверялся локально против TLS-стаба источника:
синхронизация каталога, импорт месяца (22 пары), затем тот же импорт повторно, и
jsdom-рендер настоящей страницы против живого сервера — 6 дней / 22 пары, 0 ошибок в
DOM, у гостя панель источника скрыта. Работа `ui` из `ci.yml` повторена локально
целиком (своя база, порт `:8123`, `seed.sh` + `npm run test:all`): 235 проверок,
семь сьютов, код выхода 0. Развёрнуто ничего: прод-стенд и Pages не
настраивались, а боевой `apeks.tksu.ru` с этой машины по-прежнему не проверялся —
проверен тот же формат, что принёс парсер владельца. CI на GitHub эти коммиты ещё
не видел: PR #2 слит в `main` (`64a1232`), а `ci.yml` запускается на `pull_request`,
push в `main` и вручную — push в feature-ветку прогона не создаёт, нужен новый PR.

**Что это не закрыло.** Расписание по неделе/дню как режим просмотра (есть месяц),
подписка студента на свою группу (`groups` как сущность с участием людей — это B1/B2
из `docs/03`), планировщик импорта, история изменений импорта (`import_runs`) и
переезд этих двух таблиц на PostgreSQL (`T2.1`). Живая проверка против настоящего
источника остаётся за владельцем: если формат окажется другим, лечится это парсером и
фикстурой, а не переписыванием модуля.

## ADR-0016. T0.5: доступность — сначала измерить, потом править то, что не проходит численно

Статус: принята агентом 3 (фронтенд). Реализовано в `1256959`, документация — в коммите `docs:` сразу за ним (этот файл).

**Контекст.** `docs/01` §7 перечислял пять пропусков во фронтенде: нет skip-link,
нет `aria-current` в навигации, у `<th>` нет `scope`, на `dashboard`/`schedule`/`admin`
нет `<h1>` при `h3` в карточках (разрыв иерархии), у модалок нет `role="dialog"`,
ловушки фокуса и возврата фокуса — и отдельно оговорка, что вспомогательный текст
`--muted #8d8676` «требует проверки контраста (не проверено численно)». Последняя
оговорка и была настоящим началом работы: править доступность «по списку» означает
дописывать ARIA вслепую, а это ровно то, что в отчёте уже было записано как правдивое
утверждение про модалки и не оказалось им (пункт 6 ниже).

Сначала считалка. WCAG 2.1 1.4.3 требует 4.5:1 для текста обычного размера, 1.4.11 —
3:1 для границы компонента. Относительная яркость по sRGB считается по формуле, а не
на глаз, и `#8d8676` на `#e9e2d3` дал **2.81:1**, на `--parchment-deep` — **2.48:1**.
То есть подписи форм, меты карточек и «Обновлено …» были нечитаемы по критерию AA, и
это был единственный пункт из списка, который можно было проверить до решения, а не
после.

**Решение.**

1. **Контраст правится значением токена, а не новыми классами.** `--muted` стал
   `#625b4c` (5.22:1 на parchment, 5.56:1 на surface, 4.62:1 на parchment-deep,
   6.73:1 на белом), `--danger` — `#a13f35` (текст отказа на `--danger-tint` давал
   4.38:1, стало 4.74:1; подпись удаления на красном — 5.64:1). Тон тот же тёплый,
   палитра не менялась: вопрос A7 из `docs/03` (тёмно-синяя база из брифа вместо
   parchment) остаётся открытым, и проверка контраста намеренно сравнивает **пары**
   токенов, а не запомненные значения, — переделка палитры пройдёт через неё, а не
   мимо неё.
2. **Граница контрола отделена от декоративного разделителя.** `--line` оставлен как
   есть для линеек и разделителей (1.27:1 с подложкой — это декор, а не сигнал),
   для контура поля введён `--line-strong #877f6f` (3.08:1 на parchment, 3.28:1 на
   surface). Без него «куда нажимать» различалось только по neumorphic-тени, а тень
   — не граница по смыслу критерия.
3. **Skip-link первым делом, цель — фокусируемый `#main`.** На всех восьми страницах
   первая ссылка — `<a class="skip-link" href="#main">К основному содержимому</a>`,
   `<main id="main" tabindex="-1">`. Обе детали не косметические: `display:none`
   спрятал бы ссылку и от скринридера, поэтому она вынесена за вьюпорт
   (`top:-60px`) и возвращается при `:focus`; а без `tabindex="-1"` переход по якорю
   прокручивает страницу, но фокус оставляет в шапке — то есть клавиатурный читатель
   всё равно начал бы с навигации. Рамка фокуса вокруг `<main>` снята: это шум, а не
   подсказка.
4. **У каждой страницы есть `<h1>`, и уровни не перескакивают.** Добавлены
   `h1.page-title` на `dashboard` («Личный кабинет»), `schedule` («Расписание и
   ресурсы»), `profile` («Профиль»), `admin` («Администрирование»), `404` («Страница
   не найдена»); на `index` и страницах входа `<h1>` уже был (`hero-title`,
   `auth-title`). Нумерованные подписи секций (`01 Возможности`, `02 Журнал действий`)
   переведены из `<span class="section-label">` в `<h2>` — 16 мест на пяти страницах
   (`index`, `dashboard`, `schedule`, `profile`, `admin`); класс и вёрстка не
   изменились, изменился только тег. Одно исключение — `404`: там подпись секции
   «404 · Ошибка транспорта» осталась `<span>`, потому что заголовок страницы уже
   есть (`<h1>` + `<h2>` внутри панели), и третий заголовок того же смысла был бы
   ложной структурой.
5. **Ориентир «Навигация» рисует `core/layout.js`, а не только гостевые страницы.**
   `<div class="top-actions">` стал `<nav class="top-actions" aria-label="Навигация
   страницы">`; у гостевой ветви (`<nav class="nav">`) имя добавлено то же. Классы
   обёрток сохранены, поэтому вёрстка не сдвинулась, но на «Кабинете», «Расписании»,
   «Профиле» и в админке список ориентиров страницы перестал быть пустым.
6. **`aria-current` сознательно не вводился.** Проверено конфигом страниц в
   `web/js/core/layout.js`: ни одна ссылка шапки не ведёт на ту страницу, на которой
   стоит, — это панель действий («Курсы», «Задания», «Выйти», «Админ»), а не карта
   разделов. Атрибут `aria-current="page"` пришлось бы вешать на ссылку, которая всегда
   ведёт «не сюда», то есть писать мёртвый код ради галочки в списке. Первый вариант
   правки был именно такой и откачен до коммита; в `check-frontend.mjs` нет проверки на
   него, чтобы он не «требуился» задним числом.
7. **Пункт про модалки в отчёте был устаревшим, а не недостающим.** `role="dialog"`,
   `aria-modal="true"`, `aria-labelledby`, ловушка фокуса на Tab/Shift+Tab и возврат
   фокуса на элемент, который открыл окно, живут в `web/js/modals.js:12-126` с T0.1
   (`3368fc2`). Ничего из этого не дописывалось; вместо этого тот же путь закрыт
   тестом — иначе через неделю отчёт снова утверждал бы то, чего уже нет.
8. **Закрепляется проверка двумя слоями, потому что слои ловят разное.**
   `scripts/check-frontend.mjs` добавила секции 5 и 6: `lang`, `<title>`, ровно один
   `<h1>`, отсутствие разрыва уровня, skip-link первой ссылкой и в существующий
   фокусируемый `id`, `scope` у каждого `<th>`, и 13 пар контраста по формуле sRGB
   (пороги 4.5 и 3). Это статика, которая падает, если кто-то удалит заголовок или
   посветлит токен в `:root`. `tests/ui/accessibility.cjs` (103 проверки, офлайн —
   подменный `fetch`, лимитер входов не расходуется) проверяет то, чего статика не
   видит: что `<nav>` в шапке действительно появляется после `renderLayout`, что
   ссылки навигации внутри него, что аватар скрыт `aria-hidden`, что модалка закрывает

не трогали), `seed.sh` + `npm run test:all` — 103 + 55 + 59 + 35 + 20 + 24 + 29 + 14 =

учётки пароль не меняет) — прогон перенесён на чистую базу, и это же объясняет, почему
повторные «живые» прогоны требуют перезапуска сервера ещё и из-за лимитера входов.

`<nav>` — каждая поймана соответствующим слоем, файлы восстановлены.

токенов — не для каждого сочетания в CSS (hover-состояния, `--teal-tint` подложки,

расширяется вместе с комментарием в CSS, а не автоматически. **(Закрыто ADR-0019,

новых состояний фокуса не выполнена. **(Приёмка сделана ADR-0020, `304f0cc`:

видимость колец; найдено и исправлено одно невидимое кольцо — радиокнопка на входе в

его по-прежнему не было, и он требует человека, а не машины разработки.)**
Связь «поле → строка сообщения» через
`aria-describedby` не проставлена: сообщения подписаны `role="status"` (11 мест, было

вопросах доступности не трогались.

## ADR-0017. Третья копия submit-обработчика: общий механизм уезжает в `GS`, а копия — под запрет CI

Статус: принята агентом 3 (фронтенд). Реализовано в `3a6c8e9`, документация — в коммите `docs:` сразу за ним (этот файл, `fb51659`).

**Контекст.** ADR-0013 (`8b3a027`) свёл две копии обработчика отправки в `schedule.js`
к одной приватной функции `bindCreateForm` и оставил на месте комментарий: «если
понадобится dashboard.js, он переедет в common.js без изменения вызовов». `docs/01` §7
при этом прямо записывало остаток: «остались копии в других скриптах:
`dashboard.js:284-309` (создание курса) — та же форма обработчика, слово в слово».
Слово в слово — не фигура речи: совпадали `preventDefault`, чтение `FormData` с
`trim()`, проверка `payload.title` до запроса, `classList.add("is-loading")` +
`disabled`, сохранение и возврат `innerHTML` кнопки в `finally`, `form.reset()` после
успеха и `showMessage` в `catch`. Отличались адрес, набор полей и тексты.

Вторая, более неприятная деталь: копия на кабинете оказалась **старой по поведению**.
Она печатала `error.message` напрямую, поэтому подпись поля из конверта 422 — то, что
ADR-0003 добавил специально («title is required» плюс «поле: Название»), — на
расписании появлялась, а на кабинете нет. Класс, ради которого T0.4 вообще писался:
механизм правят в одном месте, а второе место молча остаётся прежним, и ни `go test`,
ни `node --check` этого не видят.

**Решение.**

1. **Переезд при третьем потребителе, не раньше.** Функция перенесена из `schedule.js`
   в `common.js` и опубликована как `GS.bindCreateForm`. На двух формах одной страницы
   приватная функция была правильным решением (ADR-0013, пункт про «публичный API на
   одного потребителя — это ещё один контракт»); контракт появился, когда потребителей
   стало двое на разных страницах. Вызовы в `schedule.js` изменились ровно на префикс
   `GS.` — как и обещал комментарий на месте.
2. **Разница текстов — параметром, не копией.** У механизма добавлен `requiredText`
   (по умолчанию «Название обязательно»): страница курса говорит «Название курса
   обязательно», и этот текст остался у страницы. Всё остальное общее: `form`,
   `message`, `endpoint`, `buildPayload`, `successText`, `errorText`, `reload`.
   Разбор даты события (`toEventDate`) остался страничным — он нужен только расписанию.
3. **Кабинет получил поведение ADR-0003.** `error.message` → `describeServerError(error,
   form, errorText)`, то есть отказ 422 на создании курса теперь показывается как
   «title is required — поле: Название курса». Живой curl на изолированном сервере
   подтвердил, что сервер и правда отдаёт `fields: {"title": …}` — подпись берётся из
   label формы, а не выдумана.
4. **Что осознанно НЕ переехало.** `auth.js` (вход) и `account.js` (смена пароля): у
   них 401 — штатный ответ формы (`on401: "throw"`), нет «перезагрузить список» и нет
   `buildPayload` в этом смысле. `modals.js`: делегирование на весь документ с разбором
   по `data-`-атрибутам, другая форма механизма. `GS.bindCreateForm` — это не
   «универсальный submit», а именно «создать запись и перезагрузить список», и
   расширять его на все виды форм до второго реального случая не стали бы по той же
   причине, что и в пункте 1.
5. **Копия карается проверкой CI, а не правилом в документе.** В
   `scripts/check-frontend.mjs` добавлена седьмая группа: определение
   `bindCreateForm` ровно одно и лежит в `common.js`; хотя бы одна страница его вызывает
   (мёртвый механизм — тот же род бага, что неподключённый `modals.js` до T0.1); и ни
   один страничный скрипт не содержит `addEventListener("submit"` вместе с
   `classList.add("is-loading")` — за исключением `modals.js`, чьё исключение названо в
   коде с причиной. Проверка статическая, потому что копипаста в рантайме выглядит как
   успех: поведение общее, а расходится оно только когда кто-то правит одну копию.

**Проверено.** `gofmt -l` пусто, `go vet` чисто, `go build` ok — продуктовый Go не
менялся вовсе (те же 52 файла и 9122 строки), `go test -race -count=1 ./...` — семь
пакетов `ok`, 158 верхнеуровневых тестов и 52 подтеста (210 запусков, ноль `FAIL`).
`node --check` по всем файлам `web/js` (13) и по `scripts/check-frontend.mjs`;
`node scripts/check-frontend.mjs` — exit 0, восемь страниц и две страницы на общем
механизме в списке заметок. Офлайн-сьют `tests/ui/schedule-forms.cjs` вырос с 55 до
80 проверок: добавлен раздел про кабинет (payload курса, своя формулировка
обязательного поля, сброс и перезагрузка каталога, подпись поля из 422, сохранение
ввода при отказе, 401-редирект без залипшей кнопки, скрытая форма у студента) и два
статических пункта про единственность механизма. `./seed.sh` (exit 0) +
`npm run test:all` против изолированного сервера `127.0.0.1:8155` на свежей базе —
**8 сьютов, 364 проверки (277 офлайн + 87 против сервера), код выхода 0**. Живой
ответ `POST /api/courses` с пустым названием сверялся curl'ом на `:8156` (своя база,
админ-сид): 422, `code: "validation"`, `fields.title` — конверт ADR-0003 без изменений.
Проверка мутациями: вернуть локальный обработчик в `dashboard.js` → пойманы и
статическая проверка, и «пустое название отсекается до запроса», и текст отказа
(77/80); убрать экспорт `bindCreateForm` из `GS` → падают обе страницы и сьют
шумно; определение в двух файлах → «определений найдено 2»; определение только в
`schedule.js` → «должно жить в common.js»; ни одного вызова `GS.bindCreateForm` →
«механизм мёртвый». Файлы после каждой мутации восстановлены из копии, финальный
прогон зелёный. Второй прогон `test:all` подряд на том же сервере упал на 429
(`s_stud не входит`) — это документированный эффект лимитера входов (ADR-0006,
20 попыток на IP за 10 минут), а не регрессия: повторный прогон сделан на новой базе и
сервере, exit 0.

**Что это не закрыло.** `auth.js` и `account.js` по-прежнему пишут свои submit-обработчики
сами — сознательно (пункт 4), но это значит, что «один submit-механизм на фронтенде»
верно только для форм создания, и формулировку надо держать точной. Поведение кабинета
в браузере глазами не проверялось: jsdom и curl, не живой клик (страница пользователя на
`:8080` не трогалась). Механизм по-прежнему рассчитывает на поле `title` как на
обязательное: форма, где обязательным является не `title`, требует либо своего
проверочного шага, либо нового параметра — до первого такого случая не выдумывали.
`check-frontend.mjs` ловит копию по двум признакам (`submit` + `is-loading`);
копия, устроенная иначе (например, со своей кнопкой-загрузкой), мимо него пройдёт.

## ADR-0018. Связь «поле → сообщение»: aria-describedby проставлен и защищён проверкой

Статус: принята агентом 3 (фронтенд). Реализовано в `11ac07f`, документация — в коммите `docs:` сразу за ним (этот файл).

**Контекст.** ADR-0016 закрыл доступность структуры и контраста, но сам же записал
в «что это не закрыло»: строки сообщений подписаны `role="status"`, а поле никуда на
них не ссылается. Это KVK-дыра в двух смыслах. Первый — практический: live-region
озвучивается в момент изменения текста, и если фокус уже стоит в поле (а после
отказа формы он обычно там и остаётся), пользователь слышит сообщение только если
не отвлёкся; ассистивная технология, которая читает описание поля по входу в него,
не читает ничего, потому что описания у поля нет. Второй — этот остаток был
единственным пунктом `docs/01` §7 и ADR-0016, который не требовал ни решения
владельца, ни Docker, ни браузера: его можно было закрыть здесь и сейчас.

Отдельным шагом, а не хвостом T0.5, потому что у правки своя приёмка: атрибут
виден только запросом к DOM, а типичная ошибка в нём — не отсутствие, а опечатка в
id, при которой ссылка формально есть и ведёт в никуда.

**Решение.**

1. **Ссылка ставится в HTML, а не в рантайме.** Можно было навесить
   `aria-describedby` из `common.js` одной строкой на все поля сразу, но тогда
   страница без JS (и `404.html`, где скриптов нет намеренно) осталась бы с
   несоответствием разметки и проверки, а проверка превратилась бы в проверку
   кода, а не контракта. Атрибут в разметке — это то, что уйдёт в браузер вместе
   с первым ответом сервера.
2. **Что именно ссылается.** В каждой форме, где есть строка с `role="status"`,
   на неё ссылается каждое поле с `class="control"` (22 атрибута, 29 ссылок в
   восьми HTML-страницах). Подсказки `span.helper`, которые раньше были просто
   текстом рядом, получили id (`identifierHelper`, `usernameHelper`,
   `teacherHelper`, `newPasswordHelper`, `urlHelper`, `dateHelper`, `roleHelper`,
   `groupHelper`) и попадают в ту же ссылку: порядок — сначала подсказка, потом
   сообщение, потому что текст отказа полезнее читать последним, он и есть причина, по
   которой пользователь вернулся в поле. Поле вне формы со статус-строкой ссылается
   только на свою подсказку: поиск группы на расписании (`groupInput` → `groupHelper`) —
   текст каталога и ошибки загрузки пишет в этот `span` `schedule.js`, формы он не
   отправляет.
3. **Радиогруппа ссылается через `fieldset`.** В регистрации две метки `role`;
   повесить описание на каждую означало бы прочитать одну строку дважды (или
   четырежды, когда ролей станет больше), поэтому ссылка стоит на контейнере
   группы — так же, как на неё смотрит `legend`.
4. **Разметка, которую генерирует JS, не исключение.** Формы модалок
   (`modals.js`: сдача работы, создание задания, поля оценки в таблице сдач)
   собираются из шаблонов, и в HTML их нет вообще — 6 атрибутов и 8 ссылок на
   `modalStatus`, `submitHelp` и `deadlineHelp`; ещё один атрибут (1 ссылка на
   `adminMsg`) рисует `admin.js` в строке смены роли. Итого в JS-шаблонах 7 атрибутов
   и 9 ссылок. Проверка применяет то же правило к самим шаблонам, а поведение
   дополнительно смотрит в DOM живого сьюта.
5. **Закрепление — восьмая группа `check-frontend.mjs`.** Четыре правила: каждая
   ссылка ведёт на id, который есть на этой же странице; каждое поле формы со
   статус-строкой на неё ссылается; подсказка с id подключена к своему полю;
   сгенерированное в JS поле без атрибута — красное. Плюс два стража против
   вырождения: если ссылок во всём фронтенде ноль или ни одна форма не содержит
   `role="status"`, проверка падает, а не молча становится пустой (тот же класс
   риска, что с «мёртвым механизмом» в ADR-0017).

**Проверено.** `gofmt -l` пусто, `go vet` и `go build` чисто, `go test -race
-count=1 ./...` — семь пакетов `ok`, ноль `FAIL`; продуктовый Go не менялся вовсе
(52 файла / 9122 строки). `node --check` по 13 файлам `web/js` и по скрипту;
`node scripts/check-frontend.mjs` — exit 0 и заметка «ссылок 29, форм
со статус-строкой 6, полей в JS-шаблонах 7». `tests/ui/accessibility.cjs` вырос со
103 до 112 проверок: три статические (ссылки существуют, поля связаны, радиогруппа
через fieldset) по всем восьми страницам, и рантайм-проверки на расписании — после
`GS.showMessage` текст отказа лежит именно в том элементе, на который ссылается
поле, `hidden` с него снят, а после `GS.hideMessage` описание пустое, а не залипшее.
`tests/ui/assignments-modal.cjs` вырос с 20 до 24 проверок на сгенерированной форме
(атрибут у каждого поля, ссылки ведут на существующие id, подсказка дедлайна
подключена, поле оценки ссылается на строку состояния модалки). `./seed.sh` +
`npm run test:all` на изолированном `127.0.0.1:8159` со свежей базой — **8 сьютов,
377 проверок (286 офлайн + 91 против сервера), код выхода 0**; входов по логу
сервера 17, то есть бюджет лимитера (ADR-0006) не вырос. Мутации, каждая из которых
сделана и откачена: снятая ссылка на `#message`, опечатка `teacherHelp`, снятая
подсказка `urlHelper`, `fieldset` радиогруппы без ссылки, поле в шаблоне `modals.js`
без атрибута (ловят и статика, и три проверки живого сьюта), снятые вообще все
ссылки и снятые `role="status"` (срабатывают стражи вырождения).

**Что это не закрыло.** Живого скринридера не было: проверены атрибуты, DOM и то,
что текст попадает в связанный элемент, но не то, как связка озвучивается в
NVDA/VoiceOver — это по-прежнему открытый пункт ADR-0016. `check-frontend.mjs`
работает с HTML-разметкой страниц и шаблонами в JS: форма, собранная динамически
из данных (например, если поле начнёт рисовать сторонний код), мимо правила 4.
Ссылка «одно поле → несколько сообщений» не появилась: сейчас на каждое поле
приходится одна строка, и если их станет несколько, порядок чтения — отдельное
решение, а не правка атрибута. Группы, предпочтения и карта (B1/B2/B3) в вопросах
доступности снова не трогались.

## ADR-0019. Покрытие контраста: список пар обязан накрывать CSS, а не пополняться «по мере надобности»

Статус: принята агентом 3 (фронтенд). Реализовано в `487af91`, документация — в коммите `docs:` сразу за ним (этот файл).

**Контекст.** ADR-0016 сам записал в «что это не закрыло», что числа посчитаны для
13 перечисленных пар, а hover-состояния, подложки `--teal-tint` и литеральные цвета
внутри постраничных блоков — нет, и что «список пар расширяется вместе с комментарием
в CSS, а не автоматически». Никто дальше этого списка не шёл, и в этом ровно риск:
проверка остаётся зелёной до той правки, которая её не касается. Как только цвет
появляется в правиле, которого нет в списке, его не читает ни один слой — ни
`check-frontend.mjs` (он сверяет пары из массива, а не из CSS), ни jsdom-сюты (атрибуты
и DOM, не пиксели). Молчание при этом выглядит как «контраст в порядке».

Тот же класс риска закрыт в этом репозитории дважды: ADR-0017 — копия обработчика,
которой нет в проверяемом множестве, и ADR-0018 — стражи вырождения, чтобы пустая
проверка была красной, а не зелёной. Здесь зависимость перевёрнута: проверка есть, но
её вход (список пар) ведёт кто-то руками.

Формулировка ADR-0018 («этот остаток был единственным пунктом, который не требовал ни
браузера, ни Docker, ни слова владельца») была верна в том смысле, что связка поля с
сообщением закрывалась правкой разметки и DOM-тестом. Остаток контраста — тоже работа без
браузера, и он стал следующим шагом того же класса: считать то, что уже можно посчитать,
и замкнуть это проверкой.

**Решение.** Зависимость развернута: не CSS по доброй воле дополняют списком, а список
обязан покрывать CSS.

1. **Покрытие считается по фактическому CSS.** `scripts/check-frontend.mjs` вырезает из
   `style.css` комментарии, разбирает блоки вида «селектор { тело }» (`:root` и `@`-правила
   пропускает) и считает парой случай, когда в одном блоке заданы и текст (`color` или
   `--btn-fg`), и подложка (`background`, `background-color` или `--btn-bg`). Такая
   пара обязана оказаться в `CONTRAST_PAIRS` или в `CONTRAST_EXEMPT`. `var(--btn-fg)` —
   это не цвет, а ссылка на вариант кнопки: конкретное значение лежит в том же блоке,
   поэтому индирект нормализуется в `null` и пара берётся из `--btn-fg`/`--btn-bg` этого
   блока. `transparent`, `rgba()` и унаследованные значения парой не считаются.
   19 уникальных пар в CSS — все покрыты.
2. **Состояния проверяются отдельно, потому что блок с парой — не единственный
   способ их задать.** `.btn:hover` красит только подложку, текст приходит из базы
   (`.btn`), и правило 1 его не видит. Поэтому подложка любого селектора с `:hover`,
   `:active`, `:focus` или `[disabled]` обязана встречаться хотя бы в одной измеренной
   паре. Так в список попали `--teal-hover` (8.57:1) и `--teal-press` (10.30:1).
3. **Инлайновые `style=""` в HTML под тем же правилом.** Сейчас в восьми страницах 6
   таких атрибутов, и ни один не задаёт пару: три — `background:transparent` у заглушек
   пустых состояний (`.empty-state`), остальные — отступы и обрезка панелей. Правило не
   «пустое», оно закрывает зону: one-off блок на одной странице больше не остаётся местом
   без проверки (именно так в ADR-0016 появились непроверенные литералы внутри
   постраничных правил).
4. **Исключение — с проверяемой причиной, а не «значение не понравилось».** Новая
   `CONTRAST_EXEMPT`. Единственное падение в проекте — подпись отключённой кнопки
   `#b3aa97` на `--parchment-deep`, 1.58:1. WCAG 1.4.3 освобождает неактивные компоненты,
   и в этом проекте `disabled` — почти всегда состояние отправки, где
   `.btn.is-loading { color: transparent }` убирает текст совсем и рисует спиннер:
   освобождение не бумажное. Само исключение тоже под проверкой — если пара исчезнет из
   CSS, CI спросит, а мёртвая договорённость не переживёт правку цвета.
5. **Что добавилось числами.** Список вырос с 13 пар до 26: посчитаны впервые состояния
   кнопки (`--teal-hover`, `--teal-press`), подложки `--teal-tint` и `--surface` для
   бирюзового текста, три светлых литерала подписей на бирюзовом (`#f4efe4` у логотипа —
   6.57:1, `#f3eee3` у чипа — 6.51:1, `#f1ece1` у баннера — 6.39:1) и пиктограмма
   `.btn-icon`. Все новые комбинации держат AA; минимальная из них — 4.97:1
   (`--danger` на фоне страницы), прежний минимум 4.62:1 (`--muted` на `--parchment-deep`)
   ниже не стал. Порог 3.0 записан только для двух границ поля и для пиктограммы
   `.btn-icon` (6.33:1 при пороге 3): это не-текстовый компонент по 1.4.11, считать его
   по 4.5 смысла нет, но и «не считать» нельзя. Значения токенов в `:root` не менялись
   ни на одно — `style.css` вырос на 14 строк комментариев, пиксельно ничего не сдвинулось.
6. **Стражи вырождения — третий раз тот же приём.** Пустой `CONTRAST_PAIRS` (считать
   нечего), пустое покрытие (ни одного блока с парой — значит разбор CSS сломался) и
   устаревшее исключение (пара больше не встречается в CSS).

**Проверено.** `node scripts/check-frontend.mjs` — exit 0, 8 страниц и заметка о покрытии:
«уникальных пар «текст + подложка» в CSS и inline-стилях 19, из них инлайновых в HTML 0,
измеренных пар 26, исключений 1 — все покрыты».
`node --check` по 13 файлам `web/js` и по скрипту. Продуктовый Go не менялся (52 файла /
9122 строки): `gofmt -l` пусто, `go vet` и `go build` чисто, `go test -race -count=1 ./...`
— семь пакетов `ok`, ноль `FAIL`. `./seed.sh` + `npm run test:all` на изолированном
`127.0.0.1:8161` со свежей базой `/tmp/sos-adr19.db` — **8 сьютов, 377 проверок
(286 офлайн + 91 против сервера), код выхода 0**; входов по логу сервера 17, бюджет
лимитера (ADR-0006) не вырос. Мутации, каждая сделана и откачена: (а) неизмеренная
комбинация в `.chip-muted`, (б) подложка `:hover`, которой нет в парах, (в) смена
`--btn-fg` у отключённой кнопки — ловят два правила сразу (неизмеренная пара и
устаревшее исключение), (г) инлайновая пара в копии страницы входа, (д) обнулённый
`CONTRAST_PAIRS`, (е) посветлевший `--teal-ink` — три падения по порогам. Сервер
остановлен, порт свободен, временные базы и копии удалены; рабочая инстанция на `:8080`
не трогалась.

**Что это не закрыло.** Проверка видит пары, объявленные в одном блоке: 8 из 26
измеренных сочетаний таким способом не собираются. Двоих из них — подписи кнопки на
`--teal-hover` и `--teal-press` — держит правило 2 (подложка состояния), остальные шесть
живут «текст в компоненте, подложка у родителя или `body`»: границы поля `--line-strong`
на parchment и surface, `--ink-soft` и `--danger` на parchment, `--teal` и `--teal-ink`
на surface. Покрытие их не проверяет: новый тон подложки у родителя при унаследованном
тексте красного не даст. Считаются только плоские значения: `rgba()`-подложки, оверлеи,
градиенты и подложки из изображений в расчёт не берутся (в `style.css` 12 упоминаний
`rgba` — тени и внутренние подсветки). Пороги взяты для WCAG 2.1 AA; 2.2, критерий AAA и
усиленный контраст не проверялись. И главное: ни один из этих численных слоёв не говорит,
как палитра читается живым скринридером или на реальном экране — браузер в этой работе
снова не использовался. **(Экран закрыт следующим шагом, ADR-0020 `304f0cc`: живая
приёмка состояний фокуса плюс группа 9, которая статически запрещает невидимое кольцо;
скринридер — по-прежнему открыто.)**

## ADR-0020. Состояния фокуса приняты живым браузером; различимость кольца закрыта статической проверкой

Статус: принята агентом 3 (фронтенд). Реализовано в `304f0cc`, документация — в коммите `docs:` сразу за ним (этот файл).

**Контекст.** Три ADR подряд записывали один и тот же остаток. ADR-0016: «пиксельная
приёмка новых состояний фокуса не выполнена», ADR-0018 и ADR-0019 повторили это как
единственное, что от доступности осталось. WCAG 2.4.7 (`Focus Visible`) — из всех
критериев, которых касались правки доступности, единственный без проверки: контраст
текста (1.4.3), границу контрола (1.4.11) и разметку (1.3.1, 3.3.1) считают числами и
DOM, а «увидел ли человек, куда попал Tab» — нет.

Ни один из существующих слоёв этого физически не видит. `check-frontend.mjs` читает
текст CSS и токены: он знает, что правило `.radio-card input:focus-visible ~ .radio-dot`
существует и что `--teal-tint` — это `#d6e2df`, но не знает, что под элементом лежит
`--surface`. `tests/ui/accessibility.cjs` работает в jsdom: layout там не считается,
пиксели не красятся, `box-shadow` как картинки не существует. Риск при этом специфичен
для этой палитры: neumorphic собирает состояния из теней и полупрозрачных подложек, и
светлое «мягкое» кольцо выглядит в коде правдоподобно, а на экране не показывает ничего.
Такой случай и нашёлся (пункт 7).

Утверждение ADR-0018 («остаток требовал браузера, поэтому отложен») оказалось неточным:
ограничением было не отсутствие браузера, а то, что его не поднимали. Headless-оболочка
Chromium уже лежала в кэше Playwright, а Node 26 даёт `fetch` и `WebSocket` без единой
зависимости — приёмка доступна на той же машине, где живёт вся остальная проверка.

**Решение.**

1. **Живая приёмка — отдельный скрипт `scripts/check-focus.mjs` (671 строка), не новая
   группа в `check-frontend.mjs`.** Разные слои живут по разным правилам: статика обязана
   работать на голом чекауте в CI, а этот шаг требует запущенный сервер, сид и браузер,
   поэтому у него отдельные коды выхода (0 — видно, 1 — есть невидимые фокусы, 2 — не
   проверялось) и своё место в документации. Реализация — Chrome DevTools Protocol
   напрямую: `chrome-headless-shell --headless --remote-debugging-port=0
   --user-data-dir=<mkdtemp>`, порт из файла `DevToolsActivePort`, цель из `/json/list`,
   дальше `WebSocket` и команды `Page.enable`, `Runtime.enable`,
   `Emulation.setDeviceMetricsOverride`, `Input.dispatchKeyEvent`,
   `Page.captureScreenshot`, `Runtime.evaluate`. npm-зависимостей ноль.
2. **Два прохода вместо одного.** Первый — обход реальными нажатиями `Tab` со
   свежезагруженной страницы: только свежая загрузка сбрасывает «точку продолжения
   клавиатурной навигации» и включает клавиатурную модальность, без этого часть
   фокусов `:focus-visible` не показала бы ничего, и замер врал бы. Список
   фокусируемых из DOM сверяется с тем, куда клавиатура действительно приходит (порядок
   Tab и порядок DOM расходятся из-за `tabindex`, «доехать молча до i-го» нельзя), а
   пропущенное событие не засчитывается недоступностью — нажатие повторяется до сдвига
   фокуса, число повторов печатается. Второй проход — `el.focus()` с проверкой
   `matches(':focus-visible')` и двумя снимками одной области: с фокусом и без.
3. **Метрика видимости — контраст индикатора к тому, что вокруг, а не «сила изменения».**
   Изменившимся считается пиксель с расхождением по каналам больше 8 (шум растеризации и
   антиалиасинга). Окружающий фон — медиана двухпиксельной рамки кадра. Решающая цифра:
   сколько изменившихся пикселей имеют контраст цвета «после» к этому фону ≥ 3:1
   (WCAG 1.4.11 для нетекстового компонента) на площади не меньше 24 px. Площадь —
   вторая страховка, потому что одна яркая точка ничего не доказывает: у текстового поля
   её даёт мигающая каретка (17 пикселей на 10:1 против сотен пикселей настоящего кольца).
   Контраст самого перехода «до → после» — это дух WCAG 2.2 SC 2.4.13; проектом заявлен
   2.1 AA, поэтому он печатается замечанием (NOTE), а не провалом.
4. **Перед снимком всё, что шевелится, заморожено** — `transition`, `animation` и
   `caret-color`: иначе кадр ловит середину перехода, а каретка даёт ложные «сильные»
   пиксели (на этом держались первые ложные FAIL текстовых полей). Кадр берётся в
   документных координатах (`rect` + `scrollX/Y`) с `captureBeyondViewport: true` —
   вьюпортные координаты на прокрученном `/schedule` снимали чужой кусок макета вместо
   элемента. `settle()` ждёт неизменности подписи DOM (тег + id + классы + текст
   фокусируемых), а не только их числа: шапка после `/api/auth/me` остаётся того же
   размера, но ссылки в ней другие.
5. **Браузер ищется, а его отсутствие — не зелёный результат.** Порядок: `--chrome=`,
   `CHROME_PATH`, кэш Playwright, `/Applications`; если ничего не найдено — код 2 и
   текст «проверка не выполнялась» (пустая проверка не должна выглядеть пройденной —
   тот же принцип, что со стражами вырождения в группах 6-9). Учётки проверяются до
   запуска браузера: нехватка `ADMIN_PASSWORD` раньше обрывала прогон в конце и выбрасывала
   уже снятые замеры половины страниц.
6. **Группа 9 в `check-frontend.mjs` — статический замок на тот же дефект.** Каждое
   правило с `:focus`, `:focus-visible` или `:focus-within`, которое снимает системный
   контур или рисует свой (`outline`, `box-shadow`, `border`), обязано задать хотя бы
   один цвет с контрастом ≥ 3:1 против **каждой** из трёх подложек (`--parchment`,
   `--parchment-deep`, `--surface`): статически неизвестно, на какой стоит компонент,
   поэтому держится худшая. Правило, тронувшее индикатор и не задавшее ни одного
   посчитаемого цвета, красное; `currentColor` и `rgba`-тени в расчёт не берутся. Одно
   освобождение — `.main:focus` (контейнер-цель skip-link, `tabindex="-1"`, не компонент
   управления) с причиной в коде; устаревшее освобождение краснит CI так же, как в
   `CONTRAST_EXEMPT`. Стражи: ни одного фокус-правила в CSS и ни одного посчитанного
   кольца. Роли слоёв разделены: живой прогон отвечает «видно ли сейчас», группа 9 —
   «не вернулось ли невидимое кольцо с новой правкой CSS», и работает она там, где
   браузера нет. Сейчас: 7 правил, 6 колец, слабейшее проходящее — `--danger` в
   `.btn-danger:focus-visible` (4,39:1 на `--parchment-deep`).
7. **Что нашёл прогон и что исправлено в продукте.** На `/register` у
   `input[radio] «role»` кольцо рисовал только `--teal-tint`: 211 изменившихся пикселей
   из 8464, из них **ноль** с контрастом ≥3:1 к окружению (максимум 1.33:1) — 1,10:1 к
   подложке панели `--surface` и 1,03:1 к фону страницы. Фокус был, но не виделся: с
   клавиатуры это выглядит как «Tab провалился в никуда». Исправление — то же кольцо,
   что у кнопки (`inset` + `--teal-tint` + 5 px `--teal`): тот же кадр даёт 148 пикселей
   ≥3:1 при максимуме 6,23:1. Весь продуктовый фронтенд — 13 строк в `web/css/style.css`
   (из них 12 — комментарий с числами) и ни одной правки в JS или HTML.

**Проверено.** `node scripts/check-focus.mjs --base=http://127.0.0.1:8174` (свежая база
`/tmp/sos-focus2.db`, `./seed.sh`): 8 страниц, 77 фокусируемых элементов, до всех
доходит `Tab` (недоступных 0), `:focus-visible` совпал на 77 из 77, замеров 77, видимый
индикатор у 63, замечаний 14, невидимых 0, **код выхода 0**. Chromium 151.0.7922.34
(headless shell), 1280×900, `deviceScaleFactor` 1. Тот же прогон на другом порту и
другой базе (`:8162`) дал ровно те же 77 / 63 / 14 / 0 — цифры воспроизводимы, а не
зависят от конкретного запуска. Единственная страница, где понадобились повторные
нажатия, — `/schedule` (6 повторов): таблица перестраивается, пока идёт обход, и
пропущенное событие не должно выглядеть как недоступный элемент.
Мутации живого прогона: откат кольца радиокнопки → `FAIL input[radio] «role»`
(211 / 0 px / макс 1.33:1), код выхода 1; возврат — код 0. Мутации группы 9, каждая
сделана и откачена: (а) тот же откат кольца — «1,03:1 против `--parchment`»; (б)
`.control:focus`, снявший контур без замены; (в) переименованный `.main:focus` — ловят
два правила сразу (неосвобождённое правило и устаревшее исключение); (г) кольцо из
`--sh-dark` (rgba-токен, цвета нет); (д) `--line-strong` как кольцо — 2,72:1 на
`--parchment-deep` при 3,08:1 на `--parchment`, то есть решает именно худшая подложка;
(е) вычерпанные из CSS все фокус-правила — срабатывают оба стража вырождения.
Прогон паритета на этом дереве: `gofmt -l` пусто, `go vet` и `go build` чисто,
`go test -race -count=1 ./...` — семь пакетов `ok`, ноль `FAIL`; `node --check` по 15
файлам (13 в `web/js` и два скрипта); `check-frontend.mjs` — код 0 с новой заметкой
«фокус: правил 7, колец 6»; `./seed.sh` + `npm run test:all` на `127.0.0.1:8173` со
свежей базой — **8 сьютов, 377 проверок, код выхода 0**, входов по логу 17 (бюджет
лимитера ADR-0006 не вырос). Живой прогон `check-focus` и сид на `:8174` вместе стоят
6 входов: 4 у сида и 2 у скрипта (студент входит один раз на три страницы, админ — один
раз). Серверы остановлены, временные базы удалены; рабочая инстанция на `:8080` не
трогалась, браузер пользователя тоже — прогон шёл на отдельном профиле в `mkdtemp`.

**Что это не закрыло.** Живого скринридера не было по-прежнему: картинка доказывает, что
фокус виден, но не то, как озвучиваются `role="status"`, `aria-describedby` и сам переход
по Tab в NVDA/VoiceOver. Это последний открытый остаток ADR-0016, и он по-прежнему
требует не машину разработки, а человека с ассистивной технологией.
Второе: обход идёт по состояниям страниц при загрузке, **модалки не открывались** —
`#modalDialog` живёт в закрытом диалоге, его кольцо (`outline: 2px solid var(--teal)`)
проверяет только статика, картинка не снята; ловушку фокуса в модалке и поныне держит
только jsdom.
**(Снято ADR-0022, `86edfe9`: тот же обход теперь открывает пять состояний диалога настоящими
кликами, замеряет 14 колец внутри окон и проверяет ловушку живым `Tab`. Находка оказалась не
про кольцо: форма с скрытым полем в первом же пункте не отдавала фокус диалогу вовсе, и ни
статика, ни jsdom этого не видели — подробности и числа в ADR-0022.)**
Третье: 14 замечаний (NOTE) — восемь `.control`-полей и `select.control-small` в
админке. Кольцо видно (сотни пикселей ≥3:1 к окружению), но изменение «до → после»
слабое (0 пикселей ≥3:1, максимум 1,9:1), потому что поле темнеет границей и светлеет
подложкой. По WCAG 2.1 AA это не провал; чтобы стало провалом, проект должен заявить
2.2 — это вопрос владельцу, а не решение агента.
Четвёртое: один вьюпорт, одна плотность, один движок. Safari и Firefox рисуют
`box-shadow`-кольца иначе; при 200% увеличении и на 320 px ничего не измерялось. Метрика
— эвристика, а не буквальный текст критерия: 1.4.11 говорит про различимость, а мы
считаем контраст к медиане рамки кадра и площадь ≥24 px; пороги 8 (шум), 24 px и сама
схема «медиана рамки = окружающий фон» выбраны в этом шаге и ни с чем независимым
(axe, Pa11y) не сверялись.
Пятое и главное по регулярности: **в CI этого шага нет** — на раннере GitHub Actions нет
браузера, а смысл проверки в отрисовке, поэтому она ручной шаг, и ничем, кроме этого
текста, не защищена от «забыли прогнать». Группы, предпочтения и карта (B1/B2/B3) в
вопросах доступности снова не трогались.

## ADR-0021. T4.1 (продолжение): источник расписания разбирает приложенный Python-парсер, Go-клиент остаётся запасным движком

Статус: принята агентом 2 (бэкенд) по прямому указанию владельца. Реализована в `63f8cb3`, документация — в коммите сразу за ним (этот файл).

**Контекст.** ADR-0015 (пункт 1 «Решения») записывала обратное: «парсер переписан на Go, а не
оставлен как Python-процесс; это эталон, а не зависимость». Тогда это был единственный
доступный вариант: приложенный парсер пришёл без адреса и без токена, живой
`apeks.tksu.ru` с машины разработки не отвечал, и держать в продукте процесс, который
никто не может запустить, было нельзя. Владелец поставил другую задачу дословно:
«припиши этот парсер на python к сайту. Не переписывай его полностью на Go. Нужно
только то, чтобы он работал на странице с расписанием».

Смысл правки не в языке, а в том, где живёт знание о формате чужого API. Пока разбор
один, расхождение с источником ловится в одном месте. Как только их два (наш Go-код и
поддерживаемый вузом Python-код), второй молча отстаёт: источник поправляют не по
репозиторию платформы. Заодно выяснилось, что обратный вариант тоже неверен — «эталон,
а не зависимость» пережил проверку живым ответом ровно один раз, и на нём Go-разбор
каталога упал (пункт 6).

**Решение.**

1. **`Handlers.Apeks` стал интерфейсом `apeks.Backend`.** Раньше поле имело конкретный
   тип `*apeks.Client`, и в комментарии было обоснование: единственному потребителю
   второй реализатор не нужен, а тесты проверяют маршрут через `httptest`-сервер
   источника, и с заглушкой исчезла бы проверка «мы реально умеем разбирать ответ вуза».
   Реализатор появился, поэтому интерфейс завели — но список методов остался ровно тем,
   что спрашивает обработчик (`GetGroups`, `GetMonth`, `Endpoint`, `Engine`), и границы
   не сдвинулись: права (`schedule.source.manage`), CSRF, частоту обращений и запись в
   базу держит обработчик, ни один движок про сессию не знает. `httptest`-путь никуда не
   делся — он и есть проверка Go-движка.
2. **Граница — отдельный процесс, а не библиотека.** `internal/apeks/python.go` запускает
   `fetch.py` через `exec.CommandContext(python, script, args...)` без оболочки:
   аргументы не разбирает shell, поэтому путь с пробелом или `;` в значении не способен
   ничего выполнить. Токен передаётся **только** `cmd.Env` — в командной строке его нет,
   потому что её видно в `ps` и она попадает в логи падений дочернего процесса. Выводы
   ограничены (stdout 8 МиБ, stderr 4 КиБ), таймаут 20 с, коды выхода `fetch.py`
   (0 — данные, 1 — источник или разбор не удались, 2 — неверный запуск) превращаются в
   разные ошибки, а текст ошибки вычищается от токена и адреса источника — тот же
   принцип, что в ADR-0015 для HTTP-клиента.
3. **Движок выбирает оператор, а не падение.** `SCHEDULE_SOURCE` принимает `python`
   (по умолчанию — код, присланный владельцем) и `go` (прежний клиент). Автоматический
   откат с одного на другой при ошибке сознательно не сделан: два движка могут разойтись
   в разборе, и молчаливый переход показал бы админу расписание, собранное другим кодом,
   чем тот, что он настроил. Вместо этого выбранное имя пишется в лог старта и отдаётся
   в `engine` из `GET /api/schedule/source/status`, а при ненастроенном источнике поле
   пустое — выдать «go» или «python» там, где пути нет, значит нарисовать рабочий источник
   на странице, где его нет.
4. **`external_id` считается на стороне парсера.** `parser.py` не сохраняет id пары у
   источника, поэтому `fetch.py` считает `py:<sha1 от содержимого строки>` сам. Это
   нужно только дедупликации: `ReplaceMonth` = удаление месяца + upsert, и без
   детерминированного ключа повторный импорт октября плодил бы второй комплект строк
   вместо обновления (проверка «3 строки → 3 строки» в сквозном прогоне).
5. **HTML из полей вырезает Go, а не Python.** Источник кладёт разметку прямо в значения
   (`<i class="fa fa-times"></i> без ауд.`). Парсер отдаёт её как есть — он чужой код и
   менять его поведение без нужды нельзя, — а `stripHTML` в мосту и в Go-движке стоит в
   одном месте перед записью в базу. Страница вставляет текст через `textContent`, так что
   разметка не может стать элементом DOM ни на одном из двух путей; обе проверки —
   «вырезано на импорте» и «не стало элементом DOM» — стоят в сквозном прогоне.
6. **Запасной путь пришлось починить, и это не косметика.** Живой каталог пустые уровни
   дерева отдаёт списком `[]`, а не пустым словарём `{}` (14 узлов из 659). Go-разбор
   ждал `map[string]…` и падал с «каталог групп пришёл в неизвестном формате». Формулировка
   «Go остаётся запасным» была бы ложью, если бы путь был сломан, поэтому добавлены типы
   `nodes` и `named[V any]`: они принимают `{}`, `[]` и `null` как «пусто», и отказываются
   на **непустом** списке — молча проглотить данные, которые не понимают, хуже падения.
   Закреплено срезом живого ответа (`internal/apeks/testdata/apeks-groups-tree.json`,
   значения не выдуманы, токена в файле нет) и тестами на обе стороны формы.
7. **Второй рендер не подключался.** `main.py`, `renderer.py` и `colors.json` лежат в
   папке как пришли и никем не вызываются: `renderer.py` собирает автономную HTML-страницу
   расписания, а страницу `/schedule` строит `web/js/schedule.js`. Переносить его означало
   завести вторую копию вёрстки, расходящуюся с первой, — ровно тот класс дублирования,
   который убрали ADR-0017. `scraper.py` из архива в репозиторий не перенесён вовсе —
   почему, описано в «что это не закрыло».
8. **Секрет из приложенного кода удалён, а не перенесён.** В присланном `api_client.py`
   был `DEFAULT_TOKEN`, вписанный прямо в модуль. Он снят: доступ берётся только из
   `APEKS_TOKEN` (или аргумента), схема HTTPS проверяется при конструировании клиента, а
   не первым запросом, потому что токен едет в строке запроса. **Как именно и на какой
   срок выдаётся токен вуза — по-прежнему вопрос владельцу (`docs/03` B2)**: секрет в
   репозитории пережил бы любой срок жизни токена и попал бы в историю git.
9. **CI получил четвёртую работу, и она офлайн.** `parser` job: `py_compile` по всем
   модулям, `test_parser.py` (тест из архива) и новый `test_contract.py` (17 проверок
   договора CLI с мостом по обеим фикстурам). Сквозная приёмка источника стоит шагом в
   job `ui` и python не требует: дочерним процессом выступает `/bin/sh` с подставным
   парсером `tests/fixtures/schedule-source.sh`. Живой API из CI не дёргается: для этого
   нужен токен вуза в секретах репозитория, а обращение к чужому сайту из чужого CI —
   лишняя нагрузка на источник и ещё один канал утечки. В job `go` отдельно ставится
   `python3`, иначе тест паритета молча пропускался бы, а «зелёный» CI читался бы как
   «движки совпадают».

**Проверено.** `gofmt -l` пусто, `go vet ./...` чисто, `go test -race -count=1 ./...` —
семь пакетов `ok`, 171 верхнеуровневый тест (было 158; `internal/apeks` — 36), ноль `FAIL`.
Два теста паритета прогнаны, не пропущены: `TestPythonParserMatchesGoParser` (пары за
месяц, 22 строки фикстуры; сравниваются все поля, кроме `external_id` — у движков разные
причины ключа, а смысл у обоих «одна строка — один ключ»)
и `TestPythonGroupsMatchGoParser` (каталог, сравнение по сортировке, потому что Go обходит
map). Python-слой: `py_compile`, `test_parser.py`, `test_contract.py` — 17/17. Сквозная
приёмка `bash tests/schedule-source-python.sh` — свой сервер на свободном порту, своя база
в `mktemp`, 21/21: каталог и месяц доехали до базы, публичные маршруты отдали строки гостю,
`/schedule` в jsdom на настоящем `fetch` нарисовал 3 пары на 2 дня, метка «обновлено»
показала имя импортированной группы, повторный импорт не удвоил строки, панель источника
гостю скрыта, пустой месяц различим, к источнику напрямую страница не обращается, и в логе
сервера токена нет. Живым прогоном против `apeks.tksu.ru` (вручную, транзитом через окружение
локального процесса): 587 групп и 98 пар за октябрь у группы 494, наборы строк обоих движков
совпали. Слои, которых правка не касалась, не деградировали: `check-frontend.mjs` код 0,
`npm run test:all` — 8 сьютов и 377 проверок, `npm run test:source` — новый сьют отдельно
(он поднимает собственный сервер, поэтому в `test:all` не входит). Рабочая инстанция владельца
на `:8080` не трогалась.

**Что это не закрыло.**

- **Python на боевом хостинге.** `SCHEDULE_SOURCE=python` теперь означает, что серверу
  нужны `python3` и — для сетевого пути — `requests` из `requirements.txt`. Где именно
  платформа будет запускаться и можно ли там это поставить, не проверялось: выгрузки на
  хостинг нет. Если окажется, что нельзя, работает `SCHEDULE_SOURCE=go`, и именно поэтому
  запасной путь был починен, а не удалён.
- **B2 (токен) остаётся вопросом владельцу**: кто выдаёт доступ, на какой срок, что делать
  при истечении. Пока это одна переменная окружения процессу.
- **Живые обращения к источнику в CI не проверяются** — только разбор по срезам. Формат
  ответа вуза может измениться, и первым об этом узнает оператор импорта, а не прогон.
- **Идемпотентность `external_id` проверена на фикстуре**, а не на живом месяце: если
  источник поменяет содержимое строки (например, аудиторию), это тот же `external_id`?
  Нет — хеш считается по содержимому, поэтому правка строки в источнике даст новую запись
  рядом со старой в том же импорте. Осознанно оставлено как есть: дедупликация по
  содержимому надёжнее порядка строк, а повтор импорта месяца чистит месяц перед записью.
- **`parser.py` не изменён ни в одной строке** — он сверен с архивом владельца
  (`cmp` даёт «файлы идентичны»; так же проверены `main.py`, `renderer.py`,
  `test_parser.py`, `colors.json` и `requirements.txt`). Правки против архива касаются
  только `api_client.py` (снятый `DEFAULT_TOKEN`, HTTPS при конструировании) и того, что
  обход дерева групп вынесен в новый `groups.py`. Если владелец обновит архив,
  `parser.py` заменяется целиком, а договор с мостом держится на `fetch.py`.
- **`scraper.py` из архива в репозиторий не перенесён.** Он открывает виджет
  `rasp-stud.html` в headless-браузере и забирает разметку, то есть второй, резервный
  способ добычи данных там, где платформа ходит в тот же API напрямую. Тащить в продукт
  зависимость от Playwright и Chromium без запроса на это нельзя: она бы не запускалась
  ни в CI, ни на хостинге, а её поведение невозможно проверить офлайном. Нужен этот путь
  — добавляем отдельным решением, с явным согласованием нагрузки на чужую страницу.
- **Панель источника при отсутствующем `python3` подсказывает не то.** `missing_config`
  в `GET /api/schedule/source/status` — константа `"APEKS_TOKEN"`, и текст 503 говорит то
  же: при одном движке другой причины и не было. С двумя движками путь «токен задан, а
  парсер не запускается» стал возможен, и админ в этом случае увидит совет завести токен,
  который уже заведён. Точная причина лежит рядом — в логе старта (`engine` + `hint` про
  `SCHEDULE_PARSER`/`PYTHON_BIN`/`SCHEDULE_SOURCE=go`), поэтому это не опасность, а
  недосказанность панели. Правка на две строки (подсказка из состояния сервера, а не
  из константы) сознательно не сделана в этом коммите: он и так меняет границу, а
  менять тексты админской панели надо проверкой, а не «попутно». Занесено в `docs/04`
  отдельной внеочередной позицией.
  **(Снято ADR-0023, `b28a036`: причина «источника нет» стала состоянием сборки —
  `newScheduleSourceClient` возвращает имя виноватой переменной и готовую подсказку, и один
  и тот же текст читают панель, 503 и `audit_detail`; проверено живьём при
  `PYTHON_BIN=/no/such/python3` и закреплено девятью новыми прогонами Go и тремя jsdom.)**

## ADR-0022. Живая приёмка фокуса дошла до открытых модалок — и нашла форму, в которую фокус не входил

Статус: принята агентом 3 (фронтенд) как снятие второго пункта «что это не закрыло» ADR-0020.
Реализовано в `86edfe9`, документация — в коммите сразу за ним (этот файл). Продуктовый код
затронут ровно в одном месте: `web/js/modals.js` — 13 добавленных строк, и из них две правки
(`input` без `type="hidden"` в списке кандидатов и страховка в `open()`), остальное — комментарий;
всё остальное в коммите — инструмент проверки.

**Контекст.** ADR-0020 замерял только то, что отрисовано при загрузке страницы, и сам записал
это как остаток: «`#modalDialog` живёт в закрытом диалоге, его кольцо проверяет только
статика, картинка не снята; ловушку фокуса в модалке и поныне держит только jsdom». Модальное
окно устроено так, что ни один из трёх имеющихся слоёв его не видит целиком. Статика
(`check-frontend.mjs`, группа 9) читает CSS и знает, что правило `#modalDialog:focus-visible`
и кольца `.control:focus` существуют и посчитаны против трёх подложек страницы, — но не знает,
откроется ли диалог и что лежит под его полем внутри окна (тень оверлея, `overflow: auto` у
`.modal-content`). `tests/ui/accessibility.cjs` и `assignments-modal.cjs` работают в jsdom:
layout там не считается, `box-shadow` как картинки не существует. Риск при этом не теоретический:
диалог — самое плотное по фокусируемым элементам место кабинета (две формы, список, таблица
сдач с полями оценки), и ровно в нём ADR-0020 нашёл бы второе «невидимое кольцо», если бы оно
было.

**Решение.**

1. **Не новый скрипт, а тот же `scripts/check-focus.mjs` (671 → 891 строка).** Двухпроходный
   обход вынесен из `checkPage` в `runPasses(cdp, label, selector, opts)`: страница и диалог
   проходят один и тот же код и потому дают одинаковые коды выхода, одинаковый отчёт и одинаковые
   пороги. Две копии обхода разошлись бы ровно там, где расходятся детали — на сбросе прокрутки
   и на повторе потерянного нажатия.
2. **Селектор ограничен `#modalDialog`.** За модалкой остаётся живая страница: без ограничения
   обход посчитал бы её элементы недоступными и падал бы с ложной находкой «Tab не доходит».
   Признаки те же, что на странице (`a[href]`, `button`, `input:not([type="hidden"])`, `select`,
   `textarea`, `summary`, `[contenteditable]`), префикс — только область.
3. **Геометрия берётся в координатах вьюпорта.** Оверлей прибит к окну (`position: fixed`), а
   снимок области задаётся в координатах документа, поэтому `FOCUS_DIALOG_JS` вызывает
   `window.scrollTo(0, 0)` до и после `focus()` — иначе кадр уезжал бы по фону каждый раз, когда
   диалог сам прокручивает содержимое к полю.
4. **У диалога проверяется ловушка, а не порядок DOM.** Точка входа у ловушки другая — кнопка
   закрытия, а не первый элемент разметки, — поэтому сверка «порядок Tab = порядок DOM» для
   модалки выключена (`assertOrder` только у страниц), а вместо неё включена `trap`: если фокус
   ушёл за пределы диалога (в том числе на элемент страницы под оверлеем — после сброса меток
   он не имеет `data-fp` и читается как `null`), это FAIL «ловушка фокуса не держит».
5. **Диалог открывается настоящими кликами по настоящим кнопкам.** Пять состояний на
   `/dashboard` описаны цепочкой `steps`: список заданий студента → форма сдачи, управление
   заданиями преподавателя → форма нового задания, → таблица сдач. Ничего не отправляется:
   кнопка «сохранить» только фокусируется и замеряется, поэтому прогон не создаёт и не меняет
   данных и не тратит бюджет лимитера на POST'ы кроме входов.
6. **«Фокус после открытия не уехал в диалог» — отдельная находка (NOTE, не FAIL).** Формально
   это не 2.4.7: кольцо у элементов видно. Но без этой строки правка, описанная в пункте «находка»
   ниже, осталась бы невидимой для приёмки, а judging строку как провал проект не имеет права —
   требование «фокус при открытии уходит в диалог» нигде не заявлен.
7. **Флаги `--no-modals` и поведение `--page=/dashboard`.** Диалоги живут на одной странице,
   поэтому `--page=/register` честно печатает «модалки пропущены», а не молча измеряет половину
   набора; метки прошлого обхода сбрасываются перед каждым прогоном, иначе замер по индексу #0
   взял бы элемент со страницы, а не из окна.

**Находка живого прогона — и это не кольцо.** У `submit-work` и `create-assignment` диалог
открыт, а `document.activeElement` остаётся `<body>`. Обе формы начинаются скрытым полем
(`assignment_id` в `modals.js:269`, `course_id` в `modals.js:284`), оно находилось первым по
списку `FOCUSABLE`, а `focus()` на `input[type="hidden"]` не перемещает фокус никуда. Значит
человек, открывший форму с клавиатуры, получал окно, которого он не видел: первый Tab шёл по
странице за оверлеем, а не по полям формы. Правка в `web/js/modals.js`: скрытые поля исключены
из кандидатов на вход, и добавлена страховка — если ни один кандидат фокус не принял,
`ModalManager` заходит в `#modalDialog` сам (у него есть `tabindex="-1"`, `web/dashboard.html:109`, и своё
кольцо, `web/css/style.css:409`). Ни один прежний слой этого увидеть не мог: `accessibility.cjs`
наполняет диалог двумя кнопками — первая фокусируется, и проверка «фокус ушёл внутрь диалога»
зелёная, — а `assignments-modal.cjs` проверяет список заданий и факт открытия формы, но не то,
куда в ней оседает фокус.

**Проверено на этом дереве.** Полный прогон на отдельном сервере `127.0.0.1:8178` (свежая база
`/tmp/sos-modal.db`, сид и headless-оболочка Chromium из кэша Playwright, профиль в `mkdtemp`):
8 страниц и 5 состояний диалога, **91 фокусируемый элемент — 77 на страницах и 14 внутри
окон, до всех доходит Tab, `:focus-visible` совпал на всех, ловушка держит в пяти случаях из
пяти, невидимых колец 0, замечаний 18, код выхода 0**. Из 18 замечаний 14 на страницах и 4
внутри диалогов — тот же класс, что и раньше: кольцо видно, но переход «до → после» составляет
~1,9:1 (WCAG 2.2 SC 2.4.13, проектом заявлен 2.1 AA). Полный обход повторён на второй чистой
базе (`/tmp/sos-modal2.db`, сервер `:8178`) — те же 91 замер, 77 на страницах, 14 внутри окон,
18 замечаний, 0 невидимых, ловушка 5 из 5, код 0, и `--no-modals` на ней даёт ровно 77 — то
есть «14 внутри окон» из этих цифр не зависит от того, что страница успела накопить.
Контрольный прогон `--page=/dashboard` после правки `modals.js` на чистой базе: 24 замера
(10 на странице и 14 в окнах), 4 замечания — все внутри диалогов, 0 невидимых, обе NOTE про
невъехавший фокус исчезли.
Остальные слои не деградировали: `node --check` по обоим файлам, `node scripts/check-frontend.mjs`
— код 0 (45 строк `ok`, включая группу 9 и покрытие контраста), `npm run test:all` — **8 сьютов и
377 проверок, 0 падений** (повторено на третьей чистой базе `/tmp/sos-modal3.db`; в их числе
`accessibility.cjs` 112 и `assignments-modal.cjs` 24, которые и проверяют поведение модалок в DOM),
`go test -race -count=1 ./...` — семь пакетов `ok`,
`bash tests/schedule-source-python.sh` — 21/21. Тот же прогон два раза подряд на одной базе
даёт `FAIL новый пароль работает` в `account-security.cjs` — это не регрессия, а бюджет
лимитера входов (ADR-0006), и он же причина, почему и `test:all`, и живой обход требуют
свежую базу. Сервер остановлен, временные база, логи и
скриншоты удалены; рабочая инстанция на `:8080` не тронута, браузер пользователя тоже.

**Что это не закрыло.**
- **В CI шага по-прежнему нет**, и причин не изменилось: на раннере GitHub Actions нет браузера,
  а смысл проверки — отрисовка. В `ci.yml` попадает только статическая группа 9. Регулярность
  прогона держится текстом этого ADR и абзацем в README, а не красным CI.
- **Покрыто пять состояний, а не «все модалки».** Набор `MODALS` — список, и ничто, кроме этого
  текста, не заставит добавить в него новый вид содержимого, когда `modals.js` его получит.
  Правильный триггер: появился новый `data-modal-action`, открывающий диалог — появился и случай.
- **Возврат фокуса в кнопку-открыватель живым браузером не замеряется.** Это ищут статика и
  jsdom (`accessibility.cjs`, проверка после Escape), картинка — только кольца внутри окна и
  замкнутость Tab.
- **Один вьюпорт, одна плотность, один движок** — как в ADR-0020: Safari/Firefox рисуют
  `box-shadow`-кольца иначе, при 200% увеличении и на 320 px ничего не измерялось.
- **Число фокусируемых элементов зависит от данных прогона.** `12` против `10` на `/dashboard`
  между двумя прогонами — это лишние кнопки от работ и сдач, созданных сюжетными тестами ранее.
  Цифры в документах — снимок конкретного прогона, а не константа; константа — «0 недоступных,
  0 невидимых, ловушка держит».
- Скринридер остаётся последним открытым пунктом доступности со времён ADR-0016, и он требует
  человека с NVDA/VoiceOver, а не машины разработки.

## ADR-0023. Вне очереди: панель источника называет настоящую причину — «источника нет» перестало быть синонимом пустого токена

Статус: принята агентом 2 (бэкенд) как снятие последней названной внеочередной позиции `docs/04`,
найденной ADR-0021. Реализовано в `b28a036`, документация — в коммите сразу за ним (этот файл).
Продуктовый код затронут в четырёх местах: `cmd/server/main.go` (причина собирается вместе с
клиентом), `internal/handlers/handlers.go` (два новых поля `Deps`),
`internal/handlers/schedule_source.go` (статус, текст 503 и `audit_detail` читают её),
`web/js/schedule.js` (панель печатает `hint`); всё остальное в коммите — проверки.

**Контекст.** ADR-0015 оставила в статусе источника одно имя: `missing_config` в
`GET /api/schedule/source/status` был строковой константой `"APEKS_TOKEN"`, и отказ 503 говорил то
же. Тогда это было верно по построению: клиент собирался из одной переменной, и «источника нет»
не могло значить ничего другого. ADR-0021 добавила второй движок — `SCHEDULE_SOURCE=python`
разбирает ответ приложенным парсером, — и вместе с ним три новых способа остаться без импорта:
нет интерпретатора (`PYTHON_BIN`), нет скрипта (`SCHEDULE_PARSER`), адрес не разбился или не по
HTTPS (`APEKS_API_URL`), значение движка написано с опечаткой (`SCHEDULE_SOURCE`). Записана эта
находка была отдельной позицией в `docs/04`, потому что правка меняет текст, который читает
человек, и требует проверки, а не «попутно» со сменой границы процесса.

Как это выглядело для оператора: на хостинге без `python3` при заданном токене страница показывает
«Источник не настроен: на сервере не задан APEKS_TOKEN», админ смотрит окружение, видит токен,
заводит его заново и получает ту же строку. Настоящая причина в этот момент существовала ровно в
одном месте — в логе старта (`engine` + `hint` про `PYTHON_BIN`/`SCHEDULE_PARSER`), до панели и
до отказа она не доходила. То есть данные у сервера были, не хватало одного провода.

**Решение.**

1. **Причина — состояние сборки, а не догадка обработчика.** `newScheduleSourceClient` возвращает
   теперь `(apeks.Backend, sourceProblem{missing, hint})`, пара кладётся в `handlers.Deps`
   (`ScheduleSourceMissing`, `ScheduleSourceHint`). Обработчик окружение не читает: единственное
   место, где переменные источника интерпретируются, остаётся `cmd/server`, и панель показывает
   ровно то решение, которое ядро приняло при старте.
2. **Имя переменной вместо текста ошибки.** В ответ уходят `missing_config` (короткое имя) и
   `hint` (готовая фраза из исходника). Сообщение `apeks.ErrParserUnavailable` не копируется: в
   нём абсолютные пути процесса — к `fetch.py` и к интерпретатору, — а браузеру они не нужны (тот
   же принцип, что с токеном в ADR-0015: в панель не уходит ничего, что можно прочитать как адрес
   или секрет чужого сайта).
3. **Значение оператора не подставляется.** При `SCHEDULE_SOURCE=apex` панель читает «принимает
   только python или go», а не echo строки из окружения. Формально `sourceHint` пишется через
   `textContent`, но держать в ответах свободные строки окружения — привычка, которая переживёт
   одну аккуратную панель; правило зафиксировано тестом, а не комментарием.
4. **Пустое поле = прежний текст.** Пустые поля `Deps` означают «причину не передали» — так собирают
   тесты и любая чужая сборка, и тогда включается прежняя формулировка про `APEKS_TOKEN`. Обратная
   совместимость сохранена бесплатно: ни один существующий тест не переписан, и
   `schedule-timetable.cjs` со старым кейсом остался зелёным.
5. **Один текст на три места.** Панель (200), отказ 503 и `audit_detail` (`…reason=not_configured
   missing=PYTHON_BIN`) берут значение из одного поля. Журнал — не украшение: к истории отказа
   админ возвращается, когда панель уже закрыта, и событие с причиной `not_configured` без имени
   переменной привело бы его обратно к ложному следу.
6. **Поднявшийся источник подсказки не имеет.** `scheduleSourceHint` возвращает пустую строку при
   `h.Apeks != nil`: «причина, по которой импорта нет» при живом клиенте — это уже не про
   конфигурацию, и показывать её значило бы оставить висящий текст после удачного старта.

**Почему не иначе.**
- *Пусть панель сама решает по `engine`.* `engine` говорит, кто разбирал данные, и пуст при
  отсутствии клиента, — из него нельзя вывести, чего не хватает в окружении.
- *Пусть обработчик читает `os.Getenv`.* Причину пришлось бы пересобирать по тем же правилам во
  втором месте, и первое же расхождение логики («python по умолчанию» в одном файле и «go» в
  другом) дало бы панели текст, которого нет в логе старта.
- *Пусть панель молчит, а причина остаётся в логе.* Вариант был принят ADR-0021 как временный и
  проиграл живой проверке: совет завести уже заведённый токен хуже отсутствия совета, потому что
  админ ему верит и начинает диагностику не с того конца.

**Проверено на этом дереве.**
- Слои не деградировали: `gofmt -l` пусто, `go vet ./...` чисто, `go test -race -count=1 ./...` —
  семь пакетов `ok`, **245 прогонов `=== RUN`** (было 234); `node --check`, `check-frontend.mjs` —
  код 0 и 45 строк `ok`; `npm run test:all` — **8 сьютов и 380 проверок** при 0 падений (было
  377); приёмка источника `tests/schedule-source-python.sh` — 21/21 с «в логе токена нет»; живой
  замер фокуса — 91 замер, 73 с видимым индикатором, 18 замечаний SC 2.4.13, 0 невидимых колец,
  код 0 (правка добавляет только текст в `#sourceHint`, новых фокусируемых элементов нет).
- Новый `cmd/server/schedule_source_test.go` — таблица из семи подслучаев выбора причины по
  окружению плюс тест на соответствие движка: пустой токен → `APEKS_TOKEN`; токен + отсутствующий
  `PYTHON_BIN` → `PYTHON_BIN` и подсказка про запасной `SCHEDULE_SOURCE=go`; токен + http-адрес →
  `APEKS_API_URL`; токен + `SCHEDULE_SOURCE=go` с http-адресом → `APEKS_API_URL` с пометкой
  движка; опечатка в движке → `SCHEDULE_SOURCE`; две ветки «источник поднялся» → пустая причина.
  Живой `python3` не требуется: `PYTHON_BIN` указывает на заглушку из `t.TempDir()`, и тест
  проходит одинаково на машине с интерпретатором и без него. Отдельно закреплено, что в `hint` и
  `missing_config` не появляются значение токена, абсолютный путь парсера и строка оператора.
- Два новых теста в `internal/handlers`: одна и та же причина доезжает до статуса и до 503 одним
  текстом (`missing_config: "PYTHON_BIN"`, 503 без «задайте APEKS_TOKEN»), `hint` пуст при
  поднявшемся источнике; плюс проверка `missing=PYTHON_BIN` в `audit_detail` и прежнего
  `missing=APEKS_TOKEN` там, где причину не передали.
- `tests/ui/schedule-timetable.cjs`: при `configured: false` с `hint` панель печатает подсказку
  сервера и не печатает «не задан APEKS_TOKEN», цифры и обещание чтения импортированного остаются;
  прежний кейс («ненастроенный источник назван переменной») зелёным не перекрашен.
- Живая проверка на отдельном стеке (`127.0.0.1:8180`, своя база и сид, `LOG_LEVEL=info`; ранее
  поднятый локальный инстанс на `:8080` и браузер пользователя не тронуты) при заданном `APEKS_TOKEN` и
  `PYTHON_BIN=/no/such/python3`: статус — `configured: false`, `missing_config: "PYTHON_BIN"`,
  `engine: ""`, `hint` про запасной путь; импорт — `503` с текстом «источник расписания не
  настроен: токен APEKS_TOKEN задан, но парсер расписания не запускается: проверьте PYTHON_BIN …
  запасной путь без python — SCHEDULE_SOURCE=go»; в журнале читается
  `source=apeks reason=not_configured missing=PYTHON_BIN`; греп значения токена по логу и ответам —
  0 совпадений. Сервер остановлен, временные база, логи, бинарник и cookie-журналы удалены, порты
  `:8179`/`:8180` свободны.

**Поправка к ADR-0023 (`4e22b33`, тот же день, нашёл чистый клон).** Проверка «работает ли то,
что написано
в README, если начать с пустого репозитория» — `git clone` этой ветки, `go build`, запуск с
`ADMIN_USERNAME`/`ADMIN_PASSWORD` и заданным `APEKS_TOKEN` — показала ответ админского статуса
вида `{"configured": true, "engine": "python", "missing_config": "APEKS_TOKEN", "hint": ""}`.
Первое поле противоречит третьему: `missing_config` означает «какая переменная отсутствует», и
при поднявшемся источнике отсутствует ничего. Панель этого не показывала (она читает поле только
при `configured: false`) — поэтому и unit-тесты, и jsdom-кейс поле в этом сочетании не сверяли:
`internal/apeks`-заглушки в тестах собирают Deps с причиной, а живой прогон с собранной причиной
никто не делал. Исправлено по симметрии с `hint`: `scheduleSourceMissing` возвращает пустую
строку при `h.Apeks != nil`, прежний fallback остался только для случая «причину не передали»,
который возможен лишь когда источника нет. Тест `TestScheduleStatusHintSilentWhenSourceWorks`
проверяет теперь оба варианта: Deps заполнены ошибочно и Deps пусты (так собирает `cmd/server`,
когда клиент поднялся) — в обоих `missing_config` и `hint` пустые при `configured: true`.

Попутно та же живая проверка вскрыла гонку в сьюте журнала (`8a73426`): `admin.js` после смены роли сам
перезагружает панель (`loadAudit`), и на время запроса в `#auditBody` лежит заглушка «Загрузка
журнала…», а `admin-roles.cjs` читал таблицу сразу после сверки роли — две проверки
(«действия по-русски», «итог показан чипом») падали не всегда. Сьют ждёт законченного состояния
панели с тем же потолком, что и клик «обновить»; продуктовый код не тронут, потому что
перезагрузка журнала после действия намеренная (админ обязан видеть запись сразу).

Цифры прогона на дереве с поправкой те же, что и до неё: семь пакетов `ok`, 245 прогонов
`=== RUN` (новые проверки добавлены в существующий тест, поэтому счётчик не вырос), 8 сьютов и
380 проверок при коде 0, `check-frontend.mjs` — 45 строк `ok` и код 0, приёмка источника — 21/21,
живой замер фокуса — 91/73/18/0. Стеки — `:8183`…`:8190` со своими базами в `/tmp` (последний
`test:all` — уже на дереве с обеими правками); клон удалён,
порты свободны, поднятый ранее инстанс на `:8080` не тронут.

`2b4a685` закрыл то, из-за чего вся поправка и случилась: правило «`missing_config` называется
ровно тогда, когда источника нет» перестало быть выводом из четырёх отдельных тестов и стало
одним `TestScheduleStatusFieldsAgreeInEveryState` на четыре сборки состояния (клиент поднят при
пустых Deps, клиент поднят при заполненных, клиента нет с причиной, клиента нет без причины).
Инвариант проверен подстановкой: без защиты `h.Apeks != nil` тест падает на обеих ветках
«источник собран». Счётчик прогонов вырос до 250 (176 верхнего уровня + 74 подтеста);
продуктовый код правка не тронула, поэтому jsdom-слой, приёмка источника и замер фокуса не
пересобирались.

**Что это не закрыло.**
- **Живого обращения к `apeks.tksu.ru` из CI по-прежнему нет** — тесты идут через `httptest` и
  заглушки `PYTHON_BIN`, поэтому отказ вида «источник не принял живой токен» панель объяснить не
  может: это тот же открытый пункт, что у ADR-0015 и ADR-0021.
- **`python3` и `requests` на боевом хостинге** (`docs/03` B2) правка не установила — теперь о них
  хотя бы говорится прямо. Ответ владельца про хостинг по-прежнему нужен.
- **Причина вычисляется один раз при старте.** Если оператор поправит окружение без перезапуска,
  панель продолжит показывать старую причину — как и всё остальное, что `newScheduleSourceClient`
  читает один раз (ADR-0021, пункт про `SCHEDULE_SOURCE`). Это следствие выбранного места
  решения, а не упущение: второй путь — читать окружение на каждый запрос — вернул бы расхождение
  с логом старта.
- **Текст подсказки — одна строка в `textContent`.** Отдельной разметки под длинную подсказку
  (перенос по пунктам, ссылка на `tools/schedule-parser/README.md`) не делалось: панель умещает
  её как есть, и проверка держит только содержание.
- **Новые причины добавляются вручную.** `sourceProblem` заполняется в ветках `switch`, и следующий
  движок — или новая проверка внутри `apeks.NewPython` — обязан принести свою ветку, иначе получит
  дефолт ветки python (`APEKS_API_URL`). Триггер: появился новый текст ошибки в мосту — появился и
  `case` с именем переменной.

## ADR-0024. Состояния источника проверяются живым сервером: ручной прогон, нашедший поправку, стал слоем

Статус: принята агентом 2 (бэкенд) как закрытие способа, которым была найдена поправка к
ADR-0023, а не только её вывода. Реализовано в `a1e5fa6`, документация — в коммите сразу за ним
(этот файл). Продуктовый код коммит не тронул: `git diff` по `cmd/server` и `internal/` на этом
дереве пуст.

**Контекст.** Противоречие `configured: true` + `missing_config: "APEKS_TOKEN"` (`4e22b33`) нашёл
не тест, а человек: был клон репозитория, собранный сервер и окружение без `python3`. Тот же удел
был у ADR-0020 и ADR-0022 — приёмка фокуса, которую нельзя было подключить к CI, потому что на
раннере нет браузера; она осталась ручным шагом, записанным текстом.
Здесь ситуация обратная: всё, что нужно для прогона, есть и на раннере, и на машине разработки
(бинарник, `node`, `curl`), — а ручным слой оставался только потому, что никто не написал скрипт.

После `2b4a685` могло казаться, что зазора больше нет: инвариант полей статуса проверяется одним
тестом на четыре сборки состояния. Но проверяется он в `internal/handlers`, где Deps собирает тест,
а `cmd/server/schedule_source_test.go` проверяет `newScheduleSourceClient` — перевод окружения в
причину. Между ними лежит ровно один провод, `main.go:141-142` (`ScheduleSourceMissing`,
`ScheduleSourceHint` из `apeksProblem`), и его не проверял ни один тест: тесты обработчика задают
эти поля руками, а тест сборки клиента до `handlers.Deps` не доходит.

**Решение.**

1. **Новый слой, а не ещё один тест в `cmd/server`.** `tests/source-states-smoke.sh` (229 строк)
   поднимает собранный сервер шесть раз с разным окружением и спрашивает статус по HTTP. Смысл
   слоя именно в процессе: он проверяет проводку `main.go` и ответ живого транспорта, а не
   поведение функции.
2. **Состояния перечислены по сборке, а не по полям.** Шесть прогонов накрывают все имена
   переменных, которые возвращает `newScheduleSourceClient` (нет токена; парсер не запускается —
   `PYTHON_BIN`; адрес не разбился или не по HTTPS — `APEKS_API_URL`; значение движка с опечаткой —
   `SCHEDULE_SOURCE`), плюс оба поднявшихся движка: `go` и `python`. К ним — седьмой прогон на
   отказ импорта: тот же код состояния должен называть ту же переменную в панели, в тексте 503 и в
   записи журнала.
3. **Подсказка сверяется подстрокой, а не целиком.** Текст `hint` — фраза для человека, и правка
   формулировки не должна ронять CI; проверяется, что названа настоящая переменная. При поднявшемся
   источнике ожидание строгое: `hint` обязан быть пустым.
4. **Отрицательное утверждение встроено в каждый прогон.** Если токен задан, ни панель, ни отказ
   не могут советовать «задайте APEKS_TOKEN» — это ровно тот ложный след, из-за которого ADR-0023
   затевался; и значение одноразового токена ищется во всех логах и ответах прогона.
5. **Живого источника слой не касается.** Состояние «парсер есть» собирается на подставном
   `tests/fixtures/schedule-source.sh` с `PYTHON_BIN=/bin/sh`, как в приёмке источника; адрес
   источника в рабочих состояниях — дефолт `apeks.tksu.ru`, но ни один запрос к нему не
   отправляется: проверяется конфигурация, а не ответ вуза.
6. **Шаг подключён к CI в job `ui`** следом за приёмкой источника, плюс алиас
   `npm run test:source-states`. Порт — первый свободный из 8220-8249, база своя на каждый прогон;
   входов в лимитер (ADR-0006) слой тратит семь — по одному на сервер.

**Проверено подстановкой — и это главное в этом ADR.** Два бага, найденных до этого слоя,
воспроизведены намеренно:

- убрана защита `h.Apeks != nil` в `scheduleSourceMissing` → слой падает **36/38** ровно на двух
  состояниях «источник поднялся» (`ожидалось «», получилось «APEKS_TOKEN»`);
- обрезан провод `main.go:141-142` (в Deps уходят пустые строки вместо `apeksProblem`) →
  **`go test -race -count=1 ./...` остаётся зелёным: семь пакетов `ok`, ноль `FAIL`** (250 прогонов
  вместе с тестом инварианта и тестом сборки клиента), а слой падает **29/38**: три состояния с
  неправильной переменной, пустые подсказки, текст 503 «задайте APEKS_TOKEN на сервере» при
  заданном токене и запись журнала `missing=APEKS_TOKEN` вместо `missing=PYTHON_BIN`.

То есть слой закрывает именно тот сегмент, который не закрывал никто, — это измерено, а не
предположение. Оба эксперимента сняты, `git diff` по продуктовому коду пуст.

Зелёный прогон на дереве с правкой: **38/38**, 16 секунд; он же через `npm run test:source-states`.
Остальные слои перезапускались на этом же дереве, и документация к этому коммиту их тоже
захватывает: `gofmt -l` пусто, `go vet ./...` чисто, `go test -race -count=1 ./...` — **семь
пакетов `ok`, 250 прогонов `=== RUN`, 0 падений и 0 пропусков**, `node scripts/check-frontend.mjs`
— 45 строк `ok` и код 0, `npm run test:all` — **8 сьютов и 380 проверок при 0 падений** (свежий
стек `:8252` со своей базой и сидом, код выхода 0), приёмка источника
`bash tests/schedule-source-python.sh` — **21/21** с «в логе токена нет». Живой замер фокуса не
перезапускался: продуктовый CSS, JS и разметка со времён `a242dcf` не менялись, а его последние
цифры на этом коде — 91/73/18/0. Серверы прогонов остановлены, базы, логи и бинарники удалены,
порты 8220-8249 и 8251-8252 свободны, инстанс на `:8080` и браузер владельца не тронуты.
Не проверялось: сам прогон CI на GitHub — шаг `source-states-smoke` там ещё не выполнялся.

**Что это не закрыло.**
- **Живого `apeks.tksu.ru` слой не видит** — он проверяет конфигурацию и ответ панели, а не то, что
  источник принял токен. Открытый пункт ADR-0015 и ADR-0021 остаётся в силе.
- **Покрыто шесть сборок, а не всё окружение процесса.** Переменные, которые читают другие ветки
  (`DB_PATH`, `TRUST_PROXY`, `SESSION_*`), слоем не проверяются. Триггер для расширения: у
  `newScheduleSourceClient` появилась новая ветка возврата `sourceProblem` — появился и прогон.
- **Слой не проверяет панель глазами.** `hint` читается из JSON; как именно его печатает
  `web/js/schedule.js` — дело `schedule-timetable.cjs` в jsdom, а не этого прогона.
- **Порты и лимитер** — общая машина: если диапазон 8220-8249 занят, прогон честно падает с
  сообщением, а не ждёт свободного порта.

## ADR-0025. Документация сверяется с деревом скриптом: пути, координаты строк, хеши, объёмы и команды

Статус: принята агентом 2 (бэкенд) как закрытие класса ошибок, который до этого ловился только
глазом и только по случайности. Скрипт, шаг CI и правки документации — один коммит, и этот файл
входит в него; собственный хеш он назовёт только в следующем заходе, что по правилу самого
скрипта не проблема: сверяются хеши уже существующих коммитов. Продуктовый код не тронут:
`git diff` по cmd/server, internal и web на этом дереве пуст.

**Контекст.** Документация — самый правимый артефакт репозитория: восемь markdown-файлов,
менявшихся за Этап 2.5 десятки раз, и ни одной проверки ни в одном слое. Три находки, из-за
которых затея родилась, — это уже жившие в docs ошибки, а не теоретический риск:

1. **Файл, которого никогда не было.** Со времён ADR-0003 (`fcfc6c9`, `2f68b4e`) README ссылался на
   apierror_test.go в пакете internal/apierror. `git show --stat fcfc6c9` и `git show --stat
   2f68b4e` называют `internal/handlers/errors_test.go` — семь тестов; у пакета internal/apierror
   тест-файла нет вовсе: конверт там собирается, а проверяется со стороны обработчика. Формулировка
   README исправлена этим же коммитом.
2. **Координаты, ведущие не туда.** В `docs/01-STATE-REPORT.md` двенадцать ссылок аудита были
   записаны голым именем файла вместе с номером строки — `courses.go`, `submissions.go`,
   `enrollments.go`, `assignments.go`, `resources.go`, `events.go`, — а под каждым таким именем в
   дереве попадают два файла: например `internal/handlers/courses.go` и `internal/store/courses.go`.
   Читатель, шедший по строке 38, мог открыться в слое доступа к
   данным, где этого решения нет. Выбор слоя сделан не по догадке: `git show 0eb89bd^1` по каждой
   координате показал, что все двенадцать — из internal/handlers.
3. **Объёмы, устаревшие на несколько строк.** `web/js/core/api-client.js` 252 против 263 в дереве,
   `web/404.html` 70 против 72, `web/profile.html` 126 против 131 ещё в трёх местах
   (`docs/01` ×2, `docs/02` ×1).

По пути к этому же слою возник и четвёртый, более скучный класс: в `docs/04` и `docs/05` номера
коммитов пишутся каждый день, и опечатка в семи символах выглядит правдоподобно.

**Решение.** `scripts/check-docs.mjs` (365 строк) — пятая статическая проверка репозитория и
первая, которая читает документацию. Пять групп, от простого к хрупкому:

1. **Пути.** Каждая ссылка вида «файл с расширением» в кавычках-бэктиках обязана резолвиться в
   файл дерева (каталог `web/` — для ссылок, начинающихся с `/`, они про сайт). Голое имя с
   номером строки отдельно отвергается, если ведёт к двум файлам: с координатой нужен путь с
   каталогом — ровно та форма, которая спасала читателя docs/01.
2. **Номера строк.** `internal/handlers/auth.go:35-45` обязан попасть внутрь файла; диапазон и
   список через запятую разбираются.
3. **Хеши.** Любой бэктик-спан из 7–40 шестнадцатеричных символов проверяется через
   `git cat-file -e …^{commit}`. В shallow-клоне группы нет (объектовHistory отсутствует), и
   скрипт честно печатает «ГРУППА ПРОПУЩЕНА» вместо молчаливого нуля — поэтому `ci.yml` получил
   `fetch-depth: 0`.
4. **Заявления об объёме** («N строк» в скобках) сверяются с длиной файла по семантике `wc -l` —
   число переводов строк, а не `split('\n').length`, расхождение на единицу это ловит. Группа
   действует только на README, `docs/01` и `docs/02`, то есть на тексты про состояние «сейчас».
   `docs/04` и `docs/05` — журналы: их цифры суть снимки на день работы, и «освежить их до
   текущих» значило бы переписать историю задним числом. Группы 1–3 и 5 на них действуют
   по-прежнему.
5. **Команды.** Каждое `npm run …` обязано существовать в `tests/ui/package.json`.

Освобождения — те же правила, что выведены в ADR-0019 (контраст) и ADR-0020 (фокус): каждое
подписано причиной и ссылается на пункт docs, а неиспользованное освобождение роняет проверку,
чтобы таблица не превращалась в свалку. Их семнадцать: 12 путей (архивный `scraper.py`, позиции
целевой схемы `csrf.js` и `dom.js`, планируемые workflow и compose-файлы, пример имени модуля,
структура выкладки Pages, внешняя страница вуза `rasp-stud.html`), 3 исторических координаты в
`dashboard.js` (состояние до ADR-0017 и до `8fef933`), 2 объёма (671 строка `scripts/check-focus.mjs`
в день ADR-0020 и 34 строки удалённой разметки в описании диффа T3.1), 1 хеш-маркер `99999999` и
1 команда `npm run lint` из целевого описания CI (§10 docs/02).

Отдельно — стражи вырождения: пороги по числу найденных ссылок каждой группы (150/20/50/5/20) и
минимум восемь распознанных документов. Без них сломанный regex даёт «0 ссылок, все ок», и CI
выглядит зелёным ровно в тот момент, когда проверка перестала что-то видеть. Это не теоретика:
первая версия разбора давала 153 ложных находки — в список расширений попал `c` (всякий
`style.c`), а без границ токена `*_test.go` давал файл `_test.go`, `/module.go` — файл `module.go`
в несуществующем каталоге, а GS.can и GS.sh — свойства объекта `GS`, а не файлы `can` и `sh`.
Второй ловушкой стал `\b`:
в JavaScript он определён через `[A-Za-z0-9_]`, поэтому после кириллического «строк» границы нет
никогда — группа 4 молча не находила ни одного заявления, пока не упёрлась в собственный порог
вырождения.

**Проверено подстановкой.** В документацию намеренно внедрено шесть дефектов — несуществующий
путь, координата за концом файла, хеш коммита, которого нет, заявленный объём 999 строк у
smoke-скрипта, npm-скрипт, которого нет, и освобождение, которое стало мёртвым. Прогон: **6 FAIL,
код выхода 1**, каждый с внятной строкой — вторая находка, например, напечатала «в
cmd/server/main.go 482 строк, а ссылка на 99999». После восстановления из резервных копий —
зелёный прогон, `git diff` по markdown пуст.
Зелёный прогон на этом дереве: **1105** файловых ссылок (144 уникальных пути), **114** координат
строк (3 освобождённых), **472** хеша, **17** заявлений об объёме, **73** упоминания `npm run` при
11 скриптах в `package.json`.

Слои, перезапущенные на этом дереве: `gofmt -l` пусто, `go vet ./...` чисто,
`node scripts/check-frontend.mjs` — код 0, `node scripts/check-docs.mjs` — код 0. `go test -race
-count=1 ./...` переснят перед этим коммитом и даёт семь пакетов `ok` при 250 прогонах `=== RUN`
(число не сдвинулось: продуктовый код не тронут). `npm run test:all` и шелловые слои не
перезапускались: правка не трогает ни JS, ни разметку, ни `cmd/server`, а их последние цифры на
неизменном коде — 380/380 и 21/21 с 38/38. Живой замер фокуса (`scripts/check-focus.mjs`) тоже не
перезапускался — вне CI, требует браузера, последние 91/73/18/0.

**Что это не закрыло.**
- **Координата сверяется с длиной файла, а не с содержимым строки.** `main.go:81` пройдёт, даже
  если на 81-й строке давно другой код: переезд функции внутрь файла не виден. Подъём до
  «строка содержит то, про что написано» — отдельное решение, и оно требует слов-маркеров в
  цитатах документации, которых сейчас нет.
- **Документ может остаться верным и вводять в заблуждение.** Скрипт проверяет ссылки, а не
  утверждения: «тест проверяет X» он не сверит ни с каким X.
- **Журналы не освежаются.** docs/04 и docs/05 сохраняют цифры дня работы, и это сознательно;
  значит группа 4 покрывает три файла из восьми.
- **README, docs/01 и docs/02 могут описывать состояние «вчерашним» числом**, если файл не менялся,
  а текст устарел по смыслу — объём тут не индикатор.
- **Прогон CI на GitHub ещё не выполнялся**: шаг `check-docs` там новый, как и `fetch-depth: 0`,
  без которого группа хешей просто пропустится.

## Что меняется в планах из-за этих решений

- docs/04 T2.1 (Postgres) и T3.1 (конфиг API + относительные пути + Pages workflow) переходят из «опциональных» в обязательные Этапа 3.
- ADR-0011: у T3.1 закрыта транспортная половина (`8fef933`): конфиг, клиент, политика 401, дубли, относительные пути, смоук-приёмка «не вечный spinner». Остались `core/layout.js`, `profile.html`, страница 404 и `deploy-frontend.yml` — в них ответ Pages по пункту 5 ADR-0001 (каталоги `login/index.html` или `404.html`-роутер) надо зафиксировать при публикации, а не в конфиге фронтенда. Позднее закрыто ADR-0013 и ADR-0014; из этого списка остаётся только `deploy-frontend.yml` и публикация.
- ADR-0013: T3.1 (`8b3a027`) — общая шапка и подвал в `core/layout.js`, страница `404.html` со статусом 404 и одним JSON/HTML-разделением в `Handlers.NotFound`, один `bindCreateForm` вместо двух копий в `schedule.js`. В планах это снимает три пункта остатка T3.1 и добавляет один: под Pages нужен собственный `404.html` с путями от базового каталога.
- ADR-0014: остаток T3.1 (`ae291e8`) — страница `/profile` из того, что реально хранится, и перенос панели «смена пароля / выйти везде» с кабинета на неё. `docs/04` больше не ждёт B1/B2 для самой страницы: группа и предпочтения остаются открытым вопросом и на профиле явно названы отсутствующими, а не пустыми полями.
- T0.4 закрыт (`docs/04`), кроме одной позиции: сервис-контейнер PostgreSQL и dry-run миграций перенесены в T2.1, где появляется сам SQL-пакет миграций (ADR-0009, пункт 6).
- T4.1 закрыт ADR-0015: артефакт владельца (готовый Python-парсер) принёс адрес,
  способ доступа и живой пример ответа — блок снят, клиент и хранение на Go, страница
  `/schedule` показывает импортированные пары. Открытым остаётся то, что парсер не
  проверяет: ответ боевого `apeks.tksu.ru` (сеть вуза с машины разработки недоступна).
- T4.2 (Telegram) снимается с MVP-трека, возвращается отдельным решением владельца.
- D-01 (собственный домен для Pages) — единственный новый вопрос владельцу; от него зависит, остаётся ли cookie-авторизация или переходим на bearer-токен.
- ADR-0012: T1.2 закрыт (`26066e8`) — `audit_events` пишется из обработчиков и читается администратором, панель в `admin.html` добавлена. Порядок Этапа 3 становится `T1.1 → T1.2 → T2.1 → T3.1`: таблица добавлена до переезда на PostgreSQL, чтобы в `T2.1` диалект менялся у всей схемы разом. Новый открытый вопрос владельцу: срок хранения журнала (`docs/03` §3).
- ADR-0010: T1.1 закрыт (`439a08b`), порядок Этапа 3 меняется на `T1.1 → T2.1 → T3.1` — `T2.1` не проверяема на машине разработки (нет Docker и утилит PostgreSQL), а `T1.1` от типа базы не зависела. Формат ошибок (ADR-0003) намеренно не мигрирован вместе с каркасом: это отдельное изменение, в нём меняются бэкенд, фронтенд и тесты одновременно.
- ADR-0003 закрыт (`fcfc6c9` + `2f68b4e`) именно как отдельное изменение, о котором
  говорилось в пункте выше: конверт отказа, коды, `fields` и их подпись из формы —
  бэкенд, клиент и тесты в одном заходе. Расширение набора кодов (`method_not_allowed`
  для 405, `source_unavailable` для 502/503) — следствие миграции транспорта, а не
  пересмотр решения: без них путь, которого нет в списке методов, отвечал старой
  плоской формой. Из планов это снимает единственный открытый пункт §4 docs/02
  («согласовать до старта Этапа 3») — формат согласован и реализован.
- ADR-0016: T0.5 (доступность) закрывает четыре пункта из `docs/01` §7 и снимает
  пятый, которого не было: `aria-current` введён не будет, пока навигация шапки — это
  действия, а не разделы (пункт 6 выше). Пункт про модалки оказался устаревшим
  записью, а не недостающей работой, — правки нет, есть тест. В очереди `docs/04`
  это внеочередная работа того же типа, что ADR-0003: она не разблокирует ничего из
  заблокированного владельцем, но снимает риск, который копи-правка палитры или
  новая страница возвращают молча. Открытым остаётся то, что требует браузера:
  пиксельная приёмка состояний фокуса и проверка живым скринридером.
  **(Приёмка фокуса сделана ADR-0020, `304f0cc`: `scripts/check-focus.mjs`, восемь
  страниц, 77 элементов, 0 невидимых; из этого списка остался только скринридер.)**
- ADR-0017 снимает из `docs/01` §7 последний пункт про дублирование submit-обработчиков
  (копия в `dashboard.js`) и переводит «общий механизм» из договорённости в проверку CI:
  седьмая группа в `scripts/check-frontend.mjs` падает, если определение `bindCreateForm`
  перестало быть единственным в `common.js`, если страница его не вызывает или если
  страничный скрипт снова написал submit с блокировкой кнопки. Числа UI-прогонов в
  документах после этого шага — 8 сьютов и 364 проверки (277 офлайн; следующий
  ADR-0018 поднял их до 377), потому что
  кабинет добавлен в `schedule-forms.cjs` (55 → 80). Из заблокированного владельцем не
  разблокировано ничего: это тот же внеочередной класс работы, что ADR-0003 и ADR-0016.
- ADR-0018 снимает последний пункт доступности, который не требовал ни браузера, ни
  ответа владельца: `aria-describedby` проставлен в разметке (22 атрибута, 29 ссылок)
  и в генерируемых шаблонах `modals.js` (7 атрибутов, 9 ссылок), а восьмая группа
  `scripts/check-frontend.mjs` не даёт связке молча распасться. Числа UI-прогонов в
  документах после этого шага — 8 сьютов и 377 проверок (286 офлайн), потому что
  `accessibility.cjs` вырос со 103 до 112, а `assignments-modal.cjs` — с 20 до 24.
  В `docs/01` §7 по доступности остаётся только то, что требует живой приёмки:
  пиксельная проверка состояний фокуса и скринридер — оба вне машины разработки.
  **(Закрыто частично ADR-0020, `304f0cc`: приёмка фокуса оказалась доступна на той же
  машине — браузер поднимается скриптом; скринридер по-прежнему требует человека.)**
- ADR-0019 закрывает последний пункт, который ADR-0016 записал как «не сделано» и который
  не требовал ни браузера, ни ответа владельца: контраст посчитан не для 13 выбранных пар,
  а для всего, что задаёт `style.css` и инлайновые `style=""` (26 пар, 19 уникальных
  комбинаций в CSS, одно именованное исключение). Числа UI-прогонов не изменились —
  8 сьютов и 377 проверок: усилен статический слой (`check-frontend.mjs`), а jsdom-сюты про
  пиксели ничего не говорят. Из заблокированного владельцем не разблокировано ничего;
  по доступности оставались только два пункта живой приёмки — скринридер и состояния
  фокуса, и второй из них закрыт ADR-0020.
- ADR-0020 снимает из `docs/01` §7 и из остатков ADR-0016/0019 последний пункт, который
  трижды назывался «требует браузера»: пиксельная приёмка состояний фокуса сделана
  (`scripts/check-focus.mjs`, восемь страниц, 77 элементов, 0 невидимых), найдено и
  исправлено одно невидимое кольцо (радиокнопка входа), а возвращать его не даёт новая
  группа 9 в `check-frontend.mjs` — она работает в CI, где браузера нет. Числа UI-прогонов
  не изменились — 8 сьютов и 377 проверок: jsdom-сюты про отрисовку ничего не говорят,
  живой же прогон фокуса в CI не подключается (на раннере нет браузера) и остаётся ручным
  шагом. По доступности остаётся один пункт — озвучка живым скринридером (NVDA/VoiceOver),
  и он требует человека, а не машины разработки. Новое в `docs/03`: 14 замечаний по
  WCAG 2.2 SC 2.4.13 (поле темнеет слишком слабо, чтобы переход был различим при
  3:1 «до → после») — чтобы это стало провалом, проект должен заявить 2.2 вместо 2.1 AA;
  решение владельцу. Из заблокированного владельцем не разблокировано ничего.
- ADR-0021 (`63f8cb3`) отменяет пункт 1 «Решения» ADR-0015 — часть про «парсер переписан
  на Go» — и
  меняет формулировку «расписание сделано» в планах: `/schedule` по-прежнему рисует
  импортированные пары, но разбирает их приложенный Python-код, а не только репозиторий.
  Из этого следует три вещи для планов. (1) `docs/04`: у T4.1 появляется позиция
  «python3 и requests на хостинге» — она проверяется только при выгрузке, локально
  проверить нельзя, и это же причина, по которой запасной Go-движок не удалён.
  (2) CI из трёх работ стал четырьмя (`go`, `frontend`, `parser`, `ui`) — все места,
  где было «три работы» (`docs/01` §2 и §4, `docs/02` §11, README, `docs/03` §4),
  исправлены этим же коммитом. (3) `docs/03` B2 остаётся открытым и уточняется: кроме
  «кто выдаёт токен и на какой срок» добавляется вопрос про интерпретатор на хостинге.
  Из заблокированного владельцем не разблокировано ничего: B1/D-01 (Pages), сроки
  журнала (§3) и целевой уровень доступности (A10) ждут тех же ответов.
- ADR-0022 (`86edfe9`) снимает внеочередную позицию `docs/04` «приёмка состояний фокуса внутри
  открытых модалок» и закрывает второй пункт «что это не закрыло» в ADR-0020. Из этого следует
  два места в планах. (1) `docs/04`: у ADR-0020 больше нет хвоста про модалки, и в очереди
  остаётся одна названная позиция — подсказка панели источника.
  **(Снята ADR-0023, `b28a036` — внеочередных названных позиций больше нет.)** (2) `docs/01` §7 и `docs/02` §10:
  формулировка «в живом прогоне фокуса модалки не открывались» заменена на актуальную, а список
  «не закрыто» пополнился новым пунктом — набор `MODALS` надо расширять вручную, когда `modals.js`
  получает новый вид диалога. Разблокированного владельцем здесь тоже ничего нет: это тот же
  внеочередной класс (ADR-0003, ADR-0016, ADR-0017), который снимает риск молча вернувшегося
  дефекта. Вопрос A10 (целевой уровень доступности: 2.1 AA или 2.2) остаётся открытым и после
  этого шага — замечаний по SC 2.4.13 стало больше на четыре, потому что к состояниям страниц
  добавились состояния внутри диалогов.
- ADR-0023 (`b28a036`) снимает последнюю названную внеочередную позицию `docs/04` — подсказку
  панели источника, найденную ADR-0021. Из этого следует три места в документах. (1) `docs/04`:
  блок «вне очереди» закрывается, новых названных позиций не остаётся, следующий шаг по плану —
  T2.1, и он по-прежнему упирается в отсутствие Docker и утилит PostgreSQL на машине разработки.
  (2) `docs/02` §5 и §8: контракт `GET /api/schedule/source/status` расширен полем `hint`, а
  `missing_config` описан как имя переменной из состояния сборки, и рядом стоит абзац про то, где
  причина рождается и почему она не читается в обработчике. (3) числа UI-прогонов в документации —
  380 проверок вместо 377 (`schedule-timetable.cjs` вырос с 59 до 62), Go — 245 прогонов `=== RUN`
  вместо 234 и 21 файл тестов вместо 20. Вопрос владельцу B2 (`python3` и `requests` на хостинге)
  остаётся открытым: правка делает его различимым для админа, но не решает. Из заблокированного
  владельцем не разблокировано ничего — это тот же внеочередной класс (ADR-0003, ADR-0016,
  ADR-0017, ADR-0022), который снимает риск ложного следа в диагностике.
- ADR-0024 (`a1e5fa6`) ничего не снимает из очереди `docs/04` — следующий шаг по-прежнему T2.1,
  и он по-прежнему упирается в отсутствие Docker и утилит PostgreSQL. Меняется три места.
  (1) `docs/02` §11: добавлен абзац про новый слой — он первый проверяет сам `cmd/server` как
  процесс, а не как функцию, и закрывает проводку `main.go` → `handlers.Deps`; в §10 состав
  работы `ui` вырос на один шаг. (2) `ci.yml`: в job `ui`
  добавлен шаг `bash tests/source-states-smoke.sh`, число работ не изменилось (их по-четыре),
  изменилось число шагов в одной из них. (3) `docs/01` и README: объём живых шелловых прогонов —
  328 строк в двух скриптах. Из заблокированного владельцем не разблокировано ничего; вопрос B2
  (`python3` и `requests` на хостинге) слой делает только различимым в CI-прогоне: при отсутствии
  интерпретатора состояние «парсер не запускается» теперь падает красным шагом, а не живёт в
  догадке оператора.
- ADR-0025 (этот коммит) ничего не снимает из очереди `docs/04` — следующий шаг по-прежнему T2.1, и
  он по-прежнему упирается в отсутствие Docker и утилит PostgreSQL. Меняется четыре места.
  (1) `docs/02` §10 и §11: работа `frontend` получила второй продукт — согласованность
  документации, — и `fetch-depth: 0`, без которого проверка хешей в CI не работает.
  (2) `docs/01` §2 и README: число статических проверок выросло с четырёх до пяти, а CI-шагов в
  работе `frontend` — с трёх до четырёх. (3) `docs/03` §4: правило «что прогнать перед коммитом»
  пополнилось пунктом про документацию — теперь его исполняет скрипт, а не память автора.
  (4) `docs/01` §7 и README: исправлены три находки — несуществовавший тест-файл, двенадцать
  неоднозначных координат и пять устаревших объёмов. Из заблокированного владельцем не
  разблокировано ничего: это тот же внеочередной класс (ADR-0003, ADR-0016, ADR-0017, ADR-0022,
  ADR-0023), который снимает риск того, что документация начнёт расходиться с деревом молча.
