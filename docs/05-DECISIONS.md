# 05. Принятые решения (ADR)

Владелец ответил на блокирующие вопросы (Этап 1 → Этап 2). Фиксируем как согласованные контракты; менять в одностороннем порядке нельзя (бриф, п.4).

## ADR-0001. Размещение: GitHub Pages + внешний backend

Статус: принято владельцем.

Схема: `web/` публикуется на GitHub Pages; Go API и фоновые задачи — на отдельном хосте с PostgreSQL. Frontend и backend — разные origin-ы, поэтому:

1. **Все пути во фронтенде — относительные** (`./css/…`, `./js/…`, ссылки `./dashboard.html`), чтобы работало под базовым путём `https://<user>.github.io/SOS/`. Плюс `<base>` не используем, ловушка: он ломает якорные ссылки.
2. **`API_BASE_URL` — отдельный конфиг** (`web/js/config.js` со значением по умолчанию для разработки и подменой при публикации), а не хардкод в вызовах.
3. **CORS**: явный allowlist origin-ов Pages, `Access-Control-Allow-Credentials: true`, обработка `OPTIONS` (pre-flight из-за заголовка `Content-Type: application/json` и `X-CSRF-Token`). Пустой allowlist = same-origin режим, заголовков CORS нет.
4. **Cookie-модель — это главный риск схемы, и у него есть дешёвый обход.** `SameSite` считается по **site** = eTLD+1, а не по origin. Поэтому:
   - Если Pages публикуется на **собственном домене через CNAME** (например `sos.example.ru`, а API на `api.example.ru`) — это одна site-зона,существующие cookie `SameSite=Lax; HttpOnly; Secure` продолжают отправляться, CSRF-модель double-submit остаётся валидной, ничего не нужно менять в модели авторизации. **Это рекомендованный путь.**
   - Если Pages остаётся на `https://numerR.github.io/SOS/`, а API на другом регистрируемом домене — запросы становятся кросс-сайтовыми: нужен `SameSite=None; Secure`, и Safari (ITP) по умолчанию блокирует такие сторонние cookie → вход на iPhone/iPad с высокой вероятностью не работает. Придётся переходить на bearer-токен (`Authorization`), что для ванильного JS означает хранение токена в коде страницы/хранилище браузера и перенос риска с CSRF на XSS.
   
   Открытый вопрос владельцу (D-01): есть ли собственный домен для Pages. До ответа код пишем так, чтобы оба варианта переключались конфигурацией (`COOKIE_SAMESITE`, `COOKIE_DOMAIN`, `CORS_ALLOW_ORIGINS`), а фронтенд читал токен авторизации из одного места (`auth.js`), а не из десяти.

5. **Страницы, которые сегодня отдаёт Go** (`/`, `/login`, `/register`, `/dashboard`, `/schedule`, `/admin` из `cmd/server/main.go:72-77` и `internal/handlers/pages.go`), на Pages становятся обычными файлами: либо `login.html` (тогда ссылки `./login.html`), либо сохранение «красивых» URL через `404.html`-роутер на фронтенде. Решение: **используем `.html`-файлы как есть** — предсказуемо на Pages, без JS-роутера и без зависимости от настроек сервера. Роуты `/api/*` уходят из статических путей.
6. GitHub Pages не запускает Go и не даёт PostgreSQL (бриф, п.5) — это и причина схемы; подключение к БД из браузера запрещено, всё через API.

## ADR-0002. PostgreSQL сейчас, версионируемые миграции

Статус: принято владельцем.

- Драйвер: `github.com/jackc/pgx/v5/stdlib` через `database/sql` — код store-пакетов остаётся на знакомом `sql.DB`, без ORM (бриф: без лишних абстракций).
- Собственный runner миграций (~150 строк): `migrations/NNNN_*.sql` + `up`/`down` секции, таблица `schema_migrations(version, applied_at)`, применение при старте, блокировка одновременных применений advisory lock. Внешняя `golang-migrate` не вводим.
- Типы: `bigserial`, `timestamptz` вместо unix-int, `CHECK` на `role`, `score`; ошибки уникальности по `pgerrcode.UniqueViolation` (`23505`) вместо сверки текста (`internal/store/users.go:94,251-253`).
- Локальная разработка и CI: `deploy/docker-compose.yml` (postgres 16 + приложение), в GitHub Actions — сервис-контейнер postgres; тесты миграций на чистом volume.
- SQLite полностью убираем: `SetMaxOpenConns(1)` (`internal/database/db.go:26`) не дал бы параллелить фоновые импортёры и держал бы два диалекта в одном коде.
- Существующие `CREATE TABLE IF NOT EXISTS` из `db.go:43-141` переносятся в `0001_init.sql` без изменения логики; локальная `data/app.db` не мигрируется (дево-файл, в git не попадает).

## ADR-0003. Модульность и единый формат ошибки

- Модули: `internal/modules/<name>` со своими handlers/service/store/migrations + явный реестр (`docs/02-ARCHITECTURE.md` §2-3). Разбор `handlers.New(...)` с 9 позиционными аргументами на `Deps`-struct — первый шаг, иначе каждая новая сущность правит все вызовы.
- Права: реестр permissions + `authz.Can(user, perm)` вместо ~15 мест сравнения строки роли.
- Формат ошибки: `{"error":{"code","message","fields"}}` (коды: `invalid_json`, `validation`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `rate_limited`, `csrf_failed`, `internal`). Бэкенд, `web/js/common.js` и тесты меняются в одном PR.

## ADR-0004. Источник расписания — контракт готов, данные не подтверждены

Владелец указал `https://tksu.ru/bitrix/js/api-apeks-vuz/rasp-stud/rasp-stud.html`. Проверено с этого хоста: DNS резолвится (`86.110.162.34`), подключение не устанавливается ни на 443, ни на 80 («Couldn't connect»/«Network is unreachable» при работающем интернете), снимков страницы и JS виджета в веб-архиве нет (`archived_snapshots: {}`).

Следовательно формат запроса к данным, параметры (группа/дата/семестр) и структура ответа **неизвестны**, и по требованию брифа (п.4: «не выдумывай структуру сайта») парсер не пишется. Что делаем вместо этого:

- Таблицы `schedule_sources`, `schedule_groups`, `schedule_entries`, `import_runs` и API `GET /api/schedule/entries?group_id=&from=&to=` — по контракту из docs/02 §5-6; они от деталей источника не зависят.
- Интерфейс `ScheduleSource { FetchGroups(ctx) ; FetchEntries(ctx, groupKey, from, to) }` и регистрация источника по имени; конкретный адаптер `tksu` остаётся незакрытым с явной отметкой «ожидает подтверждения источника» (критерий готовности MVP, бриф п.8 это допускает).
- UI показывает: нет данных + причину + `last_success_at` из `schedule_sources`.
- Чтобы завершить адаптер, нужен один из трёх артефактов: (1) URL XHR-запроса из DevTools → Network и сырой ответ для одной группы, (2) официальный API университета, (3) сохранённая HTML-страница результата, открытая с сети, где tksu.ru доступен. Также фиксируем: страница-виджет `rasp-stud.html` сама по себе данные не отдаёт — она только загружает JS, который обращается к API «1С:Университет / APEKS»; парсить её HTML бессмысленно.

## ADR-0005. События: только ручное добавление, источник — интерфейсом

Владелец выбрал ручное добавление (Telegram-канал не назван, Bot API с этого хоста недоступен). Поэтому:

- Работает CRUD событий преподавателем/админом; схема расширяется полями `location_text`, `lat/lon (NULL)`, `geo_state`, `category`, `image_url`, `source_url`, `starts_at`, `ends_at`, `published_at`.
- Дедупликация на `UNIQUE(source_id, external_id)` закладывается сразу (для ручных записей `source_id = NULL`, `external_id` не обязателен) — чтобы будущий импорт не требовал изменения схемы.
- Модуль источника `EventSource` остаётся без реализации; в UI и README явно: «источник Telegram не подключён».
- Фиктивных координат и вымышленных мест не заводим (бриф, п.3): без координат событие не попадает на карту.

## ADR-0006. Роли назначает администратор; перебор гасится токен-бакетом в памяти

**Контекст.** Публичная регистрация принимала `role: "teacher"`, то есть любой
посетитель получал права создавать курсы, задания и оценивать чужие работы.
Ограничения частоты запросов не было ни на одном эндпоинте.

**Решение.**

- Регистрация выдаёт только `student`. Роль меняет администратор через
  `POST /api/admin/users/role` (`RequireRole("admin")` + `RequireCSRF`), интерфейс —
  на `/admin`. Собственную роль менять запрещено (409): иначе админ может
  отрезать себе доступ посреди сеанса.
- Смена роли отзывает все сессии пользователя (`DeleteAllForUser`), иначе
  повышенные или отозванные права живут до истечения куки (24 часа).
- Ограничение частоты — токен-бакет (`internal/ratelimit`), три набора: вход по IP
  (20/10 мин), неудачные проверки пароля по аккаунту (5/15 мин), регистрация по IP
  (10/час). Ответ `429` + `Retry-After`. Неудачная попытка отвечает `401`, а `429`
  появляется со следующего запроса — интерфейс «вы заблокированы» не подтверждает,
  что аккаунт существует.
- bcrypt выполняется и для неизвестного логина (фиктивный хэш) — ответ не различается
  по таймингу.

**Последствия и ограничения.**

- Бакеты живут в памяти процесса: за двумя инстансами лимит удваивается, после
  рестарта обнуляется. Для одного приложения это приемлемо; при переходе на
  несколько инстансов нужен общий счётчик (Redis) — зафиксировано в docs/03.
- Ключ — адрес TCP-соединения, если не включён `TRUST_PROXY` (см. ADR-0007).
  За реверс-прокси без этого флага все клиенты делят один бакет — поэтому флаг
  завязан на публикацию наружу, а не включён «на всякий случай».
- Тесты UI и сид теперь требуют админ-сида (`ADMIN_USERNAME`/`ADMIN_PASSWORD`):
  преподаватель больше не появляется «сам из регистрации».
- Блокировка постепенная, а не жёсткая: после исчерпания бакета следующее
  разрешение выдаётся через `window/capacity`, то есть через 3 минуты будет
  доступна одна попытка. Это осознанный выбор в пользу отсутствия фонового
  очистителя и состояния «разблокировать».

## ADR-0007. Остаток T0.2: сборщик сессий, «выйти везде», смена пароля, доверие прокси

**Контекст.** ADR-0006 оставил четыре незакрытых пункта: протухшие строки в
`sessions`, отсутствие отзыва всех сессий пользователем, отсутствие смены пароля
и ключ лимитера, нераспознающий клиента за прокси.

**Решение.**

1. **Очистка — фоновый тикер в процессе, а не отдельный cron.** `cleanSessions`
   в `cmd/server/main.go` делает первый проход сразу при старте (забирает мусор
   между перезапусками) и далее ходит раз в час. Один проход ограничен
   `context.WithTimeout(30s)`; ошибка чистки пишется в лог и не роняет сервер.
2. **«Выйти везде» (`POST /api/auth/logout-all`) снимает и текущую сессию.**
   Кнопка в интерфейсе — это сценарий компрометации, «остаться здесь, выгнать
   остальных» в нём не ожидается. Требует `RequireAuth` + `RequireCSRF`, снимает
   обе куки (`gs_session`, `csrf_token`) и уводит клиента на `/login?revoked=1`.
3. **Смена пароля требует текущий пароль и сохраняет текущую сессию.**
   `POST /api/auth/change-password`: проверка текущего пароля через bcrypt,
   затем `DeleteAllForUserExcept(текущая)`. Отзыв всех сессий кроме текущей —
   сознательный выбор: пользователя не выбрасывает из вкладки, где он только что
   ввёл новый пароль, при этом чужие устройства выходят. Ответ содержит
   `revoked_sessions`, чтобы это было видно человеку. Ограничение — 6 запросов
   на IP за 15 минут: текущий пароль внутри открытой сессии тоже перебирают.
   Новую сессию при смене не заводим: если куки нет, отзываем вообще всё.
4. **`X-Forwarded-For` и `X-Forwarded-Proto` доверяем только при `TRUST_PROXY=true`.**
   `ClientIP` берёт первый валидный IP из `X-Forwarded-For`, иначе — адрес
   соединения; `isSecureRequest` читает `X-Forwarded-Proto` только под тем же
   флагом. Без флага поведение консервативное (лимитер по IP прокси, `Secure`
   только при реальном TLS); с флагом — корректное, но требующее закрытого
   прямого доступа к порту. Один флаг на оба заголовка: их нельзя доверять
   по отдельности.

**Последствия и ограничения.**

- Доверие адресов из `X-Forwarded-For` по-прежнему без списка доверенных
  прокси-хостов: флаг «врубили — закрыли порт», а не «разобрали цепочку».
  Полный разбор (списки CIDR, подсчёт глубины) остаётся заделом на публикацию.
- Верхняя граница длины пароля (`maxPasswordLength` = 200) введена, потому что
  bcrypt читает только первые 72 байта, а длинное тело — бесплатный способ
  замедлить обработчик.
- Смена пароля не пишет запись в `audit_events` (таблицы нет) — только
  структурированный лог (`slog`, ADR-0008). Аудит входит в T1.2.
- `LogoutAll` и `ChangePassword` не отзывают токены мгновенно на стороне
  клиента: вкладка на другом устройстве узнает об этом при следующем запросе,
  что для cookie-сессий и есть механизм отзыва.

## ADR-0008. T0.3: сервер с таймаутами, корректной остановкой, структурированным логом и границами полей

**Контекст.** До этого коммита `ListenAndServe` шёл без единого таймаута, база
вызывалась без дедлайна, логи были `log.Printf` без корреляции между записями,
а текстовые поля заданий/сдач/оценок не имели верхней границы. Это не «гигиена
ради гигиены»: каждый пункт — отдельная отказоустойчивость (Slowloris, висячий
запрос к базе, нечитаемый лог, мегабайтный `title`).

**Решение.**

1. **Таймауты на `http.Server`.** `ReadHeaderTimeout` 5 с, `ReadTimeout` 10 с,
   `WriteTimeout` 30 с, `IdleTimeout` 90 с, `MaxHeaderBytes` 64 КиБ. Заголовок
   ограничен отдельно от тела, потому что режет его именно заголовок: тело и так
   упирается в `MaxBytesReader` (1 МиБ) внутри `readJSON`.
2. **Остановка по сигналу, а не `os.Exit`.** `signal.NotifyContext(SIGINT,
   SIGTERM)` → `server.Shutdown(10s)`. Если за 10 секунд запросы не дошли —
   `server.Close()` принудительно: висящий процесс хуже оборванного запроса.
   Фоновый сборщик сессий останавливается тем же контекстом и дожидается до
   `db.Close()` (иначе горoutine пишет в закрытую базу).
3. **Дедлайн на базе — middleware, а не обёртка вокруг каждого вызова.**
   `WithDBDeadline` ставит `context.WithTimeout(r.Context(), 5s)` на весь
   запрос; обработчики уже передавали `r.Context()` в хранилище, поэтому
   ограничены оказываются все обращения сразу, и пропустить одно структурно
   нельзя. Вариант «обернуть каждый вызов сам» дал бы сотни строк шаблонного
   кода и гарантированно забытый адрес.
4. **`slog` JSON + request id.** `LogRequests` выдаёт идентификатор (8 байт
   `crypto/rand`), кладёт его в контекст, в `X-Request-Id` ответа и в каждую
   строку лога. Чужой `X-Request-Id` принимается только под `TRUST_PROXY`,
   и то не длиннее 64 символов и без управляющих символов — иначе это
   лог-инъекция и способ подделать корреляцию. Тело запроса и ответа в лог не
   пишется: там пароли и содержимое сдач. Уровень по умолчанию `info`,
   `LOG_LEVEL=debug` включает статику.
5. **`__Host-` на сессионную куку при HTTPS.** Имя `__Host-gs_session`
   выпускается, когда запрос защищён (`r.TLS` или доверенный
   `X-Forwarded-Proto`); на локальном HTTP остаётся `gs_session`, потому что
   браузер выбросил бы `__Host-` без `Secure`. Чтение пробует оба имени,
   снимание — всегда оба. CSRF-кука префикса не получила: её читает JS по
   имени `csrf_token`, и double-submit без HTTPS всё равно не сильнее обычной
   куки.
6. **Границы текстовых полей общие для всех mutate-эндпоинтов.** Заголовки —
   200 символов, описания и комментарии — 2000, категория — 64, URL — 2000,
   текст сдачи — 20 000. Считаются символы (`utf8`), а не байты: иначе русская
   сдача на 2000 символов (4000 байт) была бы «слишком длинной». Оценка
   ограничена шкалой 0–10 — ровно той, что задана полем ввода в `modals.js`.
   Курсы, ресурсы и события переехали на общий `validateLength` с сохранением
   прежних текстов ошибок (это покрыто тестом).

**Последствия и ограничения.**

- Проверено живьём (собранный бинарник, изолированная `DB_PATH`): соединение с
  недописанными заголовками закрыто без единого байта ответа через 5.01 с при
  `ReadHeaderTimeout` 5 с; `POST` с телом 20 КБ из заявленных 900 КБ, начатый до
  `SIGTERM`, получил `400 Bad Request` через 10.001 с (сработал `ReadTimeout`,
  сервер за это время не бросил активные соединения) и процесс завершился с
  кодом 0 и строкой `сервер остановлен корректно`; `/api/health` отдаёт
  `{"status":"ok","db":"ok"}` и `503 {"status":"error","db":"error"}`, если база
  не ответила за секунду; при `TRUST_PROXY=true` и `X-Forwarded-Proto: https`
  `Set-Cookie` уходит под `__Host-gs_session; Secure`, без заголовка —
  обычный `gs_session`; `title` из 201 символа даёт `422 {"error":"title is too long"}`,
  из 200 — `201` (граница inclusive, счёт в рунах: проверено на кириллице).
- `WriteTimeout` 30 с отключает долгие стриминговые ответы. Сейчас их нет;
  если появится выгрузка отчётов — для неё нужен отдельный обработчик со своим
  таймаутом, а не общий.
- Дедлайн в 5 с на запрос — это и лимит на «тяжёлые» future-выборки (лента по
  всем курсам). При переходе на PostgreSQL (T2.1) значения стоит пересмотреть
  по реальным замерам, а не по вкусу.
- Логи идут в stdout: файл-ротацию и сборщик делает платформа, а не приложение.
- Request id коррелирует строки одного запроса, но не связывает их с записями
  в базе: для этого нужен `audit_events` (T1.2).

## ADR-0009. T0.4: CI из трёх работ, проверка целостности фронтенда без сборки

**Контекст.** Класс багов T0.1 (`web/js/modals.js` лежал на диске, был
синтаксически валидным, но ни одна страница его не подключала, а `dashboard.js`
вызывал `ModalManager` → `ReferenceError`) не ловится ни `go test`, ни
`node --check`: файл целый, просто никем не ссылается. В репозитории не было ни
одного workflow — `.github/` отсутствовал.

**Решение.**

1. **Три работы вместо одной.** `go` (gofmt, `go vet`, `go build`,
   `go test -race -count=1`), `frontend` (`node --check` по каждому
   `web/js/*.js` + `scripts/check-frontend.mjs`), `ui` (jsdom-тесты против
   живого сервера). `ui` нуждается в первых двух: гонять полный прогон сервера
   ради теста, который падает на формате или синтаксисе, — способ получить
   красный CI без понимания причины.
2. **Целостность фронтенда проверяется по четырём признакам, а не «на глаз»:**
   каждый `<script src>` и `<link href>` указывает на существующий файл; каждый
   JS-файл в `web/js/` подключён хотя бы одной страницей (это и есть детектор
   бага T0.1); каждая `getElementById`-мишень объявлена на той странице, где
   запускается скрипт — в HTML или в разметке, которую скрипт сам вставляет;
   в HTML нет инлайновых `on*`-обработчиков.
3. **История прогона — в `npm ci`, значит lockfile в репозитории.**
   `tests/ui/package-lock.json` закоммичен: без него `npm ci` падает, а `npm
   install` каждый прогон тянет свежие версии jsdom, и UI-тесты начинают
   валиться по причинам, не связанным с кодом проекта.
4. **Пароль сида в workflow — не секрет.** `ADMIN_USERNAME`/`ADMIN_PASSWORD`
   в `env` работы `ui` питают одноразовую SQLite-базу внутри раннера, которая
   умирает вместе с ним; они не дают доступ ни к чему живому. Настоящие
   учётные данные (будущий `DATABASE_URL` прод-базы, `TELEGRAM_BOT_TOKEN`)
   по-прежнему только в GitHub Secrets и в логи не выводятся.
5. **Триггеры: `pull_request` + push в `main` + ручной запуск.** Push в
   feature-ветку CI не гоняет: для открытого PR это удвоило бы прогоны на тот же
   коммит. Проверки всё равно видны до слияния — на PR.
6. **PostgreSQL-часть приёмки T0.4 перенесена, а не сделана наполовину.**
   Сервис-контейнер `postgres` и dry-run миграций появляются вместе с T2.1:
   сейчас схема применяется кодом (`internal/database/db.go`), отдельного
   SQL-пакета нет, поэтому «прогон миграций на чистой БД» в CI сегодня означал бы
   проверку несуществующего файла.

**Последствия и ограничения.**

- Проверено локальным прогоном тех же команд на чистой копии репозитория: gofmt
  пусто, `go vet`, `go build`, `go test -race -count=1 ./...` зелёные; `node
  --check` по всем 8 файлам; `check-frontend.mjs` — 6 страниц, 8 файлов, ок;
  сервер + `tests/ui/seed.sh` + `npm ci` + `npm run test:all` → 20/20, 11/11,
  22/22. Детектор бага T0.1 проверен на намеренно сломанных копиях: удаление
  строки `<script src="/js/modals.js">` → `FAIL modals.js не подключён ни к
  одной странице`; удаление файла → `FAIL подключён несуществующий скрипт`;
  инлайновый `onclick` и фантомный `getElementById` → тоже FAIL.
  Версии `actions/checkout@v4`, `actions/setup-go@v5`, `actions/setup-node@v4`
  зафиксированы явными тегами.
- Что нельзя проверить локально: сам GitHub-раннер (версии образов, поведение
  `actions/*`). Первый прогон закрыл и это: run 40037668304 на коммите `d4a2141`
  (`pull_request`) — `completed / success`, три работы зелёные, UI-шаги (build,
  `npm ci`, запуск сервера, `seed.sh`, `test:all`) прошли на `ubuntu-latest`.
- `check-frontend.mjs` не исполняет JS: он проверяет связи. Поведение страниц
  по-прежнему закрывают jsdom-тесты, а не этот шаг.
- `go test -race` на macOS/Linux требует gcc для раннего этапа — на
  `ubuntu-latest` он предустановлен; если CI переедет на контейнер без gcc,
  флаг придётся убрать или добавить `apt-get install`.

## Что меняется в планах из-за этих решений

- docs/04 T2.1 (Postgres) и T3.1 (конфиг API + относительные пути + Pages workflow) переходят из «опциональных» в обязательные Этапа 3.
- T0.4 закрыт (`docs/04`), кроме одной позиции: сервис-контейнер PostgreSQL и dry-run миграций перенесены в T2.1, где появляется сам SQL-пакет миграций (ADR-0009, пункт 6).
- T4.1 (парсер расписания) остаётся заблокированным до артефактов из ADR-0004; готовим контракт и хранение.
- T4.2 (Telegram) снимается с MVP-трека, возвращается отдельным решением владельца.
- D-01 (собственный домен для Pages) — единственный новый вопрос владельцу; от него зависит, остаётся ли cookie-авторизация или переходим на bearer-токен.
